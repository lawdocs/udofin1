## What the screens do and do not do

- **The secret prefix is shown, not secret.** The lender draft form reads `GET /v1/lender/secret-ref-prefix?lenderId=` and says "Your provider secret names must start with `<prefix>`". Both name fields are pre-filled with the prefix (the person types the rest), carry a browser `pattern` made from it, and the operation checks the shape again (`PaymentConfigDraftInput`, which the API uses) and, when the form carries the prefix it showed, that both names start with it. The form's copy of the prefix is never trusted and never sent on: the API and the database derive the real prefix and judge the names. When the prefix cannot be read, or is for another lender, or is not the shape of a prefix, no draft form is drawn and the page says why in words.
- **The prefix is not judged as a value.** Its twelve hexadecimal digits can form a long run of digits, which the old "looks like a secret value" rules refuse. Those rules now judge only what the lender typed after the prefix. A pasted value is still called a value (lower case, long digit runs, long hexadecimal runs, long unbroken runs, symbols), before anything is said about prefixes.
- **Withdrawals are history, not deletion.** A merchant claim that was never verified and a settlement account request that was never linked can be withdrawn from the lists, with a confirm tick and no reason (the contract has none). The words: the row stays in the list as history, is not used again, and the same identifier or the same bank and masked reference can be asked for again later as a new request that starts unverified. A verified merchant and a linked account are revoked by the platform team, and the page says so. Which rows show the control follows `payments.withdraw_merchant_claim` and `payments.withdraw_settlement_account` (status `active` and `unverified` and owned by the lender; status `unverified` and no registry link). Nothing promises approval, verification or speed.
- **A hold is said, and the forms that it blocks are not drawn.** The lender's configuration page shows who put it on hold (the platform team, or the system after a check) and since when, and says what it stops (submit and retire of that configuration; submit and approval of any other configuration of the organisation) and that only the platform team releases it. Submit and retire are not drawn while a hold stands (the API refuses both with `platform_hold`). A suspended configuration without a hold keeps its submit form. The history shows "Hold released by the platform team" without "from suspended to suspended".
- **The own-account list is the platform's statement, with evidence.** `/accounts/own-accounts` says in plain words what the list is, that until it is attested no lender account can be verified or linked and payments and mandates cannot be switched on, that an attestation is the platform's own statement made by one member of staff, that it is not proof and is only as good as the evidence named, and that a key rotation needs a fresh one. It never uses the words compliance, regulation or safety (a test scans every page).
- **A hold is released with the rule said first.** `/providers/holds` lists suspended configurations of every lender (or one), with the kind of hold ("Held by the platform (a member of Udofin staff suspended it with the kill switch)", "Held by the system (the nightly check, or an automatic suspension after a mismatch)"), since when, the mode (test configurations say "test only"), and the reasons in words. The release form (provider manage right) asks for a reason of 10 to 200 plain characters. The rule for lifting is written above the form before anybody tries: a hold set by a member of staff is lifted only by a different member of staff; a system hold by any member of staff with the right. The contract carries `holdKind` and `holdSetAt` but not who set the hold, so the page says it cannot tell and asks the person who used the kill switch to hand over to a colleague; after a `self_approval` refusal it says the same again. No button without a hold, none for a configuration that is not suspended, none for a role without the right.
- **No server text on a screen.** Every sentence comes from a closed table keyed by the stable code. A code the table does not know becomes the generic sentence. The links that follow a refusal (to the own-account list, the registered accounts, the held configurations) are fixed pages chosen by a closed code, never by anything the server wrote.
- **One allow-listed operation per form, answer checked.** The new operations check their fields, send an `Idempotency-Key` minted when the page renders (a double click or a replay of the same rendered form sends the same key, so the API applies it once), check the answer against the contract and against what the operation was meant to do (an attestation must leave the list attested; a withdrawal not attested; a release must name this configuration, still suspended; a withdrawal must name this record, revoked), and report anything else as `bad_response`.
- **The BFF holds no permission of its own.** As for every earlier form, the portal hides the control from a role that may not use it, and the API and the database refuse the call again (`forbidden`, `mfa_required`, `self_approval`). The tests cover both halves: the control is not drawn, and the refusal comes back as a code with a sentence and nothing changed.

## Not built, deviations and open gaps

1. **Reason length of a release is 10 to 200 characters** (the brief), stricter than the contract and the database (10 to 1000). Anything the form accepts, the API accepts. Say if it should follow the contract.
2. **Who set a hold is not known to the screens.** The contract has `holdKind` and `holdSetAt` only. The rule is said before the person tries, and again after a `self_approval` refusal; it cannot be said "you set this one". Adding `holdSetBy` (or a boolean "set by you") to the platform read would let the page hide the button from that person.
3. **No platform screen for the kill switch or for retiring a configuration.** The API has `suspend` and `retire` under `/v1/platform/payment-configs/:id`; the brief did not ask for them and the page only releases a hold.
4. **The lender's list table does not show the hold.** The hold is on the configuration page only; the list shows the status "Suspended".
5. **`own_account_list_not_attested` and `merchant_already_claimed` are worded for the lender portal but no lender route answers them today** (the claim never reveals other claims; activation needs the platform). The wording stays in case a route starts to, and says nothing about who else holds an identifier.
6. **The pages are not unit tested** (no runner in the portals). The two new pages are thin (session, loaders, draw); their logic lives in portal-kit. The production builds of both portals succeed.
7. **Page frame navigation** (`apps/ops-portal/components/page-frame.tsx`, not mine) is unchanged: the new pages are reached from the in-page tabs ("Own-account list" on the registry pages, "Suspended payment configurations" on the provider pages).
