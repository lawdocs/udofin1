## 2. Decisions and deviations from the brief

1. **A6 (item 6) is not "delete the stored blob".** The route already asks the database first and stores the object only afterwards, and it decides `existing` by the same lookup the database uses, so a re-sent document with a request id never stored a second object. The real defect is the race between the lookup and the registration: two requests for the same new reference both find nothing, the second then fails on the unique reference with a spurious 409, and if the database ever answered "existing" after the route had decided "new" the route would store an object nothing points to. The database function returns only a uuid and no role can read `storage_key`, so the route cannot learn afterwards which key won. A per-reference advisory lock makes the second request wait, find the first one's record and store nothing. The quotation route stores no object, so it needs nothing. The residual case (a machine feed registering the same reference between the lookup and the call) is not covered and is practically empty: the bytes would have to be equal.
2. **Audit codes of a refused file (item 3).** `servicing.record_rejected_file` (migration 911) lists the codes it accepts and answers 22023 `errors_invalid` for any other; migration 925 did not add `ref_looks_personal` and `receipt_date_in_future` to that list (checked in the built database). Adding them to the route's `AUDIT_CODES`, as the hand-off said, would turn a refused file into a 422 for the lender. The answer therefore names the real class, and the audit record keeps the nearest listed class (`invalid_reference`, `invalid_date`) until the list is extended. See needs 1.
3. **The debits test (item 5d) also needed the planned debits moved from today+2 to today+3.** Migration 921 no longer offers a planned debit as "next debit" when the lender's newest report says the installment was already due before its next due date (`report_shows_paid`); the report fixture says the next due date is today+3. This is the corrected behaviour, not a regression, and is not in the hand-off.
4. **Event-field copies.** `parentPaymentRef` had to be added in two places (the worker mapper named in the brief and `toDeliveryJson` in `system/provider-hooks.ts`); with only the first, the field would have been dropped before the database.
5. **`recordOrder` skips the link for any status but `pending`**, not only for the three closed statuses: the same answer comes back for a repeat of the job after the payment moved on, and a link for a payment that is not pending cannot be taken anyway.
6. **`cancelMandate` on a finished mandate** sends the request as asked. If the provider answers that it refuses or does not support it, the job ends dead with `mandate_cancel_refused` and an error line asking an operator to look, although the mandate may already be cancelled there. That follows the instruction; the noise is the price.
7. **Waiting-time ceilings** (1..7 days, 1..168 hours) are the SQL builder's own unverified limits; the form says so ("not taken from any agreement"). The portal operation still does not refuse a value for a business reason (its stated rule); the API contract does.
