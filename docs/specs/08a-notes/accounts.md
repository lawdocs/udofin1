## 0. The one thing downstream code must understand: nothing can be registered yet

`payments.account_format_rules` is seeded with ONE row: `IN`, `bank_account`, version 1, 9 to 18 digits, `ifsc_required` true, `status = 'draft'`, `evidence_label = 'unverified'`, `source_note = 'initial assumption, no source on file'`, `drafted_by`, `submitted_by` and `approved_by` all null. `payments.register_account` refuses (55000, hint `account_format_unvalidated`) unless the rule is APPROVED and effective. Until the platform approves a rule through the two-person flow there is NO registry entry, therefore no verified settlement account, no valid collection target, no active configuration, no payment intent, and the `payments` switch cannot be enabled. This is by design (fail closed) and is tested. To open it, the owner must supply the source for the rule (or a different rule); then: a user with `platform.accounts.registry.manage` calls `payments.submit_account_format_rule(rule_id)` (takes responsibility for proposing the seeded draft) or `payments.draft_account_format_rule(...)` (a new version, proposer = drafter), then a DIFFERENT user with `platform.accounts.registry.verify` calls `payments.approve_account_format_rule(rule_id, note)`. Approving retires the previously approved version of the same (country, account_type) in the same transaction. Approving an `unverified` rule is a recorded platform decision, not evidence: the controls matrix must say so.

The registry, merchants, providers, configurations and settlement accounts are all EMPTY after migration. Nothing in this migration seeds an account, fingerprint, merchant, provider, owner or configuration. Fixtures in tests are SAMPLE and synthetic.

## 2. Functions

All definer functions: `set search_path = ''`, fully qualified, `revoke all ... from public`, explicit grants. "Platform" functions need the permission now and `aal2` (hint `mfa_required` otherwise). Idempotent unless stated. Audited through `audit.events` with identifiers and codes only (never a fingerprint, token hash or number). Return values are the new status text unless stated.

Account format rules (platform):

- `payments.draft_account_format_rule(p_country text, p_account_type text, p_min_digits int, p_max_digits int, p_ifsc_required boolean, p_evidence_label text, p_source_note text, p_effective_from date default null, p_effective_to date default null) returns uuid`. `platform.accounts.registry.manage`. The drafter is also the proposer. Hints 22023 `rule_invalid`, `source_note_required`, `dates_invalid`.
- `payments.submit_account_format_rule(p_rule uuid) returns text`. `registry.manage`. For a draft with no proposer (the seeded one). 55000 `rule_not_draft`, `already_submitted`.
- `payments.approve_account_format_rule(p_rule uuid, p_note text default null) returns text`. `platform.accounts.registry.verify`, a DIFFERENT person than drafter and proposer (42501 `self_approval`); the proposer must still hold registry.manage (`requester_not_entitled`); 55000 `not_submitted`, `rule_not_draft`.
- `payments.retire_account_format_rule(p_rule uuid, p_reason text) returns text`. Either registry permission (fail closed); reason 10 to 1000 chars (`reason_required`, `reason_invalid`).

Registry (platform):

- `payments.register_account(p_fingerprint text, p_key_version int, p_masked_ref text, p_country text, p_account_type text, p_format_rule_id uuid, p_format_validated boolean, p_owner_kind text, p_owner_org_id uuid, p_legal_owner_name text, p_permitted_purposes text[], p_effective_from date, p_effective_to date, p_idempotency_key text) returns uuid`. `registry.manage`. Refuses with 55000 `account_format_unvalidated` when the rule is null, not found, not APPROVED, not effective, for another country or account type, or `p_format_validated` is not exactly true. The database never sees the number: the API must validate the number against the approved rule BEFORE computing the fingerprint and then attests `true`. 23505 `account_already_registered` (same fingerprint and key version: one entry per real account, so one account cannot sit under two owners); 23505 `idempotency_conflict`; 22023 `fingerprint_invalid`, `key_version_invalid`, `masked_ref_invalid`, `owner_invalid`, `legal_owner_name_invalid`, `purposes_invalid`, `dates_invalid`, `bad_request`. Stays `unverified`.
- `payments.verify_account(p_registry uuid, p_evidence_ref text, p_note text default null) returns text`. `platform.accounts.registry.verify`; a different person than the registrant (42501 `self_approval`); the registrant must still hold registry.manage; evidence reference required (22023 `evidence_invalid`); 55000 `not_unverified`, `not_effective`.
- `payments.reject_account(p_registry uuid, p_reason text)` (unverified -> rejected) and `payments.revoke_account(p_registry uuid, p_reason text)` (unverified or verified -> revoked). EITHER registry permission, one person, reason 10+ chars, recorded and audited. Revoking or rejecting, in the same transaction, sets every linked settlement account to `revoked` and suspends every ACTIVE payment configuration that settles into it (`status_reasons = {destination_account_revoked}` or `_rejected`).
- `payments.link_settlement_account(p_account uuid, p_registry uuid) returns text`. `registry.manage`. THE path by which a settlement account becomes `verified`: proves the registry entry is verified, owned by this lender, permitted for repayment_settlement, effective now, same masked reference. 55000 `registry_not_permitted`, `masked_ref_mismatch`, `already_linked`, `settlement_account_revoked`. A table trigger (`private.guard_settlement_account`) enforces the same proof for any other writer (55000 `settlement_account_unproven`); the link and the masked reference are permanent; a revoked account is final.
- `payments.my_settlement_account_registry_status() returns table (settlement_account_id, lender_org_id, masked_ref, verification_status, effective_from, effective_to, usable boolean)`. Lender users with `payment.read`: their OWN linked accounts only; never the fingerprint, owner or reasons. `usable` is computed live from the registry.

Classification and validation (SYSTEM only: `private.invoking_role() = 'service_role'`, else 42501):

- `payments.classify_destination(p_fingerprint text, p_key_version int, p_lender uuid, p_purpose text) returns jsonb` `{decision: permitted|hold|refused, reasons: text[]}`. Pure function of registry state, looks up by (fingerprint, key_version). unknown -> refused `account_unknown`; unverified -> hold `account_unverified`; rejected -> refused `account_rejected`; revoked -> refused `account_revoked`; owner_kind not lender for repayment_settlement -> refused `owner_prohibited`; owner organisation <> p_lender -> refused `owner_mismatch` (so a non-lender-owned account is NEVER permitted in a lender context, whatever the purpose); purpose not in permitted_purposes -> refused `purpose_not_permitted`; outside the dates (IST, effective_to exclusive) -> refused `not_effective`; malformed input or unknown purpose -> refused `input_invalid`. Reasons accumulate; any refusing reason makes the decision `refused`, `hold` only when `account_unverified` is the sole reason. Only `permitted` passes.
- `payments.validate_collection_target(p_config uuid) returns jsonb` `{ok boolean, reasons text[]}` (reasons in check order). Spec 7.1 steps 1 to 4, reading everything live: (1) organisation is an active lender with the onboarding gate `activated` (`organisation_not_lender`, `lender_organisation_not_active`, `onboarding_gate_not_activated`); (2) the settlement account is this lender's, status verified, has a registry entry that `classify_destination` permits for repayment_settlement for THIS lender, masked references equal (`settlement_account_not_found|not_verified|unregistered`, `destination_<classify reason>`, `settlement_masked_ref_mismatch`); (3) the merchant is this lender's own active repayment merchant at this provider (`merchant_not_found|not_active|not_repayment|owner_mismatch|provider_mismatch`); (4) the provider is registered and approved, production mode needs `authorisation_evidence_ref`, mock only where the session allows it, sandbox likewise (`provider_not_registered|not_approved`, `provider_evidence_missing`, `provider_mode_mock_blocked`, `provider_mode_sandbox_blocked`); evidence and contract references present (`config_evidence_missing`, `contract_section_missing`). Step 5 (provider response bound back to the configuration) is runtime: call `system_suspend_payment_config`.
- `payments.system_suspend_payment_config(p_config uuid, p_reason_code text) returns text`. Idempotent hold of an ACTIVE configuration (for example `merchant_mismatch`); a configuration that is not active is returned as it is.
- `payments.revalidate_payment_configs(p_lender uuid default null) returns table (config_id uuid, ok boolean, reasons text[], suspended boolean)`. Nightly (or after a registry change): revalidates every ACTIVE configuration and suspends any that is not ok (system hold, reasons recorded).

Merchants and providers:

- `payments.set_payment_provider(p_provider text, p_display_name text, p_kind text, p_status text, p_authorisation_evidence_ref text, p_evidence_label text, p_reason text default null)`. `platform.payments.providers.manage`. Upsert; status draft | approved | suspended; kind payment | mandate | payment_and_mandate.
- `payments.claim_merchant(p_lender uuid, p_provider text, p_merchant_ref text) returns uuid`. Lender user with `payment.configure` for `p_lender`. Idempotent for the same lender; 23505 `merchant_already_claimed` for anyone else (including a claim against Udofin's fee merchant).
- `payments.register_udofin_fee_merchant(p_provider text, p_merchant_ref text) returns uuid`. `platform.payments.providers.manage`. Udofin's own fee merchant (owner_kind `udofin_fees`, purpose `fee_collection`); a configuration can never reference it (composite key to its own lender).
- `payments.revoke_merchant(p_merchant uuid, p_reason text)`. `providers.manage`. The id stays taken; ACTIVE configurations using it are suspended in the same transaction (`merchant_not_active`).

Payment configuration lifecycle (lender-side functions answer P0002 "not found" to anyone who does not hold the permission in the configuration's lender: no existence oracle):

- `payments.draft_payment_config(p_lender uuid, p_provider text, p_provider_mode text, p_merchant_registry_id uuid, p_settlement_account_id uuid, p_secret_ref text, p_webhook_secret_ref text, p_endpoint_token_hash text, p_rail_limits jsonb, p_rail_limits_source text, p_evidence_ref text, p_contract_section_ref text, p_idempotency_key text) returns uuid`. Lender user with `payment.configure`, aal2. Mock/sandbox via the foundation helper `private.assert_provider_mode_allowed` (22023 `provider_mode_invalid`, 42501 `mock_provider_blocked` / `sandbox_provider_blocked`). 22023 `secret_ref_invalid`, `endpoint_token_hash_invalid`, `rail_limits_invalid`, `provider_invalid`, `merchant_invalid`, `settlement_account_invalid`; 23505 `endpoint_token_in_use`, `idempotency_conflict`.
- `payments.submit_payment_config(p_config uuid) returns text` (draft or suspended -> pending_approval; `payment.configure`; re-validates: 55000 `collection_target_invalid`, first reason code in the MESSAGE `collection target invalid: <code>`).
- `payments.decide_payment_config(p_config uuid, p_approve boolean, p_note text default null) returns text`. `payment.config.approve`, a DIFFERENT person than drafter and submitter (42501 `self_approval`); the submitter must still hold payment.configure; approval re-runs the validation (55000 `collection_target_invalid`) and a table trigger re-checks it on any activation, whoever writes; rejection retires and needs a note (22023 `reason_required`).
- `payments.withdraw_payment_config(p_config uuid, p_reason text)` (draft or pending -> retired; `payment.configure`).
- `payments.suspend_payment_config(p_config uuid, p_reason text)`. Platform kill switch: `platform.payments.providers.manage`, aal2, one person, active -> suspended.
- `payments.retire_payment_config(p_config uuid, p_reason text)`. Active or suspended -> retired; platform (providers.manage) or the lender's approver.

State machine (trigger `private.protect_payment_config`): draft -> pending_approval | retired; pending_approval -> active | retired; active -> suspended | retired; suspended -> pending_approval | retired (a suspended configuration needs a fresh two-person approval); retired is final. Content never changes after drafting.

## 3. Payment intents (existing table)

Trigger `payment_intents_collection_target` (before insert, definer): `config_id` is REQUIRED; the configuration must be of the same lender and ACTIVE and `validate_collection_target` must be ok at the moment of insert, with the settlement account, merchant and registry rows locked `for share` so a concurrent revocation cannot slip between check and insert. Otherwise 55000, hint `collection_target_invalid`, message `collection target invalid: <first reason code>` (`config_required`, `config_not_found`, `config_not_active`, or a validation reason). A free-text `settlement_account_ref` other than null or the marker `via_payment_config` is refused (22023 `free_text_settlement_ref`). The trigger fills `settlement_account_id` and `provider_mode` from the configuration; a different `settlement_account_id` is refused (23503 `settlement_account_mismatch`), a different `provider` or `provider_mode` too (55000 `provider_mismatch`). `config_id`, `provider_mode` and the account are immutable (existing whole-row guard). A mock intent exists only where mocks are allowed (guard trigger on insert).

## 5. Gotchas for downstream streams

- The API computes the fingerprint (`fingerprintAccount` in `@udofin/adapters`: keyed HMAC over the bank code (first four IFSC letters) and the account number; see ports.md). It must (a) read the APPROVED rule (`status = 'approved'`; the adapter's rule `status: 'verified'|'unverified'` is the evidence label, not the DB `status`, so map carefully), (b) validate the number against it, (c) compute the fingerprint, (d) call `register_account(..., p_format_validated => true, ...)`. A new fingerprint key version means RE-REGISTRATION (different fingerprint, same real account); classification looks up by (fingerprint, key_version). The `owner to confirm` bank-code rule in ports.md is unchanged by this stream.
- The platform cannot read lender configurations through the registry permissions: a platform user needs `platform.payments.providers.manage` (or an operations role with `payment.read`) to list them. The registry users DO get a read policy on `tenancy.lender_settlement_accounts` (masked reference, label, bank name) so they can find the account to link.
- `service_role` can no longer update or delete `tenancy.lender_settlement_accounts` (insert and select only): an unverified row is created by the system on a lender request; only `link_settlement_account` (and the revocation cascade) change it.
- `service_role` cannot read `payments.account_registry`, the rules or any history table: system code asks `classify_destination` / `validate_collection_target`. For routing a callback, the system selects `lender_payment_configs` by `endpoint_token_hash` (hash the presented token with SHA-256 first).
- Mock configurations (`provider_mode = 'mock'`) need `udofin.allow_mock_providers = on` for the session, both to draft and to validate. In staging/production the setting is off, so a mock configuration cannot be created and an existing one fails validation (`provider_mode_mock_blocked`) and is suspended by the nightly run. A sandbox configuration is refused the same way (`udofin.allow_sandbox_providers`).
- Registry cascade: revoking or rejecting an entry suspends the configurations that settle into it IMMEDIATELY (same transaction) and validation reads the registry live, so even with the cascade bypassed an intent is refused (tested).
- Test fixtures that insert payment intents directly must call `pg_temp.sample_collection_config` (see 002/003/004/009/013/015) or build the same chain; the helper inserts as the table owner, bypassing the workflow functions on purpose.
- Audit action names: `payments.account_format_rule.{drafted,submitted,approved,retired}`, `payments.account_registry.{registered,verified,rejected,revoked}`, `payments.settlement_account.linked`, `payments.provider.set`, `payments.merchant.{claimed,registered_fees,revoked}`, `payments.config.{drafted,submitted,approved,rejected,withdrawn,suspended,retired}`.

## Review fixes after the independent review of this wave (15 October 2026)

These change the interface above; read them before building on it.

- **Fingerprint key versions (FC-1).** New table `payments.fingerprint_key_versions` (status `proposed` / `active` / `retired`; at most one active and one proposed). Nothing is seeded: until a version is proposed (`payments.propose_fingerprint_key_version`, registry manager) and approved by a different registry verifier (`payments.approve_fingerprint_key_version`) the registry accepts no entry and nothing classifies as permitted. `account_registry.key_version` now references it. `payments.register_account` gained two parameters at the end: `p_other_fingerprints jsonb default '{}'` (the same account's fingerprint under every OTHER live version, `{"<version>": "<fingerprint>"}`, computed by the backend, which holds the keys) and `p_rekeys uuid default null` (the entry being re-keyed). Only the ACTIVE version takes a registration; the PROPOSED version takes only a re-key. An account already registered under another live key is refused (`account_registered_under_other_key`) unless this call is its re-key. Activating a version is refused (`rotation_incomplete`) while any unverified or verified entry under the old version has no successor (`rekeyed_from_id`), and a successor of a verified entry must itself be verified; the old version is retired in the same step. `classify_destination` and the settlement-account proof treat an entry under a non-active version as refused (`key_version_not_active`). Operational consequence: a rotation means re-registering and re-verifying every live account and re-linking the lender settlement accounts, and payments for those lenders are held until that is done. Rotation is meant for a key compromise; it is not routine.
- **Merchant verification (FC-2).** `merchant_registry` gained `verification_status` (`unverified` / `verified`), `verification_evidence_ref`, `verified_by`, `verified_at`. A lender's claim starts unverified; `payments.verify_merchant(p_merchant, p_evidence_ref)` (platform, `platform.payments.providers.manage`, aal2) verifies it once. `validate_collection_target` adds the reason `merchant_not_verified`. Udofin's own fee merchant is registered verified by the platform.
- **Provider kind (FC-3).** A collection configuration needs a provider whose register kind is `payment` or `payment_and_mandate`: `draft_payment_config` refuses others (`provider_invalid`) and validation adds `provider_kind_not_payment`.
- **Segregation across memberships (FC-4)** is in `foundation.md`.
- **Test fixtures.** The `pg_temp.sample_collection_config` helper (002, 003, 004, 009, 013, 015) and the integration fixture in `lender-panel.integration.test.ts` now also activate key version 1 and insert a verified merchant. The placeholder assertion in 016 is replaced by a column list check. Rotation is tested in `016_p08a_key_rotation.test.sql`.
