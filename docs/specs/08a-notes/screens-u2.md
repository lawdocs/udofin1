# Phase 08a notes: borrower app screens for payments and auto-pay mandates (builder u2)

Code: `apps/mobile/app/(app)/payments/**` (the screens), `apps/mobile/src/borrower/payments*.ts`, `mandates*.ts`, `usePayments.ts` (client calls, view data, polling, link handling, error words), `apps/mobile/src/i18n/{en,hi}.payments.ts` (keys `pay.*` and `mandate.*`), tests in `apps/mobile/test/payments.test.ts`. The API these screens call is described in `api-payments.md`; the contracts are `packages/contracts/src/http/payments.ts` (every export prefixed `Bp`). Spec: `docs/specs/08-servicing-payments-mandates-collections.md` sections 7.2, 8 and 17. Nothing in this note claims regulatory compliance: it says what the screens do and do not do.

## What the screens do and do not do

- **Show, never work out.** Every amount, date, limit and stage is the one the API returned, put into a sentence (rupees with Indian digit grouping from integer paise, dates and times in India time with "IST" on times). Nothing is added, rounded, totalled, netted or inferred, and no stage is derived. The one place two API fields meet is the headline of a payment (`stage` and `status`, see below); it is a table, not a calculation.
- **Whose figure and when.** "As reported by {lender} on {date, time IST}" is shown next to figures. Out-of-date figures get a plain banner with the date. Withheld figures (the API says `figuresAvailable: false`) get "{lender} is checking these figures" and no amount: the screen never writes a zero for a missing figure.
- **Payment words.** Started; "Received by the payment provider" (with a sentence that this does not yet mean the lender has posted it); "{lender} has posted it to your loan"; "Needs attention: contact {lender}"; and, only for a payment still at stage `started`, cancelled, did not complete, expired. Nothing says "paid" or "successful" (a test scans every stage and status word in both languages). The headline reads the API `stage` first (money reported, posted or needing attention always wins over the request's own status) and only then the status; an unknown stage becomes a generic sentence.
- **No server text on a screen.** Closed vocabularies and stable error codes go through tables; a value or code the table does not know becomes a generic sentence, never the value (tested with drifted values). The provider's return code of a debit is never shown, only its class when the lender classified it. The lender's name and the lender's approved penal-charge sentence are lender-supplied text shown as given.
- **Overdue.** The lender's approved penal-charge sentence is drawn exactly as returned (not trimmed, not reworded) inside the overdue option. When the API says it is missing (`penalChargeTextMissing`) or sends an empty sentence, nothing at all is drawn about charges (the screen does not even read that flag). In Hindi the lender's Hindi sentence is used only if it has one; otherwise the English sentence is shown with the existing "shown in English" note.
- **Nothing pre-selected.** The purpose, the rail and the amount mode start empty; no box is pre-ticked. The `purpose` navigation parameter (`/payments/pay?loanId=...&purpose=foreclosure`) only moves that option to the top of the list; it selects nothing.
- **Calm.** No urgency, countdown, offer, guarantee, compliance or safety claim in any string (a scan over the English catalogue). A quotation's validity is a date and time ("valid until ..."), never a timer.
- **The link is a bearer secret.** It is fetched only on the borrower's tap, inside that one handler; it is passed straight to `Linking.openURL` (from `react-native`: the system browser; no new package and no new permission) after a check that it is a plain `https` link; it is never put in React state, navigation parameters, logs, analytics, the clipboard, storage, the screen or an error message (a failure is a closed word). Tests scan the sources for these properties and check the handler.
- **Bank account.** The borrower types only the last four digits (digits only, `maxLength` 4). A change that would leave more than four digits is refused and the field keeps what it had. The app builds `XXXXXX` plus the digits itself, and the client validates the whole request against the contract before sending, so a full account number cannot be sent even by a coding mistake.

## How a payment goes

1. Pay reads the options and draws only what the API offers. The borrower chooses a purpose. If the API gives exactly one amount (the instalment or overdue figure, or the lender's quotation) the request carries that amount (and the quotation id for a foreclosure). If the lender accepts a part (`minMinor < maxMinor` on an instalment or overdue option) the borrower picks between the stated amount and "another amount within limits set by {lender}", neither pre-selected. For a part-prepayment the borrower types rupees; the exact integer parser (`parseRupees`, no floats) turns them into paise, and the screen compares the paise with the limits the API showed. The API checks every amount again.
2. A summary ("You are about to start a payment of ...") and the "Start this payment" button follow. One Idempotency-Key per attempt: the same content retried repeats the key, and any edit makes a new one. The payment is created as `created`; the screen goes to Payment status.
3. Payment status reads the payment and keeps reading it with back-off (2, 3, 5, 8, 13, 20, then 30 seconds; at most 20 reads in one run, about eight minutes) while the request is `created` or `pending`, the stage is still `started`, and there is something to wait for: the provider's order, or the result after the borrower opened the provider's page. It does not wait while an unexpired link is waiting for the borrower to tap. It stops when the screen is left (the loop is told, its pending wait is cleared and nothing more is reported), at the first failed read, and at the limit; "Check again" starts a new run. Coming back to the app from the background reads again.
4. When the API says `linkAvailable`, "Continue to the payment page" appears. On tap the link is fetched, checked and opened in the system browser. On return the payment is read again and the screen shows the stage the API gives, with a sentence that coming back does not show whether a payment was made.
5. "Cancel this payment" appears only when the API says `cancellable`.

## How a mandate goes

1. Mandate setup reads the options. The app chooses the mandate id (a version-4 UUID, from the platform's secure random source when the runtime has one) the first time the screen opens for a loan and keeps it in memory until the mandate is created or the id can no longer be used, because the one-time code is bound to it.
2. The borrower chooses a rail (nothing pre-selected; plain-language effect, the highest amount per debit from the API, and "Your bank may ask you to approve every debit with a prompt" when `needsAfaEachDebit`), types the start and end dates (DD/MM/YYYY, checked to be real dates) and the last four digits of the account. The maximum amount is not sent: the database then uses the lower of the rail limit and the lender's ceiling, the figure shown on the rail.
3. "Get and enter a one-time code" opens the existing `/stepup` screen with `action: mandate_creation` and `contextRef` = the mandate id (no OTP code was reimplemented). Back on the setup screen, "Send the auto-pay request" posts the mandate. A missing code (`stepup_required`) or a failed device check (`integrity_insufficient`) is shown in plain words.
4. The screen goes to Mandate detail, which reads the mandate with back-off while it is `draft` (the worker is asking the provider for the hand-off). At `registration_pending` ("Waiting for your bank") the button "Continue to authorise" appears; it fetches and opens the link exactly like the payment link. The status becomes "Active" only when the API says `active`.
5. "Request cancellation" asks for confirmation ("this is only a request") and posts the request; the screen then says "Cancellation requested. This is a request until the provider confirms it. The status above has not changed." and reads the mandate with back-off.

## Not built, deviations and gaps (honest list)

- **No render tests and no device run.** See above. The screen files are thin (state, a call, a draw); a layout, focus or touch-target error would not be caught by any test here.
- **No list of a borrower's payments exists in the API.** A payment is reachable from the Pay screen ("Payments in progress"), from the navigation parameter the loan screens pass, and right after it is created. A finished payment can be reopened only through a link that carries its id (the loan activity belongs to the loans builder).
- **No lender contact details in the payment or mandate routes.** "Contact {lender}" is said without a phone number or e-mail, because the API gives none (the spec's link to the lender's grievance contacts is not built here).
- **UPI app intents are not opened.** Only plain `https` links are opened, through `Linking.openURL`. A provider hand-off that is a `upi://` intent needs the `<queries>` entry listed in `docs/security/mobile-permissions.md` (row 17) and an owner decision; today such a link is refused by the check and the screen says the page could not be opened.
- **Hindi approval of the penal sentence.** The API returns `sentenceHi` next to the approved English sentence without a separate approval flag. The screen shows the Hindi sentence when it is present and non-empty, and the English one with a note otherwise. If the Hindi sentence is not covered by the same approval, this needs a decision.
- **The maximum amount of a mandate cannot be lowered by the borrower.** The request leaves it out (the database uses the lower of the rail limit and the lender's ceiling). The API would accept a lower figure; offering one is a product decision.
- **No cancel flag for a mandate.** The API has no "cancellable" field for mandates (it has one for payments, which is used). The request button is shown for the statuses where the provider could still act (requested, waiting for the bank, active, paused, being checked) and hidden for the finished ones and after a request; the API still refuses a finished mandate (`mandate_finished`, mapped to words). This is a table in `mandates-view.ts`, tested.
- **The step-up screen does not tell the caller whether the code was verified.** The setup screen therefore cannot show "verified"; it says what step 1 is, and if the code is missing the API's `stepup_required` is turned into "confirm with a code in step 1, then send the request again". The code is spent only when the mandate is created.
- **Dates are typed as DD/MM/YYYY.** A date picker needs a new dependency. The screen checks only that the date is real; the database decides whether the dates are acceptable (`dates_invalid`).
- **Pasting a long number into the account field.** The text field's `maxLength` of 4 is applied by the platform before the app sees the text, so on a platform that cuts a paste to its first four characters the field would show the first four digits of a long number. The server never receives a full number (the app sends `XXXXXX` plus the field, the client refuses anything else), the setup summary shows the account as `XXXXXX1234` for the borrower to check, and the screen says "Enter only the last 4 digits". The wrong-digits case is a residual risk that only a device test can size.
- **Random numbers.** Mandate ids and attempt keys use `crypto.getRandomValues` when the runtime has it and `Math.random` otherwise. Whether the React Native runtime in use has it was not checked on a device; the ids are identifiers, not secrets, but the API notes ask for unpredictable keys.
- **Return codes are not shown.** The provider's verbatim return code of a debit is provider text; only the class is shown when classified. If support needs the code, an owner decision is needed.
- **Regulatory figures.** None are shown: no deadline, no cooling-off period, no fee, no rate limit, no 24-hour or 48-hour notice rule. The notice lead time on the setup screen is the lender setting the API returns, labelled as a setting and "not a guarantee". Owner decision before anything regulatory is added.
- **No Settings entry.** As instructed, the mandate list (`/payments`) is reachable only by route; the loans builder links to it.
- **Screen capture** is blocked on the setup screen (where bank digits are typed) and not on the other screens.
- **Contrast and screen-reader order were not tested with a tool or a person.** The screens use the existing kit and theme tokens, every control has a label, state is never shown by colour alone (every banner has words) and touch targets are the kit's 48 dp.
- **Hindi is the builder's draft**, labelled as a draft in the app already; it has not been reviewed by a native speaker or by counsel.
- **Automatic checking is bounded.** After about eight minutes, or after a failed read, the screen stops reading and says so; the lender's posting can take much longer, so a payment at "Received by the payment provider" is read again only when the borrower asks or returns to the app.

## Evidence for the controls matrix (facts about behaviour, no compliance claim)

- Payments facilitated, not made: the screens never call a payment "paid" from a redirect or a client state, say "received" is not "posted by the lender", and show the lender's name as the payee and the lender's masked account as the destination.
- Amounts are the lender's: shown as reported, or typed within the lender's limits as exact paise; no screen totals, nets or rounds.
- Mandates: requested, waiting for the bank and active are shown only as the API's status says; cancellation is a request until the status changes; the bank prompt note appears when the rail flag says so; no promise that a debit will or will not happen.
- Data minimisation: no phone number, name, account number, payment link or secret appears in a URL, log, analytics event, navigation parameter, clipboard or storage by these screens; the app sends only the last four digits as a masked reference.
- The overdue penal-charge sentence is the lender's approved text, exactly as returned, or nothing.
