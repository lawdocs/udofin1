## Evidence that the claims were real

Run against a database built from 8463bb1 (no migration 922, no change to 022), 95 of the 151 assertions of 026 fail (the file runs to the end). Every U-claim has at least one failing assertion there, including: a gross-above-limit report and a 15-digit credit failing with a raw check error that echoes the row (U22), the division-by-zero probe of lender X's amounts through the old view (U19, U57), `****3333` suspending a lender that is correctly paid (A44), a PAN, an Aadhaar-shaped number and a phone number stored as bank references (U20), a credit confirming a 475000 payment through a 100000 batch (U13), one credit confirming two batches (U14), a receipt on another loan counted as posted (U16), a resolved receipt exception staying silent after the receipt was reversed (U18), and a 30-day waiting time accepted (U25).

## Mutation testing of the migration

Forty-nine mutations of the migration functions, each removing one guard (system guards, loan check, null destination, credit account, credit amount, items tie, parts tie, UTR uniqueness in view and run, future-period filter, security_invoker and security_barrier separately, duplicate captures, hash inputs, standing line from items, evidence flag, UTR shape, echo, amount limit, ceilings, audit values, recurrence, destination as whole string, owner of the account exception, one-sided exceptions, the double-settlement and double-posting exceptions, date window, a write to a payment configuration, the run-level safety nets, the legacy tie), were applied to a copy of the database and 026 was run: all 49 fail the file. The script is not committed (it is a scratch tool).

## Changes to 022

- Bank references in fixtures are `SAMP` plus twelve digits (the old `UTR-0001` shape is refused now).
- `pg_temp.exc('event_payload_conflict')` is 3 instead of 1: batches 6 and 8 of that fixture have a stated total and no items, so the platform is told that the provider's report does not add up (the old assertion counted only the re-reported batch).

## Owner decisions and flagged assumptions

1. **UTR shape (UNVERIFIED).** Derived from NEFT (16) and RTGS (22) conventions. A bare 12-digit IMPS or UPI reference cannot be told from an Aadhaar number and is refused; a lender whose provider settles by IMPS would need another rule. Confirm with the sponsor bank's and the provider's statements.
2. **Ceilings of 7 days and 168 hours (UNVERIFIED)** against the provider and sponsor-bank settlement terms.
3. **Standing line unit.** Gross of the batches (as the brief says, and what the item view used), with the net beside it in `settlement_evidence`.
4. **Unstated destination.** A warning for the platform, payments not stopped. The alternative (treat as off-account and suspend) would halt a lender for a missing optional field.
5. **U24** as above.
6. **Batches that net refunds or adjustments.** Items are payments only, so such a batch is "not tied" and is raised to the platform; modelling refund settlement is not built.

## needs_from_other_areas

- **Payments/exceptions area (table `reconciliation_exceptions`, closed class list):** distinct classes would make the queue clearer: `settlement_destination_unstated` (now `settlement_account_mismatch`, warning, platform), `lender_receipt_wrong_loan` (now `lender_receipt_no_intent`), and `settlement_over_settled` / `receipt_over_posted` (now `duplicate_payment`). Also `private.raise_exception_once` is no longer used by the run; if U18 is implemented there too, nothing in the run depends on it.
- **API builder, `services/api/test/integration/lender-payments.integration.test.ts`:** the fixture inserts bank references the table now refuses. Lines 466 to 493 use `` `UTR${tag}000N` `` and line 2090 uses `` `BNK${stamp}NNNN` ``, where the stamp is six hex characters (it can contain a run of letters). Use references of the shape above, for example `` `UTRX${tag.toUpperCase()}000000N` `` and `` `BANK${numericStamp}${NNNN}` ``. With only those two changes, in a scratch copy, all 71 tests of the file pass and so do the 33 of `periodic-jobs.integration.test.ts` (no file of mine was changed outside the area). The direct inserts into `settlement_batches` need no new column (a row without the flag is tied from its items).
- **API contract and routes:** `mapReport` (`routes.ts` around line 676) and `LpReconciliationRun` should carry `settlement_evidence` (`zero_is_evidence`, `settlement_report_exists`, `off_account_batches`, `off_account_net_minor`, `destination_unstated_batches`, `destination_unstated_minor`, `destination_unstated_net_minor`) and `settings.above_platform_default`; `PROVIDER_PAYMENT_COLUMNS` could carry `s.bank_confirmation_basis`. `LpReconciliationSettingsInput` accepts up to 100000 days and 1000000 hours; the database now accepts 1 to 7 and 1 to 168.
- **Portal-kit** (`reconciliation-views.tsx` around line 105): show the standing line as evidence only when `zeroIsEvidence` is true; say "not stated" for unstated destinations; label `bank_confirmed` as based on the lender's own statement.
- **Docs:** `docs/regulatory/controls-matrix.md` (MNY-02), `docs/operations/phase-08a-activation-gates.md` (around line 91) and `docs/specs/08a-notes/reconciliation.md` (around line 19) present "zero settled to non-lender" as the evidence; they should say that zero is evidence only when `zero_is_evidence` is true. `reconciliation.md` also still describes the one-per-class re-raise rule, the old waiting-time limits and the permissive bank reference.
- **New hints:** none.

## Risks seen and not fixed

- A reference shared by batches of two different configurations of one lender is not stopped by the index (it is per configuration, as asked); the run and the view stop it from confirming anything and raise it.
- The stage view uses today's date for "a batch that ends in the future", the run uses the run date. A back-dated run and the view can differ by a day.
- A provider that reports its own settlement id instead of the bank's UTR produces batches that can never be confirmed; they show as late settlements until the lender and provider agree on the reference.
- The unique indexes of 922 fail to build on a database that already holds duplicate batches or matches. None can exist in an environment that never ran the defective code with real data; Phase 08a is not deployed.
