# Reconciliation (migration 20261018000916)

Interface notes for the API, worker and screens. Spec: `docs/specs/08-servicing-payments-mandates-collections.md` section 10. Tests: `supabase/tests/022_p08a_reconciliation.test.sql` (115 assertions).

## What it does and does not do

- It compares four things, all lender-scoped: what the **provider** says it settled (`payments.settlement_batches` and `settlement_items`, from the provider port's settlement report or an imported file), what the **lender** says reached its account (`payments.bank_credits`: value date, amount and UTR only), what the **lender's own LMS** posted (`servicing.lms_receipts`) and Udofin's verified provider payments.
- **Matching is exact, never fuzzy:** provider payment reference and amount to the paisa; settlement UTR, net amount and the lender's **configured** settlement account; the lender's receipt must carry our provider payment reference or the intent id, the same amount, and must not have been reversed. There is no tolerance on amounts. The only tolerance is time: the waiting times in `payments.reconciliation_settings` (platform defaults of 3 days for the provider and the bank and 72 hours for the lender to post; **unverified defaults with no source**, to be replaced from the provider and lender agreements).
- **A missing input is "not reconcilable", never "reconciled".** A lender with no settlement report, no bank credits, or no LMS feed that declares the `receipts` capability gets that source listed in the run's report and no exception for what could not be checked.
- **It never writes a money row.** A run reads payments, intents, receipts, settlement items and bank credits and writes only its own run, matches and exceptions (tested by comparing a hash of those tables before and after). A resolved exception is an annotation: the next run does not open it again; reopening is a person's decision.
- **Nothing sets a settlement stage.** `payments.payment_stages` derives, per successful provider payment, `provider_captured`, `provider_settled`, `bank_confirmed` and `lender_posted` from the tables. No function accepts a stage; the test fails if one is ever added. `bank_confirmed` additionally needs the reported destination to be the lender's verified account and the credit to be in the configured settlement account.
- **Not built:** parsing of a bank statement file (CSV or MT940) into the three allowed fields (the API stream does that and calls `import_bank_credits`), a provider settlement-report fetch (the worker calls `PaymentProviderPort.fetchSettlements` and `record_settlement_report`), per-provider cut-off times, refund and chargeback settlement reconciliation, and the daily job itself.

## Functions

- `payments.record_settlement_report(config, report_date, batches jsonb)` (system): validates the whole report first (all or nothing; money as digit strings of paise; dates real; references plain), stores batches and items as reported (never recomputed; `parts_mismatch` flags a report that does not add up). A batch already stored with the same content is a duplicate; with different content it opens an `event_payload_conflict` exception for the platform and changes nothing. **A batch whose reported destination (last digits) is not the lender's verified settlement account is stored with `destination_ok = false`, opens a CRITICAL platform exception (`settlement_account_mismatch`) and suspends that payment configuration at once.**
- `payments.import_bank_credits(lender, account, rows jsonb)` (`payment.reconcile`, aal2): rows are `{valueDate, amountMinor, utr}` and nothing else. Any other field (a narration may carry a name) refuses the whole upload (`22023|unexpected_field`); so does a bad row (`row_invalid`), a value date in the future, or a bank reference that differs from one already recorded or repeats with different content (`utr_conflict`). The account must be one of the lender's own (`P0002`). An identical credit again is a duplicate. The audit event carries counts only.
- `payments.set_reconciliation_settings(lender, settlement_lag_days, receipt_lag_hours)` (`payment.configure`, aal2).
- `payments.run_reconciliation(lender, date)` (system, a daily job after the provider cut-off): idempotent. The SHA-256 of the canonical listing of every input decides: the same inputs return the same run (`unchanged: true`), changed inputs make the next run number for that date. Exceptions raised once per class and subject: `amount_mismatch`, `provider_success_no_settlement`, `settlement_no_intent`, `late_settlement`, `settlement_account_mismatch`, `lender_receipt_missing`, `lender_receipt_no_intent`. The report carries no clock, the not-reconcilable list and the standing line `settled_to_non_lender` (items and paise; **zero is the evidence for the roadmap gate "Udofin holds no borrower funds"**, and a non-zero value is a critical finding).
- `payments.reconciliation_summary(lender, date)` (invoker, row level security): the newest run for a date. `payments.payment_stages` (view): rows of the caller's lenders only (`payment.read`).

## Missing-texts register and open points (owner decision 6)

1. The provider's and the sponsor bank's settlement documentation: cut-off times, settlement lag, how refunds and chargebacks appear in a settlement. None is assumed beyond the labelled defaults above.
2. The lender's agreement on carrying Udofin's payment reference or intent id in the receipt it posts (without it every payment is `lender_receipt_missing`; the dependency is recorded as D-69).
3. Whether the lender's bank statement can be supplied in a machine-readable form at all.
