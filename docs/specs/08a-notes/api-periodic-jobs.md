# Phase 08a, wave 5: scheduled jobs and servicing event handlers (worker)

Builder w2. Files: `services/api/src/workers/periodic-jobs.ts` (the scheduler and the jobs), `services/api/src/workers/servicing-handlers.ts` (outbox handlers), `services/api/src/workers/reminder-channels.ts` (the notification channels), `services/api/src/system/jobs.ts` (SQL wrappers for the system role). Tests: `services/api/test/periodic-jobs.test.ts` (60 unit tests, fake store and scheduler) and `services/api/test/integration/periodic-jobs.integration.test.ts` (33 tests against a real migrated database with the labelled mock providers and the mock notifier).

Nothing here decides a business rule. The database functions plan, claim, apply and reconcile; this code schedules them, calls the provider ports in between (outside any database transaction), passes ids and the provider's answers to the functions, and logs by class only. No compliance claim is made anywhere in this note: the reminder window, the daily cap, the pre-debit lead time and the settlement waiting times are the database's labelled defaults (`interpretation` or `unverified`, see `reminders.md`, `mandates.md`, `reconciliation.md`).

## How the jobs run

`startPeriodicJobs(deps)` (signature unchanged, called by `workers/main.ts`) builds the jobs with `createPeriodicJobs(deps, options)` and starts them. Every job:

- is idempotent (the database functions are);
- runs one at a time per process: a tick that finds its job still running is skipped and logged (`periodic job is still running`);
- isolates its steps: an error ends that step only and is logged as `{ job, step, errorClass, sqlstate? }`. `errorClass` is the error's class name and `sqlstate` is the five-character code of a database error. A message, a row value, an id of a person or a reference is never logged. Log lines carry counts and the job name;
- stops taking new items after `stop()` (the item in hand finishes);
- reaches a provider only through the resolver. A configuration the resolver cannot serve (`provider_not_configured`, `mock_not_allowed_here`, `secret_missing`) is skipped and only that reason class is logged. A lender whose switch is off is excluded in SQL (`private.feature_enabled(...)` in the wrapper queries), not in TypeScript.

The first run of each job comes 5 seconds after start-up plus one second per job, so they do not all start at once. All intervals and limits are named, exported constants at the top of `periodic-jobs.ts`.

| Job (`JobName`)    | Interval   | Steps, in order (SQL function; provider call)                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `reminders`        | 1 minute   | `servicing.plan_reminders()`; `servicing.claim_due_reminders(100)` (repeated while a full batch comes back, at most 10 times); for each claimed reminder one send on its channel; `servicing.record_reminder_attempt(reminder, state, 'send', providerRef, errorClass)`                                                                                                                                                                          |
| `payments_upkeep`  | 5 minutes  | candidates (SQL select, system role); `PaymentProviderPort.getOrderStatus` per candidate; `payments.raise_exception` for a held intent; `payments.expire_stale_intents(grace)` (see below)                                                                                                                                                                                                                                                       |
| `servicing_upkeep` | 5 minutes  | `servicing.complete_disbursements(null)`; `servicing.expire_document_requests(cutoff)` only when an age is configured (it is not, see gaps)                                                                                                                                                                                                                                                                                                      |
| `mandates`         | 5 minutes  | `payments.mandates_needing_lookup()` (+ switch filter) then `MandateProviderPort.getMandateStatus` then `payments.apply_mandate_lookup`; active mandates then `listDebitStatus` then `payments.apply_debit_lookup` (one call per report); `payments.sweep_mandates()`; `payments.request_cancel_for_closed_loans()`; `payments.plan_mandate_debits()`; `payments.claim_pre_debit_notices(100)` then send then `payments.record_pre_debit_notice` |
| `handoff_links`    | 5 minutes  | `payments.purge_handoff_links()`                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `payment_configs`  | 1 hour     | `payments.revalidate_payment_configs()` (logs counts: checked, not ok, suspended)                                                                                                                                                                                                                                                                                                                                                                |
| `reconciliation`   | 15 minutes | looks at the clock; does its work from 20:00 IST (see below). `payments.record_settlement_report(config, date, batches)` and `payments.run_reconciliation(lender, date)`; `PaymentProviderPort.fetchSettlements`                                                                                                                                                                                                                                 |

### Reminders and notices: the channels

- `in_app`: the database is the inbox. The content is frozen in the database when the reminder is claimed and read by the borrower through `servicing.my_reminders()`. "Sending" is recording acceptance; nothing leaves the system.
- `push`: a `NotificationChannelPort<'push'>`. In `local` and `test` it is the labelled `mock_notifier`; in `staging` and `production` it is the unconfigured placeholder, which answers `not_configured`. A mock port passed in for another environment is refused at start-up (`assertPushChannelAllowed`). The payload is exactly the opaque id (the reminder id, or the notice id) and a fixed title key (`reminder`, or `payment_update` for a pre-debit notice). The recipient reference is the borrower id. No text, amount, lender name or phone number.
- `sms`: never sent and no channel is called. If the database ever hands one over, it is recorded as `not_configured`.
- Results map to the delivery log as follows: `accepted` is recorded as `accepted` (never as delivered; there is no delivery-report intake because there is no push provider); `not_configured` as `not_configured` (the database suppresses the reminder with `channel_not_configured`); a definite refusal as `failed` with class `invalid_target`; an unknown outcome as `failed` with class `provider_timeout` (timeout) or `provider_error` (anything else), and the database retries after 15 minutes times the attempt, at most 3 attempts. The idempotency key of a push is the reminder id, so a retry is the same message to the channel. A provider reference that is not a plain id (it contains `//`) is not stored.
- A pre-debit notice goes to `in_app` and `push` and gets one state: `accepted` if any channel took it (so with the in-app inbox it is always accepted unless the id is malformed), `not_configured` only if no channel could carry it (the database marks it late and tells the lender), otherwise `failed` (released for a retry). `delivered` is never recorded.

### Payments upkeep: the order lookup before an intent is expired

Candidates are selected with the system role: status `created` or `pending`, link expired more than the grace (15 minutes) ago, no provider payment on file, and the lender's `payments` switch on (oldest first, at most 200 a run). For each, `getOrderStatus` is asked with `operationKey` = the intent id and the stored order reference:

| Answer                                                                                                                                                        | Verdict                                  | What happens                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ok`, status `created`, `failed`, `cancelled` or `expired`                                                                                                    | safe                                     | may be expired                                                                                                                                       |
| `ok`, status `captured`, `paid` or `succeeded`                                                                                                                | evidence (money seen, no verified event) | held; exception opened at once                                                                                                                       |
| `ok`, any other status (`pending`, `authorized`, `unmapped`, ...)                                                                                             | evidence (not final)                     | held; exception opened at once                                                                                                                       |
| `not_found`, intent `created` with no order reference                                                                                                         | safe (the provider never saw it)         | may be expired                                                                                                                                       |
| `not_found`, intent has an order reference                                                                                                                    | evidence (contradicts what we hold)      | held; exception opened at once                                                                                                                       |
| `unknown` (timeout, network, provider error), `rejected`, `unsupported`, not configured, resolver cannot serve, no status-lookup capability, no configuration | undetermined                             | held; an exception only when the hold ends (below). After 3 failed answers from one provider in a run, the rest of its lookups wait for the next run |

The exception is `webhook_gap` (the spec's "intent pending beyond threshold with no event after a status lookup"; the closed list in the migration has no class that fits better), severity `warning`, owner `platform`, subject `{intent_id}`. Both severity and owner are my choice and need the owner's confirmation. The lookup is evidence only: nothing here moves money, no intent status is written by the worker, no function applies a lookup, and a success is never marked.

**The database gap this works around.** `payments.expire_stale_intents(p_grace)` takes no list of intents to leave alone; it expires every intent past the grace with no provider payment on file. So "do not expire that intent" cannot be said with the function as it is. The wrapper (`expireStaleIntents` in `system/jobs.ts`) says it through the grace argument: it computes, in one SQL statement, `grace = now - boundary` where `boundary` is the oldest of (a) the cutoff of the candidate list, (b) the link expiry of the last candidate looked at when the list was cut at 200, and (c) the link expiry of the oldest held intent, each less a second of margin. The function then expires only intents whose link expired before the boundary. Consequences, all deliberate and tested:

- an intent younger than the oldest held one waits (it is looked at again next run) even if its own lookup said it was safe;
- **a hold never lasts more than 24 hours after the link expired** (`INTENT_HOLD_LIMIT_SECONDS`). After that the intent is no longer held, an exception is opened if there is none, and the database rule expires it. If the webhook arrives later it is recorded by the database as `payment_on_closed_intent` for a person. This bounds the delay one stuck intent can cause for every other intent in the system. Whether 24 hours is right is the owner's call;
- if the boundary needs a grace above the 7 days the function accepts, nothing is expired that run (logged);
- the function does not look at switches, so an intent of a lender whose `payments` switch is off is not a candidate (no provider call, no exception) but is still expired by the function once it is older than the boundary. The integration test records this.

A better fix is in the database: `expire_stale_intents(p_grace, p_hold uuid[] default '{}')`, or a table in which a lookup result is recorded as evidence that suspends expiry. I did not add either (no migration edits, and the brief says no function that applies a lookup).

### Mandates

- Lookups: `payments.mandates_needing_lookup()` does not look at the lender's `mandates` switch (it would return a registration of a lender whose switch is off). The wrapper joins it with `private.feature_enabled(lender, 'mandates')` so no provider is called for that lender. `getMandateStatus(operationKey = mandate id, providerMandateRef)`; an `ok` answer goes to `apply_mandate_lookup(mandate, status, providerRef, observedAt)`. `unknown`, `not_found`, `rejected`, `unsupported` and `not_configured` apply nothing (looked up again next run; `sweep_mandates` raises `mandate_unresolved` when an outcome stays unresolved). A `provider_ref_mismatch` (55000) from the function is only logged.
- Debit reports: active mandates with a provider reference, lender's `mandates` switch on. `listDebitStatus` over `today - 7 days` to `today + 3 days` (IST; `DEBIT_LOOKBACK_DAYS`, `DEBIT_LOOKAHEAD_DAYS`, my choice, not a rule). One `apply_debit_lookup` per report; a report whose `providerMandateRef` is not this mandate's is skipped; the return code is passed only with status `returned` (the function stores one only then). Which planned debit a report attaches to is the database's rule (same amount, date within 3 days, and exactly one candidate; otherwise unplanned and flagged `mandate_debit_unresolved`).
- A returned debit creates no charge and touches no payment (tested: the counts of provider payments, adjustments and intents are unchanged).

### Reconciliation

The job runs every 15 minutes but acts only from 20:00 IST (`RECONCILIATION_FROM_IST_MINUTE`, judged in Indian time from the injected clock). It considers two report dates: the previous and the current IST date. A date is done when the database holds a run for it (`payments.reconciliation_runs`, read through `reconciledDates`); nothing is remembered in memory, so a restart does not repeat the work (tested with a new process). For each lender with an **active** configuration and the `payments` switch on:

1. resolve the payment port (not ok: skip the lender, reason class logged);
2. if the provider declares `settlementReports`: `fetchSettlements(date)`; anything but `ok` leaves the date undone (no run is made on a half-known day; the next check retries), as does a report dated differently from the one asked for; an `ok` report is mapped to the JSON the function reads (money as digit strings of paise, nothing recomputed, all keys always present) and recorded with `record_settlement_report`;
3. `run_reconciliation(lender, date)`.

A provider that cannot report settlements is not asked; the run still happens and the database lists `settlement_reports` as not reconcilable (the brief reads two ways here; I chose to still run, because the run is idempotent and reports what could not be checked). A lender whose switch is off or whose configuration is not active gets nothing. Because a run covers every input up to its date, an input that arrives later (a bank credit, a late settlement) is picked up by the next day's run; a date that already has a run is not fetched again.

## Servicing handlers (`servicing-handlers.ts`)

Every event the database enqueues in `servicing` has a handler. Payloads are validated with strict zod schemas (an unknown field is refused as `invalid_payload`, permanent). Delivery is at least once; each handler is safe to repeat. A database error is raised so the worker retries.

| Event type                       | Payload (strict)                                 | What it does (SQL)                                                                                                                                                                                                                                               |
| -------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `servicing.import.committed`     | `{ batch_id, lender_org_id }`                    | `servicing.complete_disbursements(lender)`: the application of a loan the lender's report created moves from `disbursement_pending` to `disbursed` (the last step belongs to the system). Logs the count. See gaps                                               |
| `servicing.sync_conflict.opened` | `{ conflict_id, lender_org_id }`                 | Acknowledged; nothing to send or decide (the conflict is in the lender's queue). Logs nothing personal                                                                                                                                                           |
| `servicing.loan_closed`          | `{ closure_id, loan_account_id, lender_org_id }` | In one transaction: `servicing.suppress_reminders_for_loan(loan, 'loan_closed')` then `payments.request_cancel_for_closed_loans()` (a cancellation REQUEST, queued as `mandate.cancel` for the provider; the mandate stays as it is until the provider confirms) |

The brief described the closure payload as `{loan_account_id}`; the database writes three ids (`migration 20261018000912`), so the schema has all three.

## Error handling summary

There are no HTTP routes, so no problem codes. Job errors are logged by class (`errorClass`, `sqlstate`) and the step ends. Handler errors: invalid payload is permanent (the worker's `invalid_payload`); a database error is raised and the worker retries with its backoff.

## Not built, deviations, open gaps

1. **`payments.expire_stale_intents` cannot exclude an intent** (database gap, evidence above). Worked around through the grace argument, with a 24-hour hold limit. Recommended: a database change (an exclusion list or a recorded lookup).
2. **`payments.mandates_needing_lookup` ignores the lender's `mandates` switch** (and so do `apply_mandate_lookup`, `sweep_mandates` and `expire_stale_intents`). The wrapper filters in SQL for the two lists the worker builds (lookups, active mandates); the functions themselves do not. `payments.claim_pre_debit_notices` and `payments.plan_mandate_debits` do check the switch.
3. **Document request expiry is not scheduled.** `servicing.expire_document_requests(cutoff)` takes an age from the caller and none is approved anywhere (the statement and NOC SLA days are service targets, not an expiry). The step exists (`documentRequestExpiryDays` option) and is off; start-up logs that it is not scheduled. Needs an owner decision on the age and a configuration key.
4. `complete_disbursements` runs in the import handler, as the database note requires, and also every 5 minutes (`servicing_upkeep`) as a safety net in case an event is lost. The brief only asked for the handler to acknowledge and log counts.
5. The `webhook_gap` class, severity `warning` and owner `platform` are my choice from a closed list that has no exact class.
6. The 24-hour hold limit, the 200 lookups a run, the 3 failures before a provider is skipped, the debit window (7 days back, 3 ahead) and the batch sizes (100, up to 10 batches) are my operational choices, named constants, with no source.
7. **No real push provider exists.** In `staging` and `production` every push reminder is suppressed as `channel_not_configured`; only the in-app copy is sent. Delivery reports (`record_reminder_attempt` with source `delivery_report`) are not consumed because nothing produces them. The in-app "acceptance" proves the message is in the inbox, not that the borrower saw it (`servicing.mark_reminder_read` does that).
8. The mock notifier accepts push in `local` (a labelled mock: it delivers nothing).
9. Provider calls are bounded only if the resolver wraps its ports with the timeout wrappers (`withPaymentTimeout`, `withMandateTimeout`); this code does not add a timeout of its own. A port that never answers would hold its job's in-flight guard (the other jobs continue).
10. Reconciliation of a date that already has a run is not repeated the same day or the next; late settlement data is picked up by the next day's run (runs are cumulative). Money amounts a provider reports as negative are refused by the database (the whole report), logged by class, and the date stays undone.
11. `ServicingHandlerDeps.log` is optional and `workers/main.ts` does not pass it, so the handlers run silently in production wiring (the database audit has the same facts). Requested in the lead's file list.
12. The integration test needs a freshly migrated database (it adds its own lenders and leaves them). It builds hard-to-reach states as the owner with `session_replication_role = replica` and commits them before the jobs run: loan accounts with schedules and reports, intents whose link expired hours ago, mandates stuck in registration, and the payments recorded for reconciliation. The reminder window is judged at 10:00 IST through the system login's session settings (`udofin.test_clock`, `udofin.allow_mock_providers`), the seam the pgTAP suite uses.
13. Guards checked by removing them on purpose (each made at least one test fail, then restored): the in-flight guard; the hold boundary of the expiry (3 integration tests and at least 8 unit tests fail); the `payments` switch filter of the expiry candidates and of the reconciliation lender list; the `mandates` switch filter of the lookup list and of the active-mandate list (a spy provider is registered for the lender whose switches are off, so a call would show); the 20:00 IST check; the "database already has a run" check; the settlement capability check; the sms guard; the hold limit; the foreign-mandate report guard; the return-code guard.
14. Compliance mapping is not done here (`docs/regulatory/controls-matrix.md` is the lead's file). Rows this work touches: reminder window and daily cap (`interpretation`), pre-debit notice (`unverified`), reconciliation evidence line "settled to non-lender accounts". None is claimed as compliant.
