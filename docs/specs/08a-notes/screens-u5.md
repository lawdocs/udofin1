# Phase 08a notes: lender portal screens for reminders and payment setup (builder u5)

Code: `packages/portal-kit/src/reminders/**` and `packages/portal-kit/src/setup/**` (views, loaders, allow-listed operations, wording, the client forms), the pages and server actions in `apps/lender-portal/app/reminders/**` and `apps/lender-portal/app/payment-setup/**`, tests in `packages/portal-kit/test/reminders.test.tsx` and `packages/portal-kit/test/setup.test.tsx`. The API these call is described in `api-lender-reminders.md` and `api-lender-accounts.md`; the contracts are `packages/contracts/src/http/lender-reminders.ts` (exports prefixed `Lr`) and `lender-accounts.ts`. Spec: `docs/specs/08-servicing-payments-mandates-collections.md` sections 7.1, 11, 16, 17 and 20. These screens are for lender staff only; nothing here is shown to a borrower.

## What the screens do and do not do

- **Show, never work out.** Every figure is the one the API returned: a flat charge as rupees from integer paise (`formatRupees`, Indian grouping), a percentage as the lender's stored basis points written with exact integer arithmetic (`250` becomes "2.50 per cent"), nothing applied to any amount. No page computes, suggests, generates, translates or rounds a charge, a wording or a sentence. The lender's words (wording, penal-charge sentence, reason, hold note) are shown as written, escaped by React, with line breaks kept, and are sent to the API byte for byte (no trimming, no placeholders added).
- **Whose words, and who approved them.** Every version shows who drafted, approved and retired it and when ("you" for the signed-in person, otherwise the identifier the API gives, because the API returns user ids and no names). The approve form is drawn only for a draft made by ANOTHER person, for a person who holds `reminder.template.approve` in that lender, and it needs a box ticked ("I have read this ... in full"). The drafter sees "You drafted this version, so another person must approve it." The same holds for a payment configuration: the decide form is hidden from the person who drafted it and from the person who submitted it. Hiding a form is a convenience; the API and the database refuse self-approval again (tested at those layers).
- **SMS is never offered and never presented as working.** Channels read "SMS: not available, never sent" wherever they appear (policy, log, summary, attempts). The policy draft form offers in-app and push only and says SMS is not available. The operation refuses `sms` in a draft without a call.
- **The missing penal-charge text notice.** When the API says no approved penal-charge text exists (`overdueReminders.penalTextApproved` false, or `overdueRemindersWithheld` true), the reminder log, policy and penal-charge pages show a prominent section: "Overdue reminders are not sent until an approved penal-charge text exists", with a link. When the flag cannot be loaded the page says so and claims neither state. When a text is approved the page says so and adds that overdue reminders also need approved overdue wording and an approved policy (the API's note says the flag does not look at those).
- **Test configurations are never live.** A configuration in mock or sandbox mode is labelled "Test only" in its mode, in its status ("Approved (test only)") and in a banner on its page; a mode the screen does not know is treated as a test mode. "Approved" never reads "live", and the list page says that approved does not by itself mean payments are switched on.
- **Account numbers and secrets cannot be typed.** A settlement account is requested by a name, the bank and a MASKED reference. The field has the contract's shape (`[X*]{2,}[0-9]{2,4}`) as a browser-side check, the operation checks it again with the contract schema, and no form or operation has a field for a full number or an IFSC. A secret is given as its NAME (capital letters, digits, underscores, 3 to 64 characters, starting with a letter); the form and the operation refuse anything that looks like a value (lower case, symbols, a long run of digits, a long hexadecimal run, a long unbroken run, or the same name twice). The API applies its own check and stays the authority.
- **The callback token is shown once.** After a draft, the callback path (which ends in the token) is drawn by the draft form from its own memory, with the notice "This is shown only once", a copy button, and a button that removes it from the page. It is not put in an address, a cookie, storage, a hidden field, an attribute or a log line by the portal (tested by scanning each). It is gone when the person removes it, tries again or leaves the page. The page cannot show it again.
- **No server text on a screen.** Closed vocabularies, reason codes and stable error codes go through wording tables. A value or code the table does not know is shown as a generic sentence, never as it came (tested with drifted values, a fake SQLSTATE and the names `toString`, `constructor`, `__proto__`). The free-text `statusReason` of a payment configuration is NOT shown, because the database fills it with a mix of the person's note and sentences the system wrote; the reason CODES are shown in words instead.
- **Write forms follow the permission set.** The pages turn `/v1/me` memberships into one grant per lender; a form is drawn only for a lender in which the person holds the permission. Platform memberships hold no lender grant, so they get no write form.
- **One allow-listed operation per form.** `REMINDERS_OPERATIONS` (11 operations) and `SETUP_OPERATIONS` (7) are the only ways a form can write. Each maps a named operation to exactly one API route, checks its fields again, and sends an `Idempotency-Key` (minted when the page renders, or fresh per submission for the forms that keep what was typed). An unknown operation, a key of the wrong shape, or the configuration draft through the general entry point is refused without any call.
- **A refused form keeps what the person typed.** The drafts (policy, wording, penal-charge text, hold, settlement account, merchant claim, configuration) are client forms that hand a refusal back as a stable code and keep every typed value, so a refused paragraph of wording is not lost. Two things are deliberately not kept: the two penal-charge statements are not ticked again after a refusal (they are the lender's own act, never ticked for them), and an earlier callback path is cleared as soon as a new attempt starts.

## Not built, deviations and gaps (honest list)

- **Regulatory figures and deadlines are not displayed (owner decision).** No page states the 08:00 to 19:00 India-time window, the cap on messages per loan per day, the quiet period after a payment, or any limit on a penal charge, because `reminders.md` marks the window an interpretation of a regulation that is not verified and the cap and quiet period as unverified platform defaults. The policy form shows only what the lender typed and says the platform "can only narrow the window" and "can only lower the cap" (the database's behaviour, no number). A value the database refuses gets a general sentence. Owner decision: whether lenders should be shown the platform's current window and cap, and on what authority. The missing-texts register in `reminders.md` stays open; the screens say nothing about it.
- **No suggested, generated, translated or calculated wording or charge.** There is no preview of a rendered message (the API does not store one), no placeholder suggestion, no Hindi help and no levy notice (the API notes say it is not built).
- **Reasons a feature switch is off are only what the API states.** `GET /v1/lender/features` returns whether the switch is on, whether it can ever be enabled, and the dates. The prerequisite reasons (`prerequisites_unmet`, the catalogue's locked reason) exist only in platform routes, so the page says "has not been switched on", "was switched off on a date" or "cannot be switched on at present" and lists no prerequisite. On means the stored switch, not that the feature works for borrowers (the API notes say the effective state also needs an active organisation and an activated gate). A lender-readable reasons route would be needed to list prerequisites.
- **Suspend is not offered.** The brief lists it; the API makes it a platform act (the lender path answers 403). The page says only the platform team can suspend, and that a suspended configuration can be submitted again.
- **SMS cannot be chosen in the policy draft form.** It is shown plainly ("SMS: not available, never sent") everywhere a channel appears, and the operation refuses it. A policy made elsewhere that names SMS displays correctly.
- **Callback host.** The path (which ends in the token) is shown, not a full address: no contract carries the address of the callback service, so the page says it is not shown.
- **"Shown only once" describes this screen.** The API note (section 3) says the generic idempotency layer keeps the draft's answer, including the token, for 24 hours and would replay it for the same request key; the portal mints a new key for every submission, so it never asks for a replay. The API stream owns the fix.
- **Free-text `statusReason` of a payment configuration is not shown**, because it mixes a person's note with sentences the system wrote. The reason codes are shown in words. The history route does not return notes.
- **Reminder attempts page shows attempts only.** There is no get-one-reminder route, so the page cannot show the reminder's kind or schedule; the log links to it by reminder. No rendered wording exists to show (API decision).
- **Holds need a typed loan ID.** There is no loan picker and I did not edit the Loans pages (builder u3's) to add a link. The hint says where the ID is. The `lenderId` assertion the API allows is not sent.
- **Reminder summary has no date filter.** The default period is stated as the contract states it (the last 30 days). The generic client's path allow-list also forbids `+` in a query, so a `since` instant would need `%2B`.
- **Navigation.** The page frame (not mine) links Reminders only to people holding `reminder.policy.manage` or `reminder.template.approve`, and Payment setup only to people holding `payment.configure` or `payment.config.approve`. A person with only `loan.read` or `payment.read` can open the pages by address but sees no link. Reminder log and holds need `loan.read`; the registry status needs `payment.read` (a person who only configures sees "You cannot view the registry status").
- **People are shown by identifier.** The API returns user ids and no names, so "another person (ID ...)" is the most the screens can say about who drafted, approved, placed or released.
- **An addition to the brief.** The approver ticks "I have read this ... in full" before an approve form can be sent (never pre-ticked, checked in the operation). Rejecting a payment configuration needs a note of at least ten characters, as the API says.
- **Rail limits.** The form offers eight rows of rail, limit name, kind of value (text, yes or no, amount in rupees stored in paise, whole number) and value, plus a source note that is required once any limit is given. A stored whole number is shown as stored because the screen cannot tell an amount from a count (a note says amounts are paise).
- **Pages are not unit tested.** The Next.js pages and the three server-action files are thin (session, client, load, draw); their logic lives in portal-kit and is tested there. `apps/lender-portal` has no test runner, `tests/e2e` was not extended (its fake API would need the new routes), and the pages were not exercised against a running server here, so the server-to-client hand-off of the server actions is verified by the production build and by reading, not by a browser run.
- **Hindi.** The lender portal is English only, as in earlier phases.
- **Colour.** No new colours or styles were added; the pages use the existing portal classes and put meaning in words, never in colour alone. A contrast check against the theme tokens was not run.
- **Shared code reused, not copied.** The folders import the read-only formatting and layout helpers of `packages/portal-kit/src/servicing` (builder u3's: rupees, India time, paging, section, load-failure). A later change to those helpers reaches these screens.

## Evidence for the controls matrix (facts about behaviour, no compliance claim)

- Reminder workflow (two-person approval): the screens draw the approve form only for a different person than the drafter, ask the approver to confirm they read the text, and show the drafter and approver of every version. This shows the screen follows the API; the segregation itself is enforced by the database (the API notes describe its tests).
- Penal-charge text: the lender's figure, its two statements and its sentence are carried through unchanged and shown as stated; the screens compute and apply nothing. The sentence is the lender's own statement; nothing on the page says it meets any rule.
- Payment configuration (maker-checker, PAY-05 row): drafting, submission and decision are separate screens for separate people; secrets are names; a settlement account is requested by masked reference only; mock and sandbox are labelled test only. The registry status page shows what the account registry reports (masked reference, status, effective dates, whether usable) and claims nothing beyond it.
