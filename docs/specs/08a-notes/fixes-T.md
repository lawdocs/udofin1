## Decisions and reasoning worth a second look

### A30: why the rate limit is split this way

The old per-token limit ran before any authentication and counted every request whose token hash matched, so about two junk requests a second to a known URL held the real provider at 429. The limit exists to bound work and stored receipts per token. The new rule keeps that bound without giving unauthenticated callers a lever on the genuine sender:

1. Per address, before anything is known (unchanged, 300 a minute).
2. A delivery that fails verification spends a failure budget of 30 a minute per (token hash, address). The budget of one address never counts against another's. Beyond it the answer is 429 and nothing is stored.
3. A delivery that verifies spends 600 a minute per token hash. No unauthenticated request can reach it, so no amount of junk can lock the provider out. Only a holder of the signing secret can spend it.

The no-enumeration property is kept: the failure budget is keyed by the hash of whatever token was sent (and is applied to malformed tokens too), so a valid and an invalid token are counted and answered alike (401 until the budget is spent, then 429). A valid signature is the only way to get another answer, and a forger cannot make one.

What this does not bound: many addresses, each under 300 a minute, can still cause many configuration lookups and, up to the failure budget each, many stored unverified receipts. That was already so for unknown tokens (each had its own bucket). A shared lookup cache or a per-token ceiling on stored unverified receipts would need a database or design decision.

### A24: how long a cancellation is retried

The outbox default is eight attempts with a backoff of 5 s, 10 s, 20 s ... up to 5 minutes, about ten minutes in all. After the last attempt the event is dead with the code `mandate_cancel_not_delivered` and the handler writes an error line saying an operator must cancel the mandate at the provider. That is loud but it is not a re-send: a longer outage ends in a dead event. The database side (a sweep that re-queues cancellations that were never sent, and `record_mandate_handoff` refusing to register a mandate whose cancellation was requested) is the SQL builder's. The TypeScript half assumes no database change and is correct without it.

### A19: cross-tenant merchant id squatting (described only)

`payments.claim_merchant` lets any holder of `payment.configure`, including a lender organisation still in `onboarding`, claim a provider merchant id before its real owner; the real owner then gets 409 `merchant_already_claimed`, the platform can only revoke the squatter's claim, and a revoked id can never be claimed again by anyone. The 409 also tells a lender whether an id is registered by another tenant or is Udofin's fee merchant. A fix needs a database decision (verification before the claim holds the id, a release of a wrongly claimed id by a recorded two-person action, a per-lender cap), not a route change. Not done here.

### Owner decisions

1. **A19, a repeat claim of a revoked merchant claim.** The answer is now 201 with `status: "revoked"` (the true state). The alternative is a refusal, 409 `merchant_not_active`, which a client that reads only the HTTP status would notice at once. The brief asked for the real status; the refusal needs the owner's word because the setup screens show a success banner on any 2xx.
2. **A54, what a deployed environment does now.** With push unconfigured (staging, production) every pre-debit notice is recorded as not carried: it stays late and the lender sees `mandate_notice_late` for every debit. That is the honest state, and it means mandates cannot be run honestly in production until a real channel that reaches the borrower exists (and a channel is added to `NOTICE_CHANNELS_THAT_REACH_THE_BORROWER` with its provider). The borrower wording and the controls-matrix rows MNY-03/MNY-07 are not in this builder's files.
3. **A15, the caller must be able to read the settlement account.** The answer reports the stored status, which needs `payment.read`. The seeded role `payments_admin` has both permissions. A user with `payment.configure` alone now gets 403 (and nothing is created) instead of an answer that could not be true for a repeat request.
4. **A5, exact file rows for stored findings.** Done as a label (`rowNumbering`), not as a mapping, because the database stores the position of the record it received and the record format has no field for a file row. Giving the lender the exact file row for a stored finding needs the database half below.

## Risks noticed and not fixed

- The ports the periodic jobs get from the provider resolver are not wrapped with the payment or mandate timeout (the outbox handlers wrap theirs). A provider call that never returns would hold the polling step, and so the job, until the process restarts. The new polling budget is checked between calls, not during one.
- The rotation memory of the polling steps (`lastStatusLookup`, `lastDebitLookup`) lives in the process. A restart starts the rotation again from the beginning, which only changes the order.
- A cancellation that dies after its last attempt is a dead outbox event, visible in the log and in `ops.outbox_events`, but there is no platform exception for it. The lender-owned `mandate_cancel_unconfirmed` warning still appears after 24 hours.
