## 1. Routes

All routes are `auth: 'staff'` (so the shared layer already demands aal2 for every staff token: 401 `mfa_required` otherwise), rate limited (reads 120 per minute, writes 40, the registration 12), and every POST is idempotent (`Idempotency-Key` header; the key is also passed to the database function where it takes one). Platform reads add an explicit permission check (403 `forbidden`), because row-level security alone would answer an empty list. Lender reads add an explicit check that the caller holds a payment permission in the asked lender. Writes leave the decision to the SQL function. Unknown or foreign ids answer 404 `not_found` (P0002); a missing permission answers 403 `forbidden`; a failed second factor 401 `mfa_required`. Statuses in the "ok" column are the success status.

## 2. The account number

`POST /v1/platform/accounts` is the only request that carries a bank account number (and the IFSC), entered once.

What the route does, in order: check the permission (403 before anything else, then 503 if no key source); read the live fingerprint key versions (the active one, and the proposed one during a rotation); read the **approved, effective** format rule for the country and account type from the database (none: 409 `account_format_unvalidated`); compute the keyed fingerprint with `fingerprintAccount` for every live version (the adapters validate digits-only and the rule's length range and the IFSC shape, and throw a fixed-text error with a reason class); call `payments.register_account` with the fingerprint, the key version, the masked reference (`XXXXXX` and the last four digits), the rule id and `p_format_validated => true`, plus `p_other_fingerprints` (the same account under the other live version) and `p_rekeys` for a re-key; read back `id`, masked reference and status. The response is exactly those three fields.

How the number is kept from every sink:

- The request body schema is wrapped with a transform: the number and IFSC become an `AccountSecret` (private fields; `toJSON`, `util.inspect` and `Object.entries` show only the bank code, the length and the last four digits; `wipe()` empties it in a `finally`). The shared idempotency layer hashes the parsed body, so the stored `request_hash` covers the bank code, the length and the last four digits (the masked reference), **never the number**: an unsalted SHA-256 of a short number could be guessed offline. A test pins the stored hash to exactly that shape.
- The number never reaches SQL, a URL, a header, an error message (`account_number_invalid` and `ifsc_invalid` carry fixed text; zod validation errors name fields and rule codes, never values), a log line (the app's error handler logs type and code; the request serialiser logs method and path), an audit event (the SQL writes ids and codes), the outbox or an exception subject. The handler also empties `accountNumber` and `ifsc` in `request.body` and clears `request.rawBody`.
- The test "keeps every account number and IFSC used in this file out of every response, log line and database table" feeds every number and IFSC the file uses (valid, too short, too long, with letters, refused as duplicates, refused by owner checks, re-keyed) through the routes, then scans every response body and header, the captured pino output at trace level and **every table of every schema** (`row::text like '%number%'`, which covers `audit.events`, the outbox, exceptions, `ops.idempotency_keys`, the registry). It also checks that no fingerprint (under either key version) appears in a response or a log. Deliberate leaks (a log line under an unredacted key, an echo in an error, an extra column, the number made enumerable for the idempotency hash) each make a test fail (section 7).

Limits, honestly: JavaScript strings cannot be overwritten in memory, so what is guaranteed is that no logger, serialiser, error mapper or idempotency record reaches the number and that the references are dropped when the request ends. An idempotency key reused by the same person with a different number that has the same bank code, length and last four digits would replay the first answer (the masked reference is the same either way); the database function compares the fingerprint when the stored replay has expired, and the test "recognises a retried key even after the stored replay has expired" covers that path.

Format rule and IFSC: the adapter's rule `status` is the **evidence label** (`confirmed` maps to `verified` with the source note; `unverified` and `likely` map to `unverified`), not the database approval state, which the route selects (`status = 'approved'`, effective today IST, newest version) and the database re-checks. The IFSC is required for every registration (the canonical fingerprint input includes the bank code, the first four letters), even if a rule row says `ifsc_required = false`. The 9 to 18 digit seed is still an unverified assumption; approving it is a recorded platform decision, not evidence (`accounts.md` section 0).

Key rotation over HTTP: propose version n+1; register new accounts as usual (the route also sends their fingerprint under the proposed version); re-key every live entry by entering its number again with `rekeysRegistryId` (registered under the proposed version; the owner must match); verify the successor of every verified entry; a different registry verifier approves. A process that holds keys for only some live versions answers 503 rather than registering a half-keyed account.

## 3. The callback token

`POST /v1/lender/payment-configs` generates 32 random bytes (base64url, 43 characters), stores only `sha256(token)` (hex, the same function the callback receiver applies to the path segment) as `p_endpoint_token_hash`, and returns `endpointToken` and `callbackPath` (`/v1/hooks/provider/<token>`) in the 201 response, once. Secrets are accepted only as NAMES (`^[A-Z][A-Z0-9_]{2,63}$`, different from each other); a value, an unknown field (`endpointToken`, `webhookSecret`, ...) or a nested rail limit is a 422 that does not echo the input. The token is not in any log line, any table other than the one below, or any later response (a test scans all of them).

Known gap: the generic idempotency layer stores the response of every POST in `ops.idempotency_keys.response_body` for 24 hours and replays it for the same key, so the token exists in that row for 24 hours and a retry with the same key returns the same token. That is the one place besides the response (the test asserts the token is in no other table). To make the token strictly once, add an optional `replayBody?: (body: unknown) => unknown` to `UserRouteSpec` in `http/routes.ts` that `completeIdempotent` applies before storing, and have the draft return `endpointToken: null` there (the response contract would then need `nullable()`); I did not change the shared file. After the stored replay expires, a retry with the same key and a new random token is refused by the database with 409 `idempotency_conflict` (the stored hash belongs to the first token): the token cannot be re-issued, the lender withdraws the draft and drafts again.

## 4. Other design decisions

- Unknown or foreign ids on lender writes answer 404 (`submit`, `decide`, `retire`, `withdraw` raise P0002 for anyone without the permission in the configuration's lender); on `draft`, `claim` and the platform writes the SQL answers 403 `forbidden`. This is the database's own choice and is kept.
- Free text (reasons, notes, source notes, rail-limit source, legal owner name) and evidence labels are refused when they hold a run of nine or more digits (spaces and hyphens ignored) or a PAN-shaped token (422 `validation_failed`, no echo), so they cannot become a second copy of an account, phone or identity number. Merchant references are identifiers and are not checked this way. The database keeps its own guards (`feature_evidence_ok`, the legal owner name check).
- Responses are built from explicit column lists and passed through their schema before sending (the shared layer only validates, it does not strip), so an undeclared column cannot leak. `fingerprint`, `endpoint_token_hash` and `idempotency_key` are never selected.
- Keyset pagination (`created_at`, `registered_at`, `claimed_at` or `requested_at`, then `id`, newest first) with the shared opaque cursor; small closed lists (providers, rules, key versions, return codes) are not paged.
- Money: rail limits are the only numbers; integer values are bounded by the `Paise` primitive (0 to 1e14) and checked again by the database (`^[0-9]{1,15}$`).

## 6. Not built, deviations and open gaps

- **Wiring of the fingerprint key source** (section 0) is not done: registering an account answers 503 in the running application until the lead wires it, and no production key manager exists. The integration test builds the module's routes with a local test key source in its own Fastify instance (and checks the full application's 503).
- **Settlement accounts have no creation route.** `link` has something to link only once a settlement account row exists; the notes say the system creates an unverified row on a lender request, but no route or worker does that yet (my fixtures insert rows as the database owner). Not in my brief; it blocks a real end-to-end setup.
- **Platform per-lender switch view cannot tell an unknown lender from one with every switch off**: a features administrator cannot read `tenancy.organizations` (only `platform.organizations.read` can), so the existence check I first wrote hid every lender from them. Requests and kills for an unknown lender still answer 404.
