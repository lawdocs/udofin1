# Phase 08a notes: lender portal screens for payments, mandates, reconciliation and exceptions (builder u4)

Code: `packages/portal-kit/src/payments/**` (views, loaders, allow-listed operations, wording, formatting), the pages and the one server action in `apps/lender-portal/app/payments/**`, `apps/lender-portal/app/mandates/**` and `apps/lender-portal/app/reconciliation/**`, tests in `packages/portal-kit/test/payments.test.tsx`. The API this calls is described in `api-lender-payments.md` (and, for the list of settlement accounts, `api-lender-accounts.md`); the contracts are `packages/contracts/src/http/lender-payments.ts` (every export prefixed `Lp`). Spec: `docs/specs/08-servicing-payments-mandates-collections.md` sections 9, 10, 16 and 17 (lender portal list). These screens are for lender staff only; nothing here is shown to a borrower.

An earlier run of this builder (branch `p08a/w6-u4`, three commits) was reviewed in full and taken over: the views, the operations table, the pages and the 173 tests were sound and are kept; this run added the browser-side statement check, filters that survive the filter forms, honest cap notes, wording corrections, the guard-removal experiments and these notes.

## What the screens do and do not do

- **Show, never work out.** Every figure is the one the API returned, written as rupees with Indian digit grouping from integer paise (`lpRupees`, integer arithmetic only), or "Not reported" when the API says null. A count the report does not carry is "Not available", never zero. Nothing is added, rounded, totalled or compared: a settlement whose parts do not add up is shown as the provider reported it with a flag, and the sum of the parts appears nowhere.
- **Whose figure and when.** Provider figures say so ("as reported", "the provider calls it ..."), timestamps are written in IST with the 24-hour clock (`lpDateTimeIst`), calendar dates as stated.
- **Stages are the API's facts, not the portal's.** A successful provider payment shows four rows (provider captured, provider settled, bank confirmed, lender posted), each "Recorded" or "No record yet" from the API's booleans, each with the source that records it (taken from the definition of the `payments.payment_stages` view). Nothing says "paid" or "successful" in the portal's own voice; the provider's own word is quoted as the provider's ("The provider calls it 'paid'"). "Received by the payment provider" is the word for a succeeded request and the page says it does not mean the lender has posted it. "No record yet" also appears when the lender has not supplied an input (for example no bank credits); the page says so and points to the reconciliation report, which lists the inputs a run could not check.
- **Standing line "settled to a non-lender account".** Zero items and zero rupees is written plainly ("Zero is the expected figure") and shows no banner. When that run had no provider settlement report, the page adds that zero is not evidence. Any non-zero item count or amount, even one of the two alone, raises a banner whose heading begins with the word "Critical" (never colour alone). A withheld line (null) is "not available", never zero. A settlement batch or payment whose destination the API flags as not the lender's verified account gets the same banner.
- **No server text on a screen.** Closed vocabularies and stable error codes go through word tables (`labels.ts`). A value the table does not know is "Not recognised by this version of the portal"; an error code it does not know is a generic sentence, never the code. A failed load says "Could not load ..." and repeats nothing the API said. Lender-written free text that the API returns on purpose (the note of an exception step) is shown as written, escaped by React, under a line saying that Udofin does not check it. Provider references (payment, order, mandate, debit, event, batch and settlement references) are shown on purpose, as the API note lists them; the masked account is shown as the borrower typed it, with "Udofin has not verified it".
- **Write forms follow the permission set.** The pages derive what the person may do from `/v1/me` (`lpCapabilitiesFrom`); a form is drawn only for a person who holds the permission (configure for the three settings forms, reconcile for the upload and the exception actions). Read-only roles see the values and a sentence saying their role does not include changing them. This hides a form; the API and the database authorise every call again.
- **One allow-listed operation per form.** `LP_OPERATIONS` is the only way a form can write: eight operations, each mapped to exactly one API route, each checking its fields again and sending an `Idempotency-Key` (minted when the form renders). An unknown operation, a key of the wrong shape, a missing confirmation, or a return path outside the payment, mandate and reconciliation pages is refused without any call to the API.
- **Every write is an explicit action with a confirmation.** Each form carries its own confirmation box, never pre-ticked and required; the server action refuses a write without it. Each settings form has a "What this changes" card that says what it changes and what it does not (no loan figure, no payment, no money moves).

## Bank-credit upload behaviour worth knowing

- The statement is CSV text whose first line names exactly `valueDate,amountMinor,utr` in any order. The page says so, says that any other column (a narration may carry a name) makes the server refuse the whole file and store nothing, and says that the server checks every line and decides.
- **In the browser** a small client component (`statement-input.tsx`) reads only the first 4,096 characters of a chosen file, or looks at pasted text, and warns in words if the first line is not exactly the three columns. It only warns; the submit button is never disabled by it, because the server decides. It also says when both a file and pasted text are given.
- **In the server action** the same check (`statement.ts`, a dependency-free module shared by both) runs again before anything is sent, together with the size cap (250,000 characters, the API's) and "either a file or pasted text". The file is read as text by the action; its name is never sent anywhere. The API then repeats every rule on every line.
- The result is the API's two counts (recorded, already on record) or a whole-file refusal in words. No row value is ever shown.

## Not built, deviations and gaps (honest list)

Things the API lacks (no client-side workaround was invented):

- **No list of uploaded bank credits, no list of the matches of a run, and no link from a run to its exceptions.** After an upload the page shows the API's two counts only. A run is opened by its date, which returns the newest run of that date; an earlier run of the same day cannot be opened (no `GET` by run id).
- **No directory of the colleagues who may act on an exception.** "Assign to me" uses the signed-in person's own id; "Assign to a colleague" asks for a user id (the server refuses anyone who does not hold the right). Assignees are shown as "You" or as the end of an id, never by name, because the portal has no directory.
- **The allowed ranges are not published.** The database refuses link validity outside 5 to 10,080 minutes, a pre-debit lead time outside 24 to 168 hours, waiting times outside 1 to 30 days and 1 to 720 hours. The forms do not show these figures (that would put a rule in a screen that can drift); a refusal says "inside the range the server allows". If the owner wants hints on the forms, the API should publish the limits. **Owner decision.**
- **The defaults are not returned.** When a lender has set nothing, the pages say that the platform's defaults apply (and, for waiting times, that they are unverified and have no source on file) without a figure, because no route returns them. Each report states the waiting times its run used.
- **The settlement account list needs `payment.read`.** A role that holds `payment.reconcile` without `payment.read` sees the upload page with "Could not load your settlement accounts". The route belongs to the accounts module.
- **The activation switches are not consulted** (API note 3): a lender whose `payments` or `mandates` switch is off still sees its history, with no banner saying the switch is off.
- **Free-text notes are not screened for personal data by the database** (API note 7). The forms warn not to put names, numbers or other personal data in a note, and the history says Udofin does not check notes. A database guard is the real fix.
- **The `verification` detail of a provider event** (four status strings, not a closed list) and the `currency` fields are not drawn; the event's status, amount and processing outcome are.
- **Ops-side screens are not built here.** `GET /v1/platform/exceptions` (platform-owned exceptions for Udofin staff) has no screen; lender users see platform-owned exceptions read-only. Platform operations staff without a lender membership get no lender forms and a "cannot view" notice for the delivery counts (the route needs a lender).

Deviations from the brief:

- **The header check is also made in the server action, not only in the browser.** The brief asks for a client-side check and "the server decides". The browser component only warns and never blocks. The server action then refuses a wrong first line (`csv_header_invalid`) before calling the API, using the same function. Nothing is lost (the API refuses the same files with `unexpected_field`), but for that one rule the API is not asked. If the owner wants the API to be the only decider, delete the one line in `operations.ts` and the tests that expect the early refusal (six tests fail when the line is removed, which is how the guard was checked). **Owner decision.**
- **The file is read by the server action** (as in builder u3's import form): the browser sends the file in the multipart form, the action reads it as text and posts it as `csv`. The browser reads only the start of the file for the warning.
- **Sub-pages are reached from in-page tabs** (`Payments`, `Provider events`, `Payment policy`, and so on), not the top navigation, which has one entry per area. Navigation shows `Payments` and `Mandates` to `payment.read`, and `Reconciliation` to `payment.read` or `payment.reconcile`.
- **Regulatory figures.** No penalty, delay, notice-period or threshold figure of any regulation is shown anywhere in these screens. The only numbers are the lender's configured values and the figures the API returned. The waiting-time defaults, which the database notes call unverified with no source, are labelled "unverified default" and are not shown as figures. Nothing here says a control is met.
- **No export.** No page exports anything (the brief forbids exporting personal data; none was needed).

Not tested by an automated test:

- **The Next.js pages and the one server action.** They are thin (session, client, load, draw, redirect with a stable code); their logic lives in `packages/portal-kit` and is tested there. `apps/lender-portal` has no test runner and `tests/e2e` was not extended (its fake API would need the new routes), so there is no browser test of these pages, and no test drives the client component in a real browser (only in jsdom).
- **The stale-read guard of the browser component** (a later file choice ignores an earlier, slower read) is a convenience guard with no test.
- **Colour.** No new colours were added; the pages use the existing portal classes (`state-error`, `form-error`, `tabs`, `facts`). Meaning is always in words, not colour alone ("Critical", "Problem with the first line", "Not your verified settlement account"). A contrast check against the theme tokens was not run.
- **Hindi.** The lender portal is English only, as in earlier phases.

## Evidence for the controls matrix (facts about behaviour, no compliance claim)

- MNY-02 (no pass-through or pool account): the reconciliation report page carries the standing line "settled to a non-lender account" with items and rupees; zero is written as the expected figure, anything else raises a critical banner. This shows the portal reports what the API computed; it does not show the control is met. A zero from a run without a provider settlement report is labelled as not evidence.
- MNY-03 and MNY-07 (mandates, pre-debit notice): the mandate page shows the pre-debit notice status the database recorded and flags a late notice. The lead time is a lender setting shown as hours; no regulatory figure is stated on any screen (MNY-07 is `unverified` in the matrix).
- Exceptions: acknowledge, assign, resolve and reopen are separate, explicit, confirmed actions with a closed reason list and label-only evidence; the screens say that resolving annotates the exception and moves no money. A platform-owned exception is shown to lender users as handled by Udofin platform staff and offers them no action.
- Data minimisation: no borrower identity, no payload, no signature, no account number appears (the masked reference is what the API returns); the upload refuses any column but the three; a test scans rendered pages for long digit runs (identifiers stripped first), at-signs, phone prefixes and credential-like words.
