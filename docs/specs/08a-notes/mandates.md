# Mandates (migration 20261018000915)

Interface notes for the API, worker and screens. Spec: `docs/specs/08-servicing-payments-mandates-collections.md` section 8. Tests: `supabase/tests/021_p08a_mandates.test.sql` (222 assertions) and `packages/domain/test/mandate-lifecycle-sync.test.ts`.

## What is and is not built

- **The lender is the creditor.** A mandate carries the merchant reference of the lender's own verified merchant (the one in the lender's active, validated payment configuration). `payments.request_mandate` refuses anything else.
- **No real rail.** No provider, sponsor bank or utility code exists (D-65/D-66). The only implementations of the port are the labelled mock and an unconfigured placeholder. Mandates need a provider registered as `mandate` or `payment_and_mandate`, and rail limits copied from the provider's documentation into the lender's configuration (`rail_limits`, per rail `max_mandate_amount_minor` and `needs_afa_each_debit`). Without them the rail is `rail_not_configured`: nothing is assumed. A MOCK or SANDBOX configuration can never satisfy the `mandates` activation gate.
- **Udofin does not present debits.** The lender (or its sponsor bank) schedules and presents them; Udofin plans expected debits from the lender's reported schedule for the pre-debit notice, and records what the provider reports. The provider port has no "present a debit" method and none is added.
- **No borrower bank-account verification exists in the repository.** Phase 07 stored none (there is no such table), so the mandate stores only the masked reference the borrower supplied, and the bank's own authorisation step in the provider flow is the only proof that the account is theirs. The spec's "a changed verified bank account cancels the mandate" therefore cannot be implemented; it is recorded as an open gap (see below) and not claimed.
- **Not built:** a mandate required before disbursal (`before_disbursal` cannot be stored: it needs the Phase 07 journey changed), Udofin-initiated debits, physical NACH, retry rules beyond what the provider reports.

## Lifecycle (`payments.mandate_transitions`, mirrored in `packages/domain`, drift-tested)

`draft` to `registration_pending` (hand-off taken) to `active`; or `rejected`, `failed`, `expired`, `cancelled`, `requires_reconciliation` (outcome unknown); `active` and `paused` move between each other; `revoked` and `expired` from active or paused. **The system is the only actor in every row.** A trigger checks who is asking even for a definer function called by a borrower. Moves happen only through one rule (`private.apply_mandate_status`): a report older than the last one, or repeating the current status, changes nothing (`ignored_stale`); an allowed transition is applied; a contradiction (for example `rejected` for an active mandate, or anything after a terminal state) opens a `mandate_status_conflict` exception and changes nothing. Every move writes an append-only `payments.mandate_events` row with its source: `request`, `handoff`, `provider_event` (pointing at the verified event), `status_lookup` (an authenticated lookup) or `system` (a time rule).

## Functions

Borrower (SQLSTATE|hint): `payments.request_mandate(mandate_id, loan, rail, max_amount_minor, start_date, end_date, masked_account_ref)`. The mandate id is chosen by the app BEFORE the step-up code is requested, and the code (`mandate_creation`) is bound to that id (`42501|stepup_required`). Also required: device integrity of at least `device` (`42501|integrity_insufficient`), the `mandates` switch (`55000|feature_disabled`), an active loan (`55000|loan_not_active`), the lender's one active valid collection target (`55000|collection_target_invalid`, `config_ambiguous`), a provider that offers mandates (`55000|provider_not_mandate_capable`), `55000|rail_not_configured`, `22023|amount_not_allowed` (above the lower of the rail limit and the lender's ceiling; no amount means that lower figure), `22023|dates_invalid`, `22023|account_ref_invalid` (anything but a masked reference is refused), `23505|mandate_exists` (one live mandate per loan), `23505|idempotency_conflict` (same id, different content; the same content returns the same mandate and needs no new code). It creates a DRAFT only; the app then asks the provider for a hand-off (in the API request, so the bearer hand-off link is returned to the app and never stored) and the worker records the result. `payments.request_mandate_cancellation(mandate)` records a REQUEST and queues `mandate.cancel` (ids only); `payments.my_mandates()` lists the caller's mandates with provider-confirmed status, masked account, limits, the "needs authentication on every debit" flag and the next planned debit.

Lender (`payment.configure`, aal2): `payments.set_mandate_policy(lender, requirement, max_amount_cap_minor, pre_debit_lead_hours)` with `requirement` in `optional`, `before_first_due` (informational: no loan operation is blocked) and a lead time of 24 to 168 hours (default 48). Platform (`platform.payments.providers.manage`, aal2): `payments.set_return_code_class(provider, code, class, evidence_ref)`; nothing is seeded, an unlisted code is stored verbatim and unclassified.

System: `record_mandate_handoff(mandate, outcome, provider_ref, expires_at)` (`handoff`, `rejected` (a provider's refusal, source `handoff`), `unknown`, and from migration 918 `not_sent` (nothing reached any provider: draft to `failed` with source `system`, no exception); an unknown outcome is `requires_reconciliation` plus a platform exception, never a retry without a lookup), `apply_mandate_lookup(mandate, provider_status, provider_ref, observed_at)`, `apply_debit_lookup(mandate, debit_ref, scheduled_on, amount, status, return_code, observed_at)`, `mark_mandate_cancel_sent`, `request_cancel_for_closed_loans`, `sweep_mandates(draft_grace, cancel_grace, unresolved_after)` (closes abandoned drafts, expires mandates past their end date, reports unconfirmed cancellations and unresolved outcomes), `mandates_needing_lookup`, `plan_mandate_debits(horizon)`, `claim_pre_debit_notices` and `record_pre_debit_notice`. Verified provider events reach `private.apply_mandate_event` through `payments.apply_provider_event` (the hooks of the previous migration are replaced): a mandate is found by the provider reference within the callback's own lender and provider, never across lenders.

## Debits

`payments.mandate_debits`: one row per installment per mandate. A **planned** debit comes from the lender's newest schedule; its amount is the lender's reported figure when the newest report is consistent, fresh and names that installment, otherwise the installment as the lender's schedule states it; never above the mandate maximum (an installment above it is not planned and the lender gets `mandate_debit_exceeds_max`). A provider-reported debit attaches to the one planned debit with the SAME amount and a date within three days; otherwise it is recorded **unplanned** and flagged (`mandate_debit_unresolved`). Status moves forward only (scheduled, notified, presented, then settled, returned or cancelled); two different final statuses contradict each other (exception, no change). A debit above the mandate maximum is flagged and opens a critical `amount_mismatch`. A returned debit creates no Udofin charge and touches no payment, adjustment or intent; any bounce or late charge is the lender's, reported by the lender. The return code is stored verbatim.

`payments.pre_debit_notices`: one per planned debit, due the lender's lead time before the start of the debit day (IST). One planned too close to its debit is `late` and the lender gets `mandate_notice_late`; a notice that cannot go out on any channel is `late` too. The database stores no notice wording: the app shows a fixed factual line (amount and date). Accepting a notice moves the debit to `notified`; `delivered` is never recorded for a notice that was not sent.

## Activation (`private.feature_prerequisites_unmet`)

`mandates`: the payments checks on the lender's configuration (`payment_config_missing`, `payment_config_mock_or_sandbox_only`, `registry_entry_not_verified`, `payment_config_validation_failed`) plus `provider_not_mandate_capable`, `mandate_rail_not_configured`, `mandate_policy_missing` and `servicing_sync_not_enabled`. Every earlier reason is preserved.

## Missing-texts register and open gaps (owner decision 6)

1. The provider's and sponsor bank's written specification of each rail: no-AFA debit limits, return codes, cancellation behaviour, notice duty. All of `rail_limits` and the return-code classes are configuration to be filled from those documents; none is claimed.
2. Whether the issuer's own 24-hour pre-debit notice (reported in secondary sources for UPI) removes or adds to Udofin's duty to send one: **unverified**. The lead time is a lender setting.
3. A borrower bank-account verification (Phase 07) does not exist in this repository. Until it does, the "account verified in Phase 07" rule and "a changed account cancels the mandate" are not implemented.
4. The device-integrity tier for mandate creation (`device` or `strong`) is a conservative choice made here, not a recorded owner decision (D-24 names the tiers, not this threshold).
