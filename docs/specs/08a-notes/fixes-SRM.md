Also changed because the wording screen sits inside CHECK constraints, which PostgreSQL evaluates again on every update: the six constraints now let a row leave use (retired wording or sentence, released hold) even if it was written under the old, weaker screen, and refuse unsafe text on every insert and on any change that keeps the row in use. They are `NOT VALID`, so the migration cannot fail on existing rows (tests 107 to 111). Run `validate constraint` after those rows have been reviewed.

## How the tests were checked

- Whole pgTAP suite on its own database: see the report (`Files=25`, all passing).
- 027 against a database without the migration: 65 of 111 assertions fail (every assertion that exercises a fix); the rest are controls and the M38 guard tests, which pass on correct code and are proven by the mutation run below.
- Mutation run (a script outside the repository removed one guard at a time from the final migration, rebuilt a scratch database and ran 020 and 027): all 38 mutations were caught. They cover each guard named in M38, each rule of the new screen (domain, separators, Devanagari digits, PAN), both note limits, the cap by latest claim, the claim token, hold-after-claim, the resume rules (time, policy, loan), the planner exclusion, the three received-payment sources, the paging of the scan, the report checks and the constraint exemptions.
- A scan over 20,000 held-back rows takes about 1 second (it took about 38 seconds in a first version that re-sorted every page; the system login times out at 120 seconds).

## Owner decisions

1. **A57 scope.** Release resumes only messages scheduled after the release. A message whose time passed during the hold stays suppressed, so nothing goes out late because a complaint hold ended. If the owner prefers to resume messages up to 48 hours late, change the `scheduled_for` condition in `release_communication_hold`.
2. **M33 and arrears.** While the lender's newest report shows any overdue amount, pre-due and due-day messages for later installments wait (the reviewer's suggestion). The alternative is to send them; say so if wanted.
3. **No new suppression reason.** A pre-due or due-day message whose day has passed is suppressed `expired` ("could not be sent in time") and an overdue message for a paid anchor installment is suppressed `paid`, because the contract's zod enum and the portal's wording list are closed. A distinct reason (the finding suggested one) needs `LR_SUPPRESS_REASONS` and the portal wording changed first.
4. **Hold note limit** is 10 to 200 characters. A different limit means changing the table check and both functions.
5. **A stale lender report and suppression labels.** Rows of a loan without a consistent, fresh report are no longer selected at all, so a hold, closure or retired policy is not recorded on them first; they stay planned and expire after 48 hours as before. Nothing is ever sent in that state.

## Declined or only partly done

- **M38, "two-session test for the cap".** pgTAP runs in one session and one transaction, so two workers cannot be simulated. The per-loan advisory lock is unchanged and untested here; the API integration suite (two worker connections) is the place for it.
- **M40, window re-check at report time.** A send report is not refused because the window closed in between: the worker has already sent at claim time, so refusing the true report would only cause a duplicate send. The window is judged at claim; holds are handled by suppressing claimed messages at placement.
- **U39, names.** Not detectable (see above).
- **U39, the other half.** `private.servicing_text_safe` (document decline notes, security release delay reasons) is the servicing area's.

## Risks noticed, not fixed

- Two workers can still, in principle, deadlock on the per-loan advisory locks when they take different rows of the same two loans in opposite order (Postgres aborts one call, the next run retries). Unchanged from migration 914.
- `suppress_reminders_for_loan` still leaves claimed messages alone (only a hold stops them).
- A first import of lender receipts (history) sets every receipt's received time to the import, so reminders for those loans are quiet for 48 hours (conservative, by design of the received-time rule).
- Any message suppressed with the reason `hold` (also one written before this migration, or by `suppress_reminders_for_loan(loan, 'hold')`) resumes when a communication hold of that loan is released, if it is scheduled in the future.
- The digit rule has a visible false positive: a date written `01.04.2026` or `01-04-2026` (8 digits once the separators are removed) is refused in wording, sentences and notes. The lender writes `1 April 2026`. This follows the rule the area brief gave (8 digits after removing spaces, hyphens and dots).
