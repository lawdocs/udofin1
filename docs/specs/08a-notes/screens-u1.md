# Phase 08a notes: borrower app, loans and servicing screens (builder u1)

Code: `apps/mobile/app/(app)/loans/**` (the screens), `apps/mobile/src/borrower/servicing*.ts*` (client, view models, formats, error mapping, shared screen parts), `apps/mobile/src/borrower/{useServicing,useDocumentOpener,useRequestActions,useRefreshOnFocus}.ts`, `apps/mobile/src/borrower/MyLoansEntry.tsx` (the one entry on the home screen, wired in `apps/mobile/app/(app)/index.tsx`), the catalogue partials `apps/mobile/src/i18n/{en,hi}.servicing.ts` (201 keys, `loans.*` and `reminders.*`), tests in `apps/mobile/test/servicing.test.ts` (95 tests), `apps/mobile/test/servicing-screens.test.ts` (22 tests) and the fixtures `apps/mobile/test/servicing-fixtures.ts`. The API these screens call is described in `api-servicing.md`; the wire contracts are `packages/contracts/src/http/servicing.ts` (every export prefixed `Svc`). Spec: `docs/specs/08-servicing-payments-mandates-collections.md` sections 11, 12, 16 and 17. The pay, payment status and mandate screens are another builder's (`apps/mobile/app/(app)/payments/**`); these screens only navigate to them.

## What the screens do and do not do

- **Show, never work out.** A figure is the one the API returned: paise are written as rupees with Indian digit grouping (`formatAmount`), nothing is added, rounded, totalled or compared. The only branches in the code are on facts the API states (`figuresAvailable`, `stale`, `totalMismatch`, `status`, a nullable field). A source test scans every screen and helper for `reduce`, `toFixed`, `Math.round`, `parseFloat` and `* 100`.
- **Whose figure and when.** Figures carry "As reported by <lender> on <date, time IST>" (the lender's report time, not the time Udofin received it). The loan status and the sanctioned and disbursed amounts are labelled "per <lender>". A stale report gets a plain banner with the same time (the kit's warning tone; the words carry the meaning, not the colour); there is no countdown or urgency. A figure that cannot say when the lender reported it is not shown (`figuresAvailable` true with no readable `reportedAsOf` is drawn as withheld).
- **Withheld figures are never zero.** When the API says `figuresAvailable: false` the page says "<lender> is checking these figures. No amounts are shown for now." and draws no amount (tested: no currency sign in the withheld model). An individual figure the lender did not report is "Not reported by <lender>". A zero the lender did report is shown as zero.
- **Overdue shows no charge figure.** The overdue block shows the lender's overdue principal, overdue interest, total overdue as the lender stated it and the days past due, and the note that nothing was added up or changed here. The penal and other charge amounts that `GET /v1/loans/{id}` also returns are deliberately not drawn (tested with canary amounts), and no sentence about charges is drawn: the lender's approved penal-charge sentence is not on the loan routes (see gap 1).
- **Payment stages use the API's closed list in plain words.** started ("Nothing has been confirmed yet"); provider_received ("Received by the payment provider. This does not yet mean that <lender> has posted it to your loan"); lender_posted ("<lender> has posted it to your loan"); needs_attention ("Needs attention: contact <lender>"); cancelled, failed, expired. Receipts: posted, reversed, recorded by the lender. Adjustments: refund, chargeback, reversal, correction "was reported". No sentence uses "paid", "successful" or "completed" (tested over the contract's whole list, in English and Hindi). A stage the app does not know becomes "not available in this version of the app. Ask <lender>", never the value.
- **No server text on a screen.** Every sentence comes from a message key. Stable error codes go through `servicing-errors.ts` (its own table, then the shared `errors.ts`, then the generic sentence). A vocabulary value or code the tables do not know is never drawn (tested with drifted values and a fake SQLSTATE; a source test forbids `{...code}` between tags). The only server-written text drawn is text the API returns on purpose and a screen shows as the lender's words: the reminder message (verbatim, never shortened), a decline note ("Note from <lender>"), a delay reason ("Reason given by <lender> for a delay"), the lender's own references and the lender name.
- **Closure never claims a release.** The no-dues letter and each security-release task are drawn from the prompt KEYS the API returns, mapped to this app's own wording (5 collateral types, pending and confirmed). "Confirmed" is said only when the key, the recorded status and the lender-confirmed flag all agree; a key that disagrees with the status, an unknown key, or a malformed key shows "Ask <lender> about the status of this item." and never the key. No closure sentence mentions Udofin or says this app released, issued or verified anything; the page ends "This app does not hold or release any security and does not issue any letter."
- **Idempotent writes.** Every POST sends an `Idempotency-Key` that belongs to one user action. A lost answer (offline, timed out) keeps the key so a retry finds the first attempt; any answer from the server, or a success, ends the action and the next tap gets a new key (`keyAfter`). In the statement form, editing a date starts a new action (a new key), because the same key with different content would be refused as reused. Cancellation and "mark read" follow the same rule.
- **Documents are opened through the API.** A lender file is fetched from `GET .../documents/{docId}/content?purpose=view` (an authenticated call, `no-store`), checked in the app (it is the document and loan asked for; its byte count equals the recorded size) and only then handed to the device's PDF viewer through the Phase 07 `openPdf` (private cache file, deleted at once). There is no stored link and no browser hand-off. The SHA-256 the API returns is not recomputed in the app (see gap 6).

## Not built, deviations and open gaps (honest list)

1. **No penal-charge sentence on the loan routes.** The brief says an overdue loan shows the lender's approved penal-charge sentence exactly as returned, and nothing when the API says it is missing. `GET /v1/loans/{id}` carries no sentence and no "missing" flag; the sentence (`penalCharge`, `penalChargeTextMissing`) is on the payment options route, which this builder was told not to call. So the loan home shows the overdue figures and nothing about charges, and the sentence appears where the API carries it: in the lender's reminder wording (shown verbatim) and on the pay screen (the payments builder's). If the owner wants the sentence on the loan home, the API needs to add it (or the loan home needs to read the options route). **Owner decision.**
2. **Charge amounts reported by the lender are not shown.** `penalChargesMinor` and `otherChargesMinor` come back from the loan route but are not drawn (the brief: "nothing else about charges"). The total overdue is drawn as the lender stated it, so the principal and interest lines can add up to less than the total; the note says nothing was added up or changed here. **Owner decision** whether a borrower should see the lender's charge amounts.
3. **Target dates are shown, labelled a platform default.** The API's `dueBy` for statements, quotations and the closure tasks comes from platform defaults labelled `unverified` (`api-servicing.md`, gap 5). The screens show it as "Target date: <date, time IST>" with "This is a platform default. It is not a legal or regulatory deadline, and not a promise by <lender>." Only a basis marked `confirmed` drops the second sentence, and even then no regulation is named or quoted: the 30-day security-release period and the ₹5,000-a-day exposure of spec section 12.3 are not shown, because the notes do not mark them verified against the primary text (CLAUDE.md rule 5). **Owner decision** whether to show target dates at all.
4. **Reminder preferences are not an API feature and nothing was added.** Language lives on the profile and push is the device permission (`api-servicing.md`, gap 1). The messages screen only reads and marks messages read.
5. **Pay and Set up auto-pay are always shown, also for a closed loan** (the brief: always show them and let the pay screen explain). The loan page does not call the options route.
6. **The SHA-256 of a document is not recomputed in the app.** There is no crypto dependency in `apps/mobile` and none was added. The API verifies the stored bytes against the recorded hash before it answers; the app checks which document it is, which loan, and the byte count. The whole file travels as base64 inside JSON (`api-servicing.md`, deviation 3), so a file near the 25 MB limit is about 33 MB in memory.
7. **The foreclosure quotation is not checked against the device clock.** "Pay this quotation" is shown for a quotation the API returned as the latest valid one and not flagged; whether it is still valid when the borrower pays is decided by the pay screen and the API. A device with a wrong clock therefore cannot hide a valid quotation or invent an expired one. The validity is shown as a date and time, never a timer.
8. **Statement dates are typed text.** The period is two fields in year-month-day form (checked for real dates, both or neither); there is no date picker because none is in the dependencies. Whether the period is backwards or in the future is the API's answer (`period_invalid`).
9. **Activity order is the order of arrival**, as the API orders it; each row shows `occurredOn` as its date (`api-servicing.md`, gap 6). The screen says so. The reminder list has no cursor (the API returns the latest 50).
10. **Extra reads.** Every loan sub-screen reads `GET /v1/loans/{id}` again for the lender name (the schedule, activity and document routes do not carry it), and the home screen makes one `GET /v1/loans` call each time it is shown to decide whether to draw "My loans". A failure of that call hides the entry and changes nothing else.
11. **The lender's loan reference is drawn on screen** ("Loan reference: ..."). It is the lender's own reference and may look like an account number to the borrower; it is never put in a URL, a log or an error. Say if it should be shortened.
12. **Dates and times do not use `Intl`.** Fixed English and Hindi month names and UTC+5:30 are used so the text is the same on every device. The shared `format.ts` (used by Phase 07 screens) is untouched.
13. **Hindi is a draft**, like the rest of the app: not reviewed by a native speaker or counsel. Hindi for the closure and stage sentences in particular needs a review.
14. **Typed routes.** `typedRoutes` is on, but `.expo/types` is not generated in this environment, so the links to `/payments/...` could not be checked against generated types. The links use literal path names with params, the same form the Phase 07 screens use.
15. **No browser or device test and no end-to-end test** was added; `tests/e2e` covers the portals only.

## Evidence for the controls matrix (facts about behaviour, no compliance claim)

- Reminder wording: the inbox shows the lender's approved text exactly as returned; the app never rewrites, translates or shortens it (source test), and never composes an overdue message of its own.
- Honest payment stages: the activity list uses the API's closed list; no sentence says a payment is paid or successful before the lender has posted it (test over the contract's whole list in both languages).
- Closure and security release: the app states only what the lender reported and never that Udofin or the app released anything (tests over every collateral type and over inconsistent and unknown keys).
- Data minimisation: no screen puts a name, phone number, account number or lender reference in a URL; the only identifiers in paths and links are opaque ids and the opaque activity cursor; nothing is logged.
