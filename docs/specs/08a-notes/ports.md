# Phase 08a notes: stream PORTS AND MOCKS (TypeScript adapters)

All code is in `packages/adapters/src/` and exported from `@udofin/adapters` (`index.ts`). Nothing here touches the network, the database or the clock (except where `now` is defaulted, stated below). Read the code; this note is the map. Vitest: `pnpm --filter @udofin/adapters test`.

Common conventions

- Money is `bigint` paise in TypeScript; decimal rupee strings on the wire, parsed only by `parseMoneyMinor`. A test (`money.test.ts`, "no floating point on money") fails if any new module uses `Number(`, `parseFloat`, `toFixed` or `Math.round/ceil/trunc`.
- Every outcome is explicit: `ok | unknown | rejected/invalid | not_found | unsupported | not_configured`. `unknown` (timeout/network) is never an empty result and never a refusal: look up before retrying.
- Errors and result reasons are classes. They never contain input values (account numbers, cell contents, amounts, secrets).
- Placeholders keep `mode: 'production'` but their key ends `_not_configured`; `satisfiesProductionGate()` is false for them, for every mock and for every sandbox.
- All mocks call `assertLocalOrTestOnly` (new, `provider.ts`): `assertProviderAllowed` (refuses mock in production) plus an explicit staging refusal for `mode: 'mock'` with the message `the <name> is for local development and tests only`. `production` -> `ProviderNotAllowedError`.

## lms.ts (spec 08 section 6.1)

Port `LmsPort` (read-only; there is deliberately no write method): `descriptor`, `capabilities {pull, push, foreclosureQuote, statement, closureDocuments, receipts}`, `listChanges(ctx, cursor)`, `fetchLoan`, `fetchSchedule`, `fetchReceipts(ctx, ref, sinceCursor)`, `requestForeclosureQuote(ctx, ref, asOfDate)`, `fetchStatement(ctx, ref, {from,to})`, `fetchClosureDocuments`. `ctx` is `ProviderCallContext`.

`LmsResult<T>`: `{outcome:'ok', value} | {outcome:'unknown', reason:'timeout'|'network'|'provider_error'} | {outcome:'not_found'} | {outcome:'invalid', reason:'malformed_report'} | {outcome:'unsupported'} | {outcome:'not_configured'}`.

Every report carries `LmsReportMeta`: `sourceSystem`, `sourceRecordId`, `reportedAt` (UTC ISO-8601 with milliseconds; the lender's "as of", not our receipt time), `sequence: number | null`, `contentSha256` (hex).

- `contentSha256 = sha256(JSON(["udofin-lms-<type>-v1", [key, value], ...]))` in the fixed key order of each normaliser; bigint as decimal string, absent as `null`. It INCLUDES `source_record_id`, `reported_at` and `sequence` (an unchanged balance reported later is a new fact and refreshes staleness) and EXCLUDES `sourceSystem`. Identical content from `file_import` and `manual_import` hashes the same. A DB unique on `(loan, content_sha256)` therefore dedupes exact re-sends only.
- `LmsLoanReport` (`reportType:'loan'`): `lmsLoanRef, borrowerRef (opaque), status ('active'|'closed'|'foreclosed'|'written_off'|'cancelled' = servicing.loan_status), sanctionedMinor, disbursedMinor|null, disbursementRef|null, disbursedOn|null, outstandingPrincipalMinor|null, nextDueOn|null, nextDueMinor|null, overduePrincipalMinor|null, overdueInterestMinor|null, penalChargesMinor|null, otherChargesMinor|null, totalOverdueMinor|null, daysPastDue|null (as reported), flags[]`. Flag `overdue_total_mismatch` is set when all four parts and the total are present and the parts do not sum to the total (flag, never fix). Disbursement evidence is all-or-none and `disbursed <= sanctioned` (mirrors the table checks); next due date and amount are both-or-neither.
- `LmsScheduleReport` (`'schedule'`): `lmsLoanRef, installments[{sequence, dueOn, principalMinor, interestMinor, feesMinor}]` (seq 1..n, strictly increasing dates, fees default 0).
- `LmsReceiptReport` (`'receipt'`): `receiptKind 'receipt'|'reversal', lmsLoanRef, lmsReceiptRef, reversesReceiptRef|null, amountMinor (> 0 also for reversals), valueDate, paymentMode|null, bankReference|null`.
- `LmsQuote` (`'quote'`): `lmsLoanRef, lenderQuoteRef, amountMinor, components[{kind (lender's label), amountMinor}], asOfDate, validUntil` (`validUntil > reportedAt`, else rejected). Udofin adds nothing up.
- `LmsDocumentRef` (`'document'`): `documentKind 'statement'|'no_dues_certificate'|'closure_letter', lenderDocumentRef, mediaType 'application/pdf', documentSha256, periodFrom|null, periodTo|null`. References only; bytes are fetched elsewhere (production document store blocked).
- `LmsChangePage {changes[{lmsLoanRef, sourceRecordId, reportedAt}], nextCursor, hasMore}`, `LmsReceiptPage {receipts, nextCursor, hasMore}`.
- Normalisers (shared by the mock, the file import and any future connector): `normaliseLmsLoan / Receipt / Schedule / Quote(raw, {sourceSystem, now?, rowNumber?})` -> `{ok:true, report} | {ok:false, errors}`. `sourceSystem` must match `^[a-z][a-z0-9_]{1,49}$` (throws otherwise). `now` defaults to the real clock and is used only to refuse `reported_as_of` more than 15 minutes in the future.
- Gotcha for the database stream: `servicing.source_system` enum currently has `finbyx, lender_lms, manual_import`. The importer emits `file_import` or `manual_import` (spec: file import is a distinct `lms_connections.kind`). Map or extend the enum; do not coerce silently.
- `createUnconfiguredLmsPort()` (`lms_not_configured`, all capabilities false, every call `not_configured`). `withLmsTimeout(port, ms)`: a call that outlasts `ms` is `unknown/timeout`, a throw is `unknown/network`, never an empty or success result.
- `LmsImportResult` now also carries `byteSize` (UTF-8 bytes of the file, also for refused files), next to `fileSha256` and `recordCount`.
- `summariseImportFailure(result) -> {fileSha256, byteSize, rowCount, errors: [{row, codes, fields}]}` (follow-up, 15 Oct 2026): the ONLY thing the audit record of a rejected import may keep (owner answer: row positions and error codes, not row values). `row` is 1-based (0 = file level), `codes` are distinct error codes sorted, `fields` are distinct field NAMES sorted. It is built from scratch from two closed vocabularies: every `LmsImportErrorCode` (a `Record<LmsImportErrorCode, true>`, so a new code does not compile until listed) and the formats' own field names (loan, receipt, schedule head and installment, quote fields, `installments`, `format_version`). A code or field outside them is dropped, so a caller-supplied key name or value cannot reach the summary even if an upstream error carried one. Verified: the first-wave key-name echo is fixed (an unknown JSON key is `unknown_field` with `field: null`; an unknown CSV header is `unknown_column` with no field), and the tests use sentinel strings for keys, cell values and loan references. Only blocking `errors` are summarised, never `warnings`; a clean file yields `errors: []`. Call it when an import is rejected (`importable === false`); the hash and size remain the batch identity.

### Import file format v1 (`udofin-lms-import-v1`, also documented in the header of `lms.ts`)

`parseLmsImportFile(text, {format:'csv'|'json', kind:'loan'|'receipt'|'schedule', sourceSystem:'file_import'|'manual_import', maxBytes?, maxRows?, now?})` -> `{kind, formatVersion, fileSha256, recordCount, rows[], errors[], warnings[], importable}`. Pure. `fileSha256` identifies the import batch. Defaults: 5 MiB, 10 000 records.

- CSV: header row of exact snake_case names, UTF-8 (BOM ignored), RFC 4180 quoting; unknown/duplicate header names and missing required columns are file-level errors; a row with the wrong cell count is `column_count_mismatch`. Nothing is trimmed or repaired. Cells starting with `=`, `+`, `-`, `@` are ordinary text (and are refused by the field rules); error rows never contain cell values.
- JSON: an array of records, or `{"format_version":"udofin-lms-import-v1","records":[...]}`. Money must be a JSON string (a JSON number is `invalid_amount`); `sequence` and `days_past_due` may be integers or strings. Unknown keys (including `__proto__`) -> `unknown_field` with `field: null`: the key is caller text and is never echoed.
- Loan columns: required `lms_loan_ref, borrower_ref, status, sanctioned_amount, source_record_id, reported_as_of`; optional `disbursed_amount, disbursement_ref, disbursement_date` (all three or none), `outstanding_principal, next_due_date, next_due_amount` (both or neither), `overdue_principal, overdue_interest, penal_charges, other_charges, total_overdue, days_past_due, sequence`.
- Receipt columns: required `lms_loan_ref, lms_receipt_ref, receipt_kind (receipt|reversal), amount, value_date, source_record_id, reported_as_of`; optional `reverses_receipt_ref` (required for a reversal, forbidden for a receipt, not equal to its own ref), `payment_mode, bank_reference, sequence`.
- Schedule columns (CSV: one row per installment, head fields must agree across rows of one report; JSON: an `installments` array of `{installment_seq, due_date, principal, interest, fees?}`): `lms_loan_ref, source_record_id, reported_as_of, sequence?` + `installment_seq, due_date, principal, interest, fees?`.
- `borrower_ref` is opaque: values shaped like a PAN (anywhere in the text) or like a 9 to 18 digit number, ignoring the separators `- . : / _`, are refused (`borrower_ref_looks_personal`), as are e-mails and anything outside `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,99}$`. A NAME cannot be recognised by shape and is not caught unless it breaks the character rule; keeping names out is the lender's responsibility and part of the file specification. `lms_loan_ref` is the lender's own loan number and is not shape-checked (numeric loan numbers are normal).
- Error object: `{rowNumber (1-based data row or JSON record; 0 = file-level), field|null, code, itemIndex?}`. Codes: `file_too_large, too_many_rows, empty_file, malformed_file, unknown_column, missing_column, duplicate_column, column_count_mismatch, unknown_field, missing_required, invalid_reference, borrower_ref_looks_personal, invalid_amount, amount_not_positive, invalid_date, invalid_timestamp, timestamp_in_future, invalid_integer, invalid_status, invalid_receipt_kind, incomplete_disbursement, incomplete_next_due, disbursed_exceeds_sanctioned, reversal_reference_invalid, invalid_items, inconsistent_report_head, invalid_validity, duplicate_row, conflicting_duplicate`.
- Duplicates inside a file: loan/schedule key `(lms_loan_ref, source_record_id)`, receipt key `lms_receipt_ref`. Identical content: first kept, later ones reported in `warnings` as `duplicate_row` (not blocking). Different content: every occurrence rejected `conflicting_duplicate`. **All or nothing (owner decision of 14 Oct 2026):** if `errors` has any entry, `rows` is empty and `importable` is false; the whole file is validated first and no partial file (for example a schedule missing its last installment) is ever returned. `errors` holds only blocking problems.

## payments.ts (spec 08 sections 7, 9, 20)

- `NormalisedProviderEvent {provider, deliveryId, eventId, objectKind: 'payment'|'refund'|'chargeback'|'mandate'|'debit'|'settlement', objectRef, orderRef?, status, rank, amountMinor: bigint|null, currency: 'INR'|null, occurredAt, settlementRef?, merchantRef?}`. `merchantRef` is added (not in the original list) so a wrong-merchant event can be compared with the lender's configuration upstream.
- `PLATFORM_EVENT_STATUSES`: `created, pending, authorized, captured, paid, succeeded, failed, refunded, disputed, cancelled, expired, active, rejected, returned, revoked, paused, unmapped`. `PAYMENT_SUCCESS_STATUSES = captured, paid, succeeded` (equals `private.payment_success_statuses()`; keep them in step). Unknown provider words map to `unmapped`, which authorises nothing.
- `defaultEventRank(status)`: unmapped 0, created 10, pending 15, authorized 20, failed/rejected 25, captured/paid/succeeded/active 30, paused 35, returned/refunded 40, cancelled/revoked/expired 45, disputed 50. Rank is per object; the database applies "lower rank after higher = `ignored_stale`". Note `active` (30) outranks `rejected` (25) on purpose: a rejection after activation must never revert the mandate, but should be raised as a reconciliation item rather than silently dropped (database stream to decide).
- `WebhookVerifier {scheme, verify(rawBody: Uint8Array, headers, {secret, now?, toleranceSeconds? = 300})}` -> `WebhookVerification`:
  - `{outcome:'verified', event, payloadSha256}`
  - `{outcome:'unverified', reason:'missing_headers'|'malformed_headers'|'no_secret'|'signature_mismatch', payloadSha256}`
  - `{outcome:'stale_timestamp', reason:'timestamp_outside_tolerance', payloadSha256}` (only for an AUTHENTIC signature: a forged stale delivery is just `unverified`)
  - `{outcome:'invalid', reason:'provider_scheme_not_configured'|'body_too_large'|'malformed_body'|'unsupported_event'|'invalid_amount'|'unsupported_currency'|'invalid_timestamp'|'invalid_identifier', payloadSha256}`
    `payloadSha256` is always present (hash of the raw body, for `payments.webhook_receipts`). The verifier needs the lender's webhook secret from the caller; it holds none. Replay (`private.mark_webhook_seen`), duplicate/unmatched, merchant and amount business checks are upstream. Deviation from spec section 9 item 5: an authentic, fresh delivery with an unsupported `object_kind` is `verified` with `objectKind: 'unsupported'` (verified-and-ignored, owner decision of 14 Oct 2026): `status` `unmapped`, rank 0, no amount, no currency, and the provider's kind word is not kept; it still needs valid identifiers and a valid `occurred_at`. `invalid/unsupported_event` is now only for a body with no usable kind word. An unknown status is verified as `unmapped`. An amount without a currency is `invalid/unsupported_currency`, so INR is always confirmed. Signatures must be canonical base64; `toleranceSeconds` must be a finite number >= 0 (otherwise `verify` throws `RangeError`); a body over 64 KiB is `invalid/body_too_large` before any HMAC is computed (the transport should still cap what it reads).
- `PaymentProviderPort {descriptor, capabilities {orderCreation, statusLookup, settlementReports, partialAmounts, webhooks}, webhookVerifier, createOrder(ctx, CreateOrderRequest), getOrderStatus(ctx, {orderRef|null, operationKey}), fetchSettlements(ctx, 'YYYY-MM-DD')}`. `PaymentResult<T>` = `ok | unknown(timeout|network|provider_error) | rejected(invalid_request|unsupported_currency) | not_found | unsupported | not_configured`. `provider_error` (a 5xx or an unparseable answer) is UNKNOWN, never a refusal: look the order up by `receiptRef`/operation key before any retry. `rejected` is a definite refusal only. The mock derives its refs from the whole operation key (a key that is already a safe reference is used as is, any other is hashed), and refuses a reused key with different parameters as `rejected/invalid_request`.
  - `CreateOrderRequest {operationKey (= intent id, idempotency), receiptRef, merchantRef, amountMinor (>0), currency 'INR', purpose, expiresAt|null}`: no personal fields exist. `CreatedOrder {orderRef, merchantRef|null, settlementProfileRef|null, checkoutLink|null (BEARER SECRET), expiresAt}`; compare `merchantRef` with the configuration (`merchant_mismatch`).
  - `OrderStatus {source:'provider_authenticated_lookup', orderRef, status, amountMinor|null, currency, merchantRef, providerPaymentRef|null, observedAt}`: the only non-webhook evidence.
  - `SettlementReport {date, batches[{batchRef, settlementRef (UTR), periodFrom, periodTo, destinationMaskedRef|null, gross/fee/tax/net minor, items[{providerPaymentRef, orderRef, gross/fee/tax/net minor}]}]}`.
- `createUnconfiguredPaymentProvider()`: key `payment_provider_not_configured`, mode `production`, all capabilities false, every call `not_configured`, `webhookVerifier.verify` -> `invalid/provider_scheme_not_configured` (the receiver should answer 503 for that provider). No real provider scheme is written.
- Mock scheme `MOCK_PAYMENT_WEBHOOK_SCHEME = 'mock-standard-webhooks-v1'`: headers `webhook-id`, `webhook-timestamp` (epoch seconds), `webhook-signature` (`v1,<base64>`, space-separated list allowed); HMAC-SHA256 with the secret as UTF-8 over `<id>.<timestamp>.` + raw body bytes; constant-time compare; header names case-insensitive. Body: JSON with string fields `event_id, object_kind, object_ref, status, occurred_at` and optional `order_ref, amount (decimal string), currency, settlement_ref, merchant_ref`. Only reachable through `createMockPaymentProvider(...).webhookVerifier` (guarded). Helpers: `signMockWebhook({secret, deliveryId, timestampSeconds, rawBody})`, `buildMockWebhookBody(fields)`, `buildMockDeliveries(scenario, {secret, orderRef, paymentRef, amountMinor, merchantRef, now, idPrefix?})` -> `MockDelivery[] {label, rawBody, headers}` (complete signed deliveries for a receiver test).
- `createMockPaymentProvider(env, {scenario?, settlementDestinationMaskedRef?})`, key `mock_payment_provider`. Scenarios: `success, failure, delayed, duplicate_event, out_of_order_refund_first, out_of_order_failed_after_captured, partial_amount, wrong_currency, wrong_merchant, refund, chargeback, unknown_outcome, bad_signature, old_timestamp`. Order calls: idempotent on `operationKey` (`mock.created` counts creations); `unknown_outcome` -> create returns `unknown/timeout` but the order exists and is found by lookup (`created`, then `captured`); `delayed` lookup -> `pending, pending, captured`; `failure` -> `failed`; `partial_amount` -> captured half the amount (integer division); `wrong_currency` lookup -> `rejected/unsupported_currency`; `wrong_merchant` -> created/looked-up with `MOCK_OTHER_MERCHANT_REF`. ## account-fingerprint.ts (spec 08 section 7.1)

- `fingerprintAccount(key: FingerprintKey, {ifsc, accountNumber}, rule: AccountFormatRule) -> {fingerprint (64 hex), formatRuleId, formatValidated: true, keyVersion, ruleStatus, maskedRef}`. `FingerprintKey = {keyId, keyVersion (int >= 1, the version of the FINGERPRINT key), key: Uint8Array (>= 32 bytes)}`. Encoding: HMAC-SHA256 over 4-byte-big-endian-length-prefixed UTF-8 parts `["udofin-account-fingerprint-v2", bankCode, accountNumber]`, where `bankCode` is the first four letters of the IFSC. **Why not the whole IFSC:** the same account number at the same bank can appear under another branch IFSC (branch change or merger, or another branch typed by the lender), and a branch-specific fingerprint would let the same account through the cross-organisation uniqueness and own-account checks. The full IFSC is still validated. The cost is a possible false match only between two different accounts that share a bank code and an account number, which is the fail-closed direction. Spec 7.1 says only "keyed HMAC of the account number"; **owner to confirm** this bank-code rule. The domain string moved to `-v2` because the input changed (no fingerprint had been stored). `maskedRef = 'XXXXXX' + last 4 digits` (matches the `masked_account_ref` check `^[X*]{2,}[0-9]{2,4}$`). A known-answer vector computed outside the code is in the test.
- `AccountFormatRule = {ruleId, country: 'IN', accountType, minDigits, maxDigits, status: 'verified'|'unverified', source: string|null}` is DATA the caller supplies (owner answer of 14 Oct 2026: configurable by country and account type, `unverified` until its source is supplied). There is no built-in range: with no valid rule `fingerprintAccount` throws `invalid_rule` and fingerprints nothing. **Registry attestation (follow-up, 15 Oct 2026):** `ruleId` is the uuid (canonical lower case; anything else is `invalid_rule`, at runtime, and a missing property is a type error) of the row in `payments.account_format_rules`. The result returns it as `formatRuleId` together with `formatValidated: true`, which the API passes as `p_format_rule_id` and `p_format_validated` of `payments.register_account` (see `accounts.md`). `formatValidated` is the literal `true` because no result exists unless the number passed the rule (otherwise the function throws). **Approval is a database state, not a property of this object:** the library cannot tell an approved rule from a draft, so the caller MUST load only rules the database marks `status = 'approved'` and effective (the field `status` here is the evidence label `verified`/`unverified`, not the DB approval `status`; map carefully), and the database refuses any rule id it does not hold as approved. `INITIAL_IN_BANK_ACCOUNT_RULE` (9 to 18 digits, `unverified`, no source) is the owner's initial value for the configuration that supplies rules; it is typed `Omit<AccountFormatRule, 'ruleId'>` and has no id, so it is not an `AccountFormatRule`, cannot be passed to `fingerprintAccount`, and is never treated as approved. The result also carries `ruleStatus`, so the registry can see that the format has no source on file; whether an `unverified` rule may be used in production is the registry's policy, not this module's (**owner to decide**). The rule id is not part of the fingerprint (the same account is the same account under any rule version).
- Normalisation: trim; IFSC upper-cased and must match `^[A-Z]{4}0[A-Z0-9]{6}$`; the account number must be ASCII digits only, within the rule's range, after trimming (internal spaces/hyphens are REJECTED, leading zeros are significant). Anything else throws `AccountFingerprintError` with `.reason` `invalid_ifsc | invalid_account_number | invalid_key | invalid_rule` (a bad or missing `ruleId` is `invalid_rule`) and a fixed message; no input value is ever included (tests assert it).
- `fingerprintsEqual(a, b)`: constant time, false unless both are 64 lowercase hex characters.
- `loadFingerprintKey(keyManager, wrappedBlob, keyVersion, context?)`: the key lives as an `EncryptedBlob` produced by the existing `KeyManager` (`key-management.ts`; the port has no export/HMAC operation and was not changed). The helper decrypts it and returns `{keyId: blob.keyRef, keyVersion, key}`. **`keyVersion` is the version of the fingerprint key, supplied by the caller from wherever the wrapped key is recorded; it is NOT the key manager's master-key version** (`blob.keyVersion`), which changes when the same key is re-wrapped under a new master key and would otherwise change fingerprints' version without changing the fingerprints. The version is also bound into the encryption context (`fingerprint_key_version`), so a blob wrapped for version 2 cannot be loaded as version 1; wrap with the same context (default `{purpose:'account-fingerprint'}` plus that entry). This stream generates, rotates and stores NO key; provisioning the production fingerprint key (and a production `KeyManager`, KMS Mumbai) is a separate authorised step.

## Owner answers of 14 October 2026 as implemented behaviour

1. **Account-number length is configuration, unverified.** `AccountFormatRule` is caller-supplied data with `ruleId`, `country`, `accountType`, a digit range and the evidence `status`. There is no built-in range; no valid rule means `invalid_rule` and nothing is fingerprinted. 9 to 18 is `INITIAL_IN_BANK_ACCOUNT_RULE`: `unverified`, no id, never approved by the library. The result attests `formatRuleId` and `formatValidated: true` for `payments.register_account`, which accepts only an approved, effective rule.
2. **Unknown webhook kinds are verified-and-ignored.** A verified, fresh delivery with an unsupported `object_kind` is `outcome: 'verified'` with `objectKind: 'unsupported'`, status `unmapped`, rank 0 and no amount; it changes no state. A failed verification is `unverified` (the separate receipts store). `invalid/unsupported_event` is only for a body with no usable kind word.
3. **Import files with errors are all-or-nothing.** `parseLmsImportFile` returns `rows: []` and `importable: false` if any blocking error exists; the whole file is validated first. `summariseImportFailure` produces the value-free audit record (hash, size, record count, per-row codes and field names). The single-transaction commit is the API and database side.
