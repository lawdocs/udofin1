# Phase 08a notes: stream PORTS AND MOCKS (TypeScript adapters)

All code is in `packages/adapters/src/` and exported from `@udofin/adapters` (`index.ts`). Nothing here touches the network, the database or the clock (except where `now` is defaulted, stated below). Read the code; this note is the map. Vitest: `pnpm --filter @udofin/adapters test`.

Common conventions

- Money is `bigint` paise in TypeScript; decimal rupee strings on the wire, parsed only by `parseMoneyMinor`. A test (`money.test.ts`, "no floating point on money") fails if any new module uses `Number(`, `parseFloat`, `toFixed` or `Math.round/ceil/trunc`.
- Every outcome is explicit: `ok | unknown | rejected/invalid | not_found | unsupported | not_configured`. `unknown` (timeout/network) is never an empty result and never a refusal: look up before retrying.
- Errors and result reasons are classes. They never contain input values (account numbers, cell contents, amounts, secrets).
- Placeholders keep `mode: 'production'` but their key ends `_not_configured`; `satisfiesProductionGate()` is false for them, for every mock and for every sandbox.
- All mocks call `assertLocalOrTestOnly` (new, `provider.ts`): `assertProviderAllowed` (refuses mock in production) plus an explicit staging refusal for `mode: 'mock'` with the message `the <name> is for local development and tests only`. `production` -> `ProviderNotAllowedError`.

## lms.ts (spec 08 section 6.1)

Port `LmsPort` (read-only; there is deliberately no write method): `descriptor`, `capabilities {pull, push, foreclosureQuote, statement, closureDocuments, receipts}`, `listChanges(ctx, cursor)`, `fetchLoan`, `fetchSchedule`, `fetchReceipts(ctx, ref, sinceCursor)`, `requestForeclosureQuote(ctx, ref, asOfDate)`, `fetchStatement(ctx, ref, {from,to})`, `fetchClosureDocuments`. `ctx` is `ProviderCallContext`.

`LmsResult<T>`: `{outcome:'ok', value} | {outcome:'unknown', reason:'timeout'|'network'|'provider_error'} | {outcome:'not_found'} | {outcome:'invalid', reason:'malformed_report'} | {outcome:'unsupported'} | {outcome:'not_configured'}`.

Every report carries `LmsReportMeta`: `sourceSystem`, `sourceRecordId`, `reportedAt` (UTC ISO-8601 with milliseconds; the lender's "as of", not our receipt time), `sequence: number | null`, `contentSha256` (hex).

- `contentSha256 = sha256(JSON(["udofin-lms-<type>-v1", [key, value], ...]))` in the fixed key order of each normaliser; bigint as decimal string, absent as `null`. It INCLUDES `source_record_id`, `reported_at` and `sequence` (an unchanged balance reported later is a new fact and refreshes staleness) and EXCLUDES `sourceSystem`. Identical content from `file_import` and `manual_import` hashes the same. A DB unique on `(loan, content_sha256)` therefore dedupes exact re-sends only.
- `LmsLoanReport` (`reportType:'loan'`): `lmsLoanRef, borrowerRef (opaque), status ('active'|'closed'|'foreclosed'|'written_off'|'cancelled' = servicing.loan_status), sanctionedMinor, disbursedMinor|null, disbursementRef|null, disbursedOn|null, outstandingPrincipalMinor|null, nextDueOn|null, nextDueMinor|null, overduePrincipalMinor|null, overdueInterestMinor|null, penalChargesMinor|null, otherChargesMinor|null, totalOverdueMinor|null, daysPastDue|null (as reported), flags[]`. Flag `overdue_total_mismatch` is set when all four parts and the total are present and the parts do not sum to the total (flag, never fix). Disbursement evidence is all-or-none and `disbursed <= sanctioned` (mirrors the table checks); next due date and amount are both-or-neither.
- `LmsScheduleReport` (`'schedule'`): `lmsLoanRef, installments[{sequence, dueOn, principalMinor, interestMinor, feesMinor}]` (seq 1..n, strictly increasing dates, fees default 0).
- `LmsReceiptReport` (`'receipt'`): `receiptKind 'receipt'|'reversal', lmsLoanRef, lmsReceiptRef, reversesReceiptRef|null, amountMinor (> 0 also for reversals), valueDate, paymentMode|null, bankReference|null`.
- `LmsQuote` (`'quote'`): `lmsLoanRef, lenderQuoteRef, amountMinor, components[{kind (lender's label), amountMinor}], asOfDate, validUntil` (`validUntil > reportedAt`, else rejected). Udofin adds nothing up.
- `LmsDocumentRef` (`'document'`): `documentKind 'statement'|'no_dues_certificate'|'closure_letter', lenderDocumentRef, mediaType 'application/pdf', documentSha256, periodFrom|null, periodTo|null`. References only; bytes are fetched elsewhere (production document store blocked).
- `LmsChangePage {changes[{lmsLoanRef, sourceRecordId, reportedAt}], nextCursor, hasMore}`, `LmsReceiptPage {receipts, nextCursor, hasMore}`.
- Normalisers (shared by the mock, the file import and any future connector): `normaliseLmsLoan / Receipt / Schedule / Quote(raw, {sourceSystem, now?, rowNumber?})` -> `{ok:true, report} | {ok:false, errors}`. `sourceSystem` must match `^[a-z][a-z0-9_]{1,49}$` (throws otherwise). `now` defaults to the real clock and is used only to refuse `reported_as_of` more than 15 minutes in the future.
- Gotcha for the database stream: `servicing.source_system` enum currently has `finbyx, lender_lms, manual_import`. The importer emits `file_import` or `manual_import` (spec: file import is a distinct `lms_connections.kind`). Map or extend the enum; do not coerce silently.
- `createUnconfiguredLmsPort()` (`lms_not_configured`, all capabilities false, every call `not_configured`). `withLmsTimeout(port, ms)`.

### Import file format v1 (`udofin-lms-import-v1`, also documented in the header of `lms.ts`)

`parseLmsImportFile(text, {format:'csv'|'json', kind:'loan'|'receipt'|'schedule', sourceSystem:'file_import'|'manual_import', maxBytes?, maxRows?, now?})` -> `{kind, formatVersion, fileSha256, recordCount, rows[], errors[]}`. Pure. `fileSha256` identifies the import batch. Defaults: 5 MiB, 10 000 records.

- CSV: header row of exact snake_case names, UTF-8 (BOM ignored), RFC 4180 quoting; unknown/duplicate header names and missing required columns are file-level errors; a row with the wrong cell count is `column_count_mismatch`. Nothing is trimmed or repaired. Cells starting with `=`, `+`, `-`, `@` are ordinary text (and are refused by the field rules); error rows never contain cell values.
- JSON: an array of records, or `{"format_version":"udofin-lms-import-v1","records":[...]}`. Money must be a JSON string (a JSON number is `invalid_amount`); `sequence` and `days_past_due` may be integers or strings. Unknown keys (including `__proto__`) -> `unknown_field`.
- Loan columns: required `lms_loan_ref, borrower_ref, status, sanctioned_amount, source_record_id, reported_as_of`; optional `disbursed_amount, disbursement_ref, disbursement_date` (all three or none), `outstanding_principal, next_due_date, next_due_amount` (both or neither), `overdue_principal, overdue_interest, penal_charges, other_charges, total_overdue, days_past_due, sequence`.
- Receipt columns: required `lms_loan_ref, lms_receipt_ref, receipt_kind (receipt|reversal), amount, value_date, source_record_id, reported_as_of`; optional `reverses_receipt_ref` (required for a reversal, forbidden for a receipt, not equal to its own ref), `payment_mode, bank_reference, sequence`.
- Schedule columns (CSV: one row per installment, head fields must agree across rows of one report; JSON: an `installments` array of `{installment_seq, due_date, principal, interest, fees?}`): `lms_loan_ref, source_record_id, reported_as_of, sequence?` + `installment_seq, due_date, principal, interest, fees?`.
- `borrower_ref` is opaque: PAN-shaped values and 10-13 digit numbers are refused (`borrower_ref_looks_personal`), as are names, e-mails and anything outside `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,99}$`.
- Error object: `{rowNumber (1-based data row or JSON record; 0 = file-level), field|null, code, itemIndex?}`. Codes: `file_too_large, too_many_rows, empty_file, malformed_file, unknown_column, missing_column, duplicate_column, column_count_mismatch, unknown_field, missing_required, invalid_reference, borrower_ref_looks_personal, invalid_amount, amount_not_positive, invalid_date, invalid_timestamp, timestamp_in_future, invalid_integer, invalid_status, invalid_receipt_kind, incomplete_disbursement, incomplete_next_due, disbursed_exceeds_sanctioned, reversal_reference_invalid, invalid_items, inconsistent_report_head, invalid_validity, duplicate_row, conflicting_duplicate`.
- Duplicates inside a file: loan/schedule key `(lms_loan_ref, source_record_id)`, receipt key `lms_receipt_ref`. Identical content: first kept, later ones reported `duplicate_row` (informational). Different content: every occurrence rejected `conflicting_duplicate`. Good rows are returned even when others fail; the caller decides whether a file with any error may be imported (recommendation: show all errors and import nothing until the file is clean, but that is policy).

## payments.ts (spec 08 sections 7, 9, 20)

- `NormalisedProviderEvent {provider, deliveryId, eventId, objectKind: 'payment'|'refund'|'chargeback'|'mandate'|'debit'|'settlement', objectRef, orderRef?, status, rank, amountMinor: bigint|null, currency: 'INR'|null, occurredAt, settlementRef?, merchantRef?}`. `merchantRef` is added (not in the original list) so a wrong-merchant event can be compared with the lender's configuration upstream.
- `PLATFORM_EVENT_STATUSES`: `created, pending, authorized, captured, paid, succeeded, failed, refunded, disputed, cancelled, expired, active, rejected, returned, revoked, paused, unmapped`. `PAYMENT_SUCCESS_STATUSES = captured, paid, succeeded` (equals `private.payment_success_statuses()`; keep them in step). Unknown provider words map to `unmapped`, which authorises nothing.
- `defaultEventRank(status)`: unmapped 0, created 10, pending 15, authorized 20, failed/rejected 25, captured/paid/succeeded/active 30, paused 35, returned/refunded 40, cancelled/revoked/expired 45, disputed 50. Rank is per object; the database applies "lower rank after higher = `ignored_stale`". Note `active` (30) outranks `rejected` (25) on purpose: a rejection after activation must never revert the mandate, but should be raised as a reconciliation item rather than silently dropped (database stream to decide).
- `WebhookVerifier {scheme, verify(rawBody: Uint8Array, headers, {secret, now?, toleranceSeconds? = 300})}` -> `WebhookVerification`:
  - `{outcome:'verified', event, payloadSha256}`
  - `{outcome:'unverified', reason:'missing_headers'|'malformed_headers'|'no_secret'|'signature_mismatch', payloadSha256}`
  - `{outcome:'stale_timestamp', reason:'timestamp_outside_tolerance', payloadSha256}` (only for an AUTHENTIC signature: a forged stale delivery is just `unverified`)
  - `{outcome:'invalid', reason:'provider_scheme_not_configured'|'body_too_large'|'malformed_body'|'unsupported_event'|'invalid_amount'|'unsupported_currency'|'invalid_timestamp'|'invalid_identifier', payloadSha256}`
    `payloadSha256` is always present (hash of the raw body, for `payments.webhook_receipts`). The verifier needs the lender's webhook secret from the caller; it holds none. Replay (`private.mark_webhook_seen`), duplicate/unmatched, merchant and amount business checks are upstream. Deviation from spec section 9 item 5: an authentic delivery with an unknown `object_kind` is `invalid/unsupported_event` (not "verified-and-ignored"); an unknown status is verified as `unmapped`. Change if the owner prefers.
- `PaymentProviderPort {descriptor, capabilities {orderCreation, statusLookup, settlementReports, partialAmounts, webhooks}, webhookVerifier, createOrder(ctx, CreateOrderRequest), getOrderStatus(ctx, {orderRef|null, operationKey}), fetchSettlements(ctx, 'YYYY-MM-DD')}`. `PaymentResult<T>` = `ok | unknown(timeout|network) | rejected(invalid_request|unsupported_currency|provider_error) | not_found | unsupported | not_configured`.
  - `CreateOrderRequest {operationKey (= intent id, idempotency), receiptRef, merchantRef, amountMinor (>0), currency 'INR', purpose, expiresAt|null}`: no personal fields exist. `CreatedOrder {orderRef, merchantRef|null, settlementProfileRef|null, checkoutLink|null (BEARER SECRET), expiresAt}`; compare `merchantRef` with the configuration (`merchant_mismatch`).
  - `OrderStatus {source:'provider_authenticated_lookup', orderRef, status, amountMinor|null, currency, merchantRef, providerPaymentRef|null, observedAt}`: the only non-webhook evidence.
  - `SettlementReport {date, batches[{batchRef, settlementRef (UTR), periodFrom, periodTo, destinationMaskedRef|null, gross/fee/tax/net minor, items[{providerPaymentRef, orderRef, gross/fee/tax/net minor}]}]}`.
- `createUnconfiguredPaymentProvider()`: key `payment_provider_not_configured`, mode `production`, all capabilities false, every call `not_configured`, `webhookVerifier.verify` -> `invalid/provider_scheme_not_configured` (the receiver should answer 503 for that provider). No real provider scheme is written.
- Mock scheme `MOCK_PAYMENT_WEBHOOK_SCHEME = 'mock-standard-webhooks-v1'`: headers `webhook-id`, `webhook-timestamp` (epoch seconds), `webhook-signature` (`v1,<base64>`, space-separated list allowed); HMAC-SHA256 with the secret as UTF-8 over `<id>.<timestamp>.` + raw body bytes; constant-time compare; header names case-insensitive. Body: JSON with string fields `event_id, object_kind, object_ref, status, occurred_at` and optional `order_ref, amount (decimal string), currency, settlement_ref, merchant_ref`. Only reachable through `createMockPaymentProvider(...).webhookVerifier` (guarded). Helpers: `signMockWebhook({secret, deliveryId, timestampSeconds, rawBody})`, `buildMockWebhookBody(fields)`, `buildMockDeliveries(scenario, {secret, orderRef, paymentRef, amountMinor, merchantRef, now, idPrefix?})` -> `MockDelivery[] {label, rawBody, headers}` (complete signed deliveries for a receiver test).
- `createMockPaymentProvider(env, {scenario?, settlementDestinationMaskedRef?})`, key `mock_payment_provider`. Scenarios: `success, failure, delayed, duplicate_event, out_of_order_refund_first, out_of_order_failed_after_captured, partial_amount, wrong_currency, wrong_merchant, refund, chargeback, unknown_outcome, bad_signature, old_timestamp`. ## account-fingerprint.ts (spec 08 section 7.1)

- `fingerprintAccount(key: FingerprintKey, {ifsc, accountNumber}) -> {fingerprint (64 hex), keyVersion, maskedRef}`. `FingerprintKey = {keyId, keyVersion (int >= 1), key: Uint8Array (>= 32 bytes)}` (the task text named `{keyId, key}`; `keyVersion` is added so the version is recorded with the fingerprint). Encoding: HMAC-SHA256 over 4-byte-big-endian-length-prefixed UTF-8 parts `["udofin-account-fingerprint-v1", ifsc, accountNumber]`. `maskedRef = 'XXXXXX' + last 4 digits` (matches the `masked_account_ref` check `^[X*]{2,}[0-9]{2,4}$`).
- Normalisation: trim; IFSC upper-cased and must match `^[A-Z]{4}0[A-Z0-9]{6}$`; account number must be 9-18 ASCII digits after trimming (internal spaces/hyphens are REJECTED, leading zeros are significant). Anything else throws `AccountFingerprintError` with `.reason` `invalid_ifsc | invalid_account_number | invalid_key` and a fixed message; no input value is ever included (tests assert it).
- `fingerprintsEqual(a, b)`: constant time, false unless both are 64 lowercase hex characters.
- `loadFingerprintKey(keyManager, wrappedBlob, context?)`: the key lives as an `EncryptedBlob` produced by the existing `KeyManager` (`key-management.ts`; the port has no export/HMAC operation and was not changed, because it is outside this stream's files). The helper decrypts it and returns `{keyId: blob.keyRef, keyVersion: blob.keyVersion, key}`. Default context `{purpose:'account-fingerprint'}` must match the one used to wrap it. This stream generates, rotates and stores NO key; provisioning the production fingerprint key (and a production `KeyManager`, KMS Mumbai) is a separate authorised step. Open question for the owner: the 9-18 digit rule is a general Indian-bank convention, not a text on file.
