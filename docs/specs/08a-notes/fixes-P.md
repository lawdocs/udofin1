## A35: why not "bind the banner to loaded data"

The brief suggested showing a banner only when it is true of loaded data. That works for one banner (the "just registered"
entry is read back from the API) but not for the others: "Your action was recorded" and the counts of a bank-credit upload
have no loaded object to be checked against. Leaving them out would remove the confirmation of a real save. The finding's own
suggested fix (a flash cookie set by the server action) is what is implemented: a link cannot set a cookie in the reader's
browser, so a notice that arrives this way was written by this portal, for this page, seconds ago.

Limits, stated plainly:

- A page cannot delete a cookie while it renders, so the notice is "cleared" by time (20 seconds) and by path (it is shown on the
  page it was written for only). A reload within 20 seconds shows it again. It is still true.
- If cookies are blocked the success banner is simply not shown; the page itself shows the new state.
- The error banner (`?error=<code>`) is unchanged. It is mapped to a fixed sentence and can only claim that something failed.

## Real browser check (not committed)

The built lender portal (production build of this branch) was started with a fake sign-in server and a fake API written for the check (the same approach as
`tests/e2e`, which was not changed). 24 checks passed, 0 failed, in Chromium, among them:

- a person in two lenders, only the second with a policy: the first lender's page says no policy has been set, the form is empty
  and for the first lender, the API was asked with `lenderId=<first lender>`, never the unfiltered list; choosing the second
  lender shows its 4,321 minutes; saving for the first lender sends the first lender and comes back to it;
- the bank-credit upload offers only the acted-for lender's account;
- a real save and a real upload show their confirmation and counts once; the address carries no `done`, `inserted` or `duplicates`;
  the cookie is HttpOnly, SameSite=Strict and lasts 20 seconds; the confirmation is not shown on another page and is gone after 20 s;
- `?done=1`, `?done=1&inserted=2000&duplicates=0` show nothing; a forged `?error=` shows only the fixed sentence.

## Owner decisions and things not changed

- **Earlier pages with the same pattern.** The onboarding, products, transactions and applications pages of both portals (before
  Phase 08a) still read `done=1` from the address (`apps/*/app/onboarding/actions.ts` and nine pages). They were not part of the
  finding. The same mechanism (`rememberSuccess` / `successNotice` in `apps/*/lib/flash.ts`) would fix them.
- **Other lists stay across lenders.** The payments, mandates, debits, settlement and exception lists of the lender portal still
  list rows of every lender the person belongs to (each row carries its lender); only the policy and settings pages, the run list
  and the bank-credit accounts were narrowed to one lender, as the finding asked.
- **Timeout.** The portal waits 60 s for an apply or a document registration. `api-lender-servicing.md` says the API allows
  its apply under a 120 s statement timeout, so a very large file can still outlast the portal; the person is then told the result
  is unknown and to reload, not that the service could not be reached.
- **A33 contract and SQL.** `SettlementAccountRequestInput` (contracts) and `payments.request_settlement_account` (SQL) need the
  same rule from their owners; until then a caller that skips the portal is still only stopped by the six-digit run.
