## 2. What the tests prove

- `029` runs 283 assertions. Against a database built WITHOUT the migration (all other migrations), the same file fails (131) or errors (17) on 148 of its 283 assertions: every assertion of a corrected behaviour. The other 135 pass there: guards that already existed (M20, M21), controls, setup, and the "no error" half of a replay (whose result assertion fails). Run with `psql -v ON_ERROR_ROLLBACK=on` to see which.
- 17 mutations of existing guards (M20 a to g, M21 a to d) were each applied inside a rolled-back transaction while the whole file ran; each fails the named assertions (script and result in the report).
- The A7 race was exercised with two real sessions (session A holds its confirmation open for 4 seconds): WITH the migration the second session waits about 3 seconds and gets `already_confirmed` (55000); WITHOUT it, `task_final` (P0001, an unmapped trigger error that the API turns into a 500).

## 4. Decisions, declines and residual risk

1. Owner decision (M8, optional part): a lender conflict can still be acknowledged and resolved by the same person. Requiring resolver different from acknowledger would break the one-operator lender; not done.
2. Owner decision (M15): the 31-day maximum validity is a constant in `record_foreclosure_quote` and the `validity_bound` check; staleness is tested on receipts, on a later report showing the loan not active, and on a later report with LESS principal outstanding than the quotation counted. Both are conservative: a stale quotation simply asks the borrower to request a new one.
3. Declined (U38, second half): `import_rows.source_record_id_sha256` stays an unsalted SHA-256. Nothing reads it; salting with the batch id is no defence (the id is stored beside it) and only a keyed hash would be, which needs a key the database does not have. Residual risk exists only if a lender uses a mobile number as its record id. Recommended: drop the column for discarded batches or key it with a vault secret (owner decision).
4. Mutation results (script `mutate.py`, run against the final migration): M20a CAUGHT (2 assertions), M20b (1), M20c (2), M20d1 (2), M20d2 (3), M20d3 (2), M20e (2), M20f (4), M20g (5), M21a1 (2), M21a2 (2), M21a3 (1), M21a4 (2), M21b (2), M21c (1), M21d1 (1), M21d2 (1).
5. Bank references: the personal-shape test cannot tell a 9 to 12 digit account number from a 12-digit UPI RRN or an IMPS reference, so those pass; 13 to 18 digit numbers and 10-digit mobile numbers are refused. A bank reference that is exactly a 10-digit number starting 6 to 9 is refused and the lender must prefix it.
6. The text screen refuses a few ordinary texts: a date with separators and a time (`12/10/2026 15:30`) reads as a 12-digit number, and two words glued by a full stop (`closed.please`) read as a domain. The lender rewrites the sentence. The screen is defence in depth, not a personal-data scanner (a name cannot be recognised by shape).
7. `closure_letter` then `noc`: the NOC replaces the closure letter as the closure's pointer even without a supersession link, because the pointer is named for the NOC. A second NOC, or a later closure letter, that corrects nothing does not take it.
8. The new `validity_bound` check is NOT VALID (it governs new rows; rows written before it are not re-tested). The decline-note and delay-reason screens moved from table checks to a trigger that looks only at new or changed text, so a row written before the stricter screen can still be confirmed or closed (tested).
9. `apply_lms_report` now writes an audit event per stored, conflicting or quarantined report. With a real machine feed this is one event per changed report; if volume matters, the owner may want a sampled or batched audit.
10. API integration files run against a database built from this worktree (`servicing`, `lender-servicing`, `payments`, `periodic-jobs`, `lender-reminders`, `payments-worker`, `lender-payments`, `provider-callbacks`, `documents`, `lender-accounts`): 520 tests, 518 pass; the two failures are items 3 and 4 above and assert the old behaviour.
