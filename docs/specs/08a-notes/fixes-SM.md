`creditor_not_lender` in `request_mandate` cannot be reached with real data: `validate_collection_target_impl` refuses a merchant of another organisation first (`collection_target_invalid`). The refusal is tested; the branch itself stays as defence in depth.

## Changes to the existing mandate test (021)

- `pg_temp.at(m)` steps in 20 seconds instead of minutes: events dated half an hour ahead are now replaced by the clock (U6).
- The planner result has two more counters (`cancelled_paid`, `cancelled_restated`); the two exact comparisons subtract them.
- The "installment due before the reported next due date" fixture asserted the old behaviour (it planned an installment the lender's report showed as paid); it now adds a newer lender report that names the installment as the next one due.

## Needs from other areas

1. `supabase/tests/023_p08a_api_reads.test.sql` (SP), test 142, line 671: `my_mandate_debits` on a live mandate with the lender's switch off now answers (U9). Expected result `'ok'`, text "with the lender's mandates switch off a live mandate stays readable". Everything else in 023 passes.
2. `services/api/test/integration/payments.integration.test.ts` (API builder), two tests assert behaviour that is now corrected: (a) "lists the debits with the notice state..." (about line 2699) expects a next debit on `state.active`, a mandate whose cancellation was requested earlier in the file; it must expect no next debit there (A52, M45), or use a mandate without a request; (b) "a lender whose mandates switch goes off hides every mandate route..." (about line 2706) must expect the live mandate to stay in the list and readable with its debits, while a finished mandate is hidden and `/v1/loans/:id/mandate-options` stays 404 (U9). All other integration files that touch mandates pass (counts in the report).
3. `payments.take_handoff_link` / `payments.store_handoff_link` (SP): refuse the authorisation link of a mandate with `cancel_requested_at` set (A51: the borrower can still authorise a mandate they asked to cancel).
4. `payments.ingest_provider_delivery` (SP): an `amountMinor` above 1e14 (up to 15 digits) raises 23514 and the callback fails; it should be an invalid receipt (U7). A verified mandate event rejected because the configuration is suspended leaves only a receipt; a platform exception would stop a lost revoke being silent (U2). Optional: a unique `(id, lender_org_id)` on `provider_events` would let the two triggers of U8 become composite keys.
5. `services/api/src/workers/payments-handlers.ts` `cancelMandate` (API builder): it ignores a mandate that is no longer live. Now that a late provider reference is stored for a finished mandate that had a cancellation request, and the cancellation is queued again, the handler should send it when `cancel_requested_at` is set, `cancel_sent_at` is null and a reference exists, whatever the status.
6. `services/api/src/workers/periodic-jobs.ts` (API builder): the notice claim can stay as it is (every claimed notice is now claimable), but looping until a call returns 0 rows is cheap insurance (A22).
7. New hints: none. Constraint errors 23503 and 23514 from the new triggers can only come from a mandate function bug, never from a request.

## Risks noticed, not fixed

- The mandate lookup list is filtered by the lender's switch in `jobs.ts`, so the new periodic lookup does not run for a lender whose switch is off.
- A fresh report that alternately names and does not name an installment can replace its planned debit (and send a new notice) more than once; only the lender's own figure changes cause it.
- The sweep re-queues a cancellation at most 48 times; after that the 24-hour `mandate_cancel_unconfirmed` exception is the only signal.
