## 0. What this is, in one paragraph

The lender's LMS stays the system of record. This stream stores **what the lender reported**, append-only, with provenance (lender, source system, import batch, source record id, `reported_as_of` = lender time, `received_at` = our time, content hash, the recording person), and shows it back. Udofin computes nothing: no balance, interest, charge, days past due or foreclosure amount. Everything arrives through one private implementation (`private.servicing_apply_one`), reached by `servicing.apply_lms_report` (system, one report) and by `servicing.commit_import` (a lender user, a whole file). Imports are **all or nothing** (owner decision 10). No real LMS connector exists; `finbyx` and `generic_rest` rows can only be `blocked_unverified`.

## 3. Rules of `apply` (both entry points run the same code)

- **Idempotent** on `(loan, content_sha256)` and on the lender's sequence; the same receipt (same lender receipt ref and same figures) is `unchanged` however often and however late it is re-sent.
- **Loan creation** only when the application is found and ready and the disbursement evidence is complete: otherwise quarantine with a reason. `borrower_ref` must be the **Udofin application id (uuid)** or the **lender's application reference** (`lending.applications.lender_reference` or `lending.application_routing.lender_application_ref`) of the SAME lender. A lender-customer reference cannot be matched and is quarantined `application_not_found`; another lender's application looks exactly like a missing one. Ready = `agreement_executed`, `disbursement_pending` or `disbursed`. Disbursement date in the future (IST date) is quarantined.
- **Existing loan**: `borrower_ref` must still resolve to the loan's own application, else `borrower_ref_mismatch` (nothing stored against that loan).
- **Older `reported_as_of`, or a lower sequence at a later time**: not stored, flagged `older_report_ignored` / `older_sequence_ignored` (info), counted (`count_ignored_older`, `applied_counts.ignored_older`).
- **Conflict** (queued, nothing applied): same source record id with other content at the same or an older time (`same_record_different_content`), another record id at exactly the newest `reported_as_of` (`same_time_different_content`), a sequence number already used with other content (`sequence_reused`), a receipt ref re-sent with other figures (`receipt_differs`), the same for schedules.
- **Anomalies** (stored as reported, flagged, never corrected): status moving backwards (a non-active status reported `active` again: `status_regression`), terminal to another status, outstanding principal rising without a higher reported penal or other charge, parts not adding to the stated total (also kept in `balance_snapshots.flags`), changed sanctioned amount or disbursement evidence, reversals exceeding their receipt. **The loan account follows the lender forward only** (active to a terminal status); a terminal status is never reopened by a report; a changed sanctioned amount is applied only if it still covers the recorded disbursement (the change is in `loan_account_events` and flagged); disbursement evidence is never rewritten. A lender correction after closure is still a new snapshot.
- Receipts: positive amounts; a reversal must name a receipt (not a reversal) of the same loan, else `reversal_target_unknown`. A reversal may name a receipt of the same file in any order.
- Dry runs (staging) use exactly the same code with a flag and write nothing.

## 4. Record format accepted by `stage_import` / `apply_lms_report` and how it maps from `packages/adapters`

`p_rows` is a JSON array of **import records of format `udofin-lms-import-v1`**: snake_case keys exactly as documented in the header of `packages/adapters/src/lms.ts`, every value a JSON string (money as decimal rupees `"1250.50"`; `days_past_due` and `sequence` may be integers or strings; timestamps ISO-8601 with zone; dates `YYYY-MM-DD`). Empty strings and nulls mean "absent". Unknown keys are `unknown_field` (the key is never echoed). `apply_lms_report` additionally takes `report_type` (loan / receipt / schedule), `source_system` and optionally `content_sha256` (verified against the recomputed hash, mismatch = error result). Schedule records carry `installments: [{installment_seq, due_date, principal, interest, fees?}]`.

`parseLmsImportFile` returns NORMALISED reports (camelCase, `bigint`), and nothing but errors when the file is not importable. To call the database the API must send RAW records (the parsed `raw` objects) or map reports back with `formatMoneyMinor`: `lmsLoanRef` -> `lms_loan_ref`, `borrowerRef` -> `borrower_ref`, `sanctionedMinor` -> `sanctioned_amount`, `disbursedMinor` / `disbursementRef` / `disbursedOn` -> `disbursed_amount` / `disbursement_ref` / `disbursement_date`, `outstandingPrincipalMinor` -> `outstanding_principal`, `nextDueOn` / `nextDueMinor` -> `next_due_date` / `next_due_amount`, `overduePrincipalMinor`, `overdueInterestMinor`, `penalChargesMinor`, `otherChargesMinor`, `totalOverdueMinor` -> `overdue_principal`, `overdue_interest`, `penal_charges`, `other_charges`, `total_overdue`, `daysPastDue` -> `days_past_due`, `sourceRecordId` -> `source_record_id`, `reportedAt` -> `reported_as_of`, `sequence`. The database validates everything again (it never trusts the API), so the API's own parse is for fast feedback. `file_sha256` and `byte_size` are the TypeScript importer's `fileSha256` and byte length; the database cannot verify them against the records.

**The SQL content hash equals the TypeScript `contentSha256`** for the same record (`lmsReportHash`: `sha256(JSON(["udofin-lms-<type>-v1", [key, value], ...]))`, bigint as paise decimal string, absent as `null`, includes `source_record_id`, `reported_as_of`, `sequence`, excludes the source system). Verified by running the TypeScript normalisers on five vectors (loan with all optionals, loan with absent optionals / one-digit fraction / zone offset, receipt, reversal with integer sequence, schedule with defaulted fees); the same five hashes are hard-coded in pgTAP section 2. A TypeScript test asserting the same five hashes would make the guard mutual (deferred, not my files).

Differences from the TypeScript rules (all stricter, never looser): zone offsets beyond +-15:59 are refused (real offsets stop at +14:00); everything else (reference charset, PAN/phone-shaped `borrower_ref`, limits 999999999 / 99999 / 600, strictly increasing due dates, date years 2000 to 2100) is identical. Names inside `source_record_id`, `bank_reference`, `payment_mode` or `disbursement_ref` cannot be recognised by shape (same as TypeScript): keeping personal data out of the file is the lender's responsibility and belongs in the file specification.

**`stage_import` / `commit_import` / `reject_import` result** (jsonb): `batch_id, lender_org_id, status, existing, kind, source_kind, row_count, counts {new, unchanged, duplicate, changed, conflict, error, quarantined, ignored_older}, resubmission_of, errors [{row_no, outcome, error_codes[], field_names[]}] (at most 1000, `errors_truncated`), applied_counts, failure_class`. Row outcomes: `new` / `changed` / `unchanged` (also older-ignored, flagged) / `duplicate` (identical repeat inside the file, applied once) / `conflict` (queued at commit, does NOT invalidate the file) / `error` and `quarantined` (invalidate the file). Error codes: the TypeScript list (`unknown_field, missing_required, invalid_reference, borrower_ref_looks_personal, invalid_amount, amount_not_positive, invalid_date, invalid_timestamp, timestamp_in_future, invalid_integer, invalid_status, invalid_receipt_kind, incomplete_disbursement, incomplete_next_due, disbursed_exceeds_sanctioned, reversal_reference_invalid, invalid_items, conflicting_duplicate`) plus `row_not_object, content_hash_mismatch` and the quarantine reasons above.

## 5. Borrower reads

`servicing.my_loans()` and `servicing.my_loan(p_loan)` (SECURITY DEFINER, `private.my_borrower_id()`, borrower's own loans only; lenders whose `servicing_sync` switch is off are not listed; an unknown loan, another borrower's loan and a switched-off lender all answer P0002). Columns: `loan_account_id, lender_org_id, lender_display_name, lender_loan_ref, loan_status, sanctioned_amount_minor, disbursed_amount_minor, disbursed_at` (loan facts), then `reported_status, reported_as_of, received_at, stale, stale_threshold_minutes, figures_available, outstanding_principal_minor, overdue_principal_minor, overdue_interest_minor, penal_charges_minor, other_charges_minor, total_overdue_minor, next_due_on, next_due_minor, days_past_due`. Nothing is computed: every figure is the lender's, with the lender's time.

- `figures_available = false` (status and all figures null; `reported_as_of` and `stale` still shown) when there is no report yet, when the NEWEST report carries a warning anomaly (regression, mismatch, rise without charge, changed sanctioned amount or evidence), or when a conflict about the loan REPORT (`record_type = 'loan'`) is unresolved. The borrower is not told why, and no anomaly, conflict, batch or provenance column exists in the result. The UI should say "ask <lender>" / "refresh". (Owner decision proposed: this is fail-closed; the alternative is to show the lender's figures with a notice.)
- `stale` = no report, or `now - newest reported_as_of > connection.staleness_threshold_minutes` (default 1440; 1440 also when there is no connection row). It is pure staleness: combine with `loan_status` in the UI (a closed loan is expected to stop updating).
- Borrowers read none of the tables or the status view directly (no policy), and `loan_accounts` stays as before (own rows).

## 6. Switches, permissions, guards

- `servicing_sync` (foundation) is required by every function above except the borrower and history reads (`my_loans` lists only switched-on lenders; the history functions are plain RLS reads that keep working after a kill: a switch off never hides history from the lender). `servicing.kill_feature` was exercised end to end (stage, commit, reject, acknowledge, resolve, connection, system apply all answer 55000 `feature_disabled`).
- People: `servicing.manual_entry` stages, rejects, records refused files; `servicing.sync.manage` commits, handles conflicts, writes the connection. The system role `servicing_operator` holds both plus `loan.read`; stage and commit by the same person is allowed (the audit records both events with the person). All people functions need aal2 (42501 `mfa_required`).
- Mock: a `mock` connection, and `mock_lms` reports, work only in a session with `udofin.allow_mock_providers = 'on'` (checked again at use time: 42501 `mock_provider_blocked`); a mock record never satisfies a production gate (foundation).
- `tenancy.permissions` / roles were not changed.

## 7. Gotchas for the API, worker and the next streams

- **`commit_import` returns `status: 'failed'` instead of raising** when applying fails; treat it as an error response. `stage_import` returns `status: 'invalid'` with `errors` (not an exception) for a bad file; exceptions are for permission, state and request-shape problems.
- **Performance** (measured on the development sandbox): staging costs about 1 ms per record (10 000 records about 10 s), commit about 1.8 ms per new loan (2 000 loans: 3.6 s). `udofin_api` has `statement_timeout = 30s`: the API should run these calls with `set local statement_timeout = '120s'` for large files or cap files near 5 000 records.
- Previewed batches keep row values (canonical, closed field set) until committed or rejected; there is no expiry job (deferred: a worker should reject stale previews).
- `servicing.import.committed` and `servicing.sync_conflict.opened` are written to the outbox in the same transaction (payloads: ids only). Something must consume the first to call `servicing.complete_disbursements`.
- Deadlocks between two commits touching the same loans in different order are possible in theory; the loser is recorded as `failed` (class 40P01) and nothing is applied; the lender stages again.
- `service_role` still holds the DEFAULT ALL on `servicing.loan_accounts`, `schedule_snapshots` and `schedule_installments` (existing fixtures in 002/003/004/009/013 insert as the system role, so revoking now would break files this stream does not own). Everything in the new sync path writes them through the definer functions. See `deferred` in the stream report for the exact revoke and the fixture change.
- Nothing here seeds data, accounts, fingerprints or credentials; all fixtures are labelled SAMPLE.
- To enable `servicing_sync` in a test, use the foundation recipe (an `applied` two-person request and the switch row in ONE transaction), then a connection row (`insert into servicing.lms_connections (lender_org_id, kind, status) values (..., 'file_import', 'active')` as the owner, or `servicing.set_lms_connection` as a `servicing.sync.manage` holder).
