# Phase 08a notes: stream API, borrower payments and mandates (HTTP)

Code: `services/api/src/modules/payments/routes.ts` (`paymentsRoutes({ handoff? })`, the only module file), contracts in `packages/contracts/src/http/payments.ts` (every export is prefixed `Bp` / `BP_`), tests in `services/api/test/integration/payments.integration.test.ts` (66 tests, real database). Spec: `docs/specs/08-servicing-payments-mandates-collections.md` sections 7.2, 8 and 16. Database notes: `provider-events.md`, `mandates.md`, `reconciliation.md`, `api-payments-worker.md` (the worker that creates the order and the link). Nothing in this note claims regulatory compliance: it describes what the code does and does not do.

## How the layer works

- **Every rule stays in SQL.** A route validates the shape of the request (zod, `z.strictObject` for every body, query and params), takes the caller from the token (the database resolves who the borrower is), passes ids, calls one SQL function and maps the answer. Nothing here computes an amount, derives a stage, decides an eligibility, checks a limit or re-implements a closed list (the lists in the contract only mirror the database vocabularies for clients; a test fails if one drifts).
- **Auth.** Every route is `auth: 'borrower'`. A lender or platform user (second factor passed) gets `403 borrower_only`; no token or a bad one gets `401 token_*`. Staff are not given a path into a borrower's payments.
- **Unknown, someone else's and "switched off" look the same.** Every function answers P0002 for a loan, payment or mandate that is not the caller's, that does not exist, or whose lender switch (`payments` / `mandates`) is off, and the API maps P0002 to `404 not_found` with the same body (tested: the body for another borrower's payment equals the body for an unknown one, apart from the request id). Another borrower of the SAME lender and a borrower of ANOTHER lender are both tested.
- **Responses are mapped field by field** from the columns this module chooses to read (the table-returning functions are selected with an explicit column list; the two `jsonb` answers are parsed against a schema of their shape and copied name by name). The contract objects are strict, so an undeclared field fails the response check (a 500, never a leak). Money is integer paise as a JSON number (the database returns bigint as text: a checked parse; the `jsonb` amounts are checked by the `Paise` primitive); dates `YYYY-MM-DD`; timestamps ISO 8601 with an offset. `cache-control: no-store` comes from the app and is set explicitly on the link routes.
- **What is never returned.** No provider order or mandate reference, merchant or creditor reference, payment configuration id, settlement account id, secret reference, endpoint token hash, fingerprint, ciphertext, key version, idempotency key, borrower id, phone or account number. The lender's destination appears only as its masked reference (last digits). Tested by planting canary values in those columns and scanning every response, the stored idempotent answers (`ops.idempotency_keys`) and the captured request log.
- **Idempotency.** Every POST requires `Idempotency-Key` (the framework: letters, digits `. _ : -`, 16 to 128 characters; stored per caller and route; a replay answers `idempotent-replayed: true`; the same key with another request is `422 idempotency_key_reused`). `POST /v1/loans/{id}/payments` ALSO passes the header value to `payments.request_payment` as its idempotency key (scoped to the lender in SQL), and `POST /v1/loans/{id}/mandates` relies on the mandate id the app chose. When the framework's stored answer is gone (its retention is 24 hours) the database repeats the decision: the same content returns the same payment or mandate, other content is `409 idempotency_conflict` (both layers tested).
- **The order is not awaited.** See "Deviations" below.

Notes on the wire shapes:

- **Payment options** (`BpPaymentOptions`): `purposes` is a discriminated union on `purpose`: `installment` (`amountMinor` = the lender's reported next installment, `dueOn`, `minMinor`, `maxMinor`), `overdue` (`amountMinor` = the lender's reported total overdue), `part_prepayment` (`minMinor` and `maxMinor` only: the borrower chooses within the lender's limits) and `foreclosure` (`amountMinor` = the unexpired lender quotation, `quoteId`, `validUntil`, `flagged`). `penalCharge` is the lender's APPROVED sentence or null, `penalChargeTextMissing` says an overdue figure is shown with no approved sentence (the app shows nothing in its place). Nothing is offered when the figures are missing, withheld or stale (`figuresAvailable`, `stale`) or the collection target is not valid (`available: false`, `unavailableKey`).
- **Payment detail** (`BpPaymentDetail`): `status` is the request's own state (`created`, `pending`, `succeeded`, `failed`, `expired`, `cancelled`); `stage` is the database's honest stage (`started`, `provider_received`, `lender_posted`, `needs_attention`) taken as given. `linkAvailable` is true while an unexpired link can be fetched; `cancellable` only while `created`. The destination is `destinationMaskedRef`.
- **Mandate** (`BpMandate`): `status` is exactly what the provider-confirmed history last left; a draft or `registration_pending` mandate is never shown as active. `cancelRequested` is true after a cancellation request; the status does not change until the provider confirms. `nextDebit*` is the next planned debit, if any.
- **Debits** (`BpMandateDebitList`): at most 60, newest scheduled date first (the function's order). A debit has `planned`, an optional `amountMinor`, the provider's own `returnCode` and its `returnClass` (only when the lender's configuration classified the code), and its pre-debit `notice` (`status`, `dueAt`, `sentAt`) or null. The provider's debit reference is not returned.

## The flow the app follows

Payment: `GET payment-options` then `POST payments` (201, status `created`, no link yet) then poll `GET payments/{id}` until `linkAvailable` is true (the worker creates the order after the request commits) then `GET payments/{id}/link` and open the link at the provider. The app shows "payment started", "received by the payment provider" (`provider_received`) and "posted by the lender" (`lender_posted`) from `stage` only; it never shows "paid" from a redirect.

Mandate: `GET mandate-options`, the app picks a `mandateId`, asks `POST /v1/stepup/challenges {action: 'mandate_creation', contextRef: <mandateId>}` and verifies the code (`POST /v1/stepup/challenges/{id}/verify`), then `POST /v1/loans/{id}/mandates` (201, status `draft`; the code is spent only when the mandate is created), then polls `GET mandates/{id}` until `registration_pending`, then `GET mandates/{id}/link` and opens the link at the provider. The mandate is `active` only when the provider says so (a verified event or an authenticated lookup).

## Hand-off links

`GET .../link` first checks that a keyring is configured (no keyring: `503 handoff_unavailable`, and no read is counted), then calls `payments.take_handoff_link(kind, id)` (every read is counted in the database), then opens the ciphertext with `openHandoffLink` using the kind, the subject id from the path and the lender id the function returned. The link is returned only as `{link, expiresAt}` with `cache-control: no-store`. A stored link that cannot be opened (wrong key, tampering, unknown key version, a value that no longer looks like a link) is `500 internal_error` with no detail, the transaction is rolled back (the read is not counted), and the log line says `a stored hand-off link could not be opened` with the error class, the closed reason word of the vault, the subject kind and the subject id: never the link, the ciphertext or the key version. The link is never in a log, URL, event, push payload or stored idempotent answer (the link routes are GET and are not stored).

## Deviations from the brief and the spec

1. **The order is not awaited (spec 7.2 says the API waits about three seconds).** A route runs in one transaction, and the worker cannot see an uncommitted payment, so waiting inside the request could never succeed. `POST /v1/loans/{id}/payments` returns the payment as `created` (201) and the app polls `GET /v1/payments/{id}` until `linkAvailable` is true. The end-to-end test shows the chain: request, worker, pending, link.
2. **An Idempotency-Key shorter than 16 characters is `400 idempotency_key_required`, not 422.** The framework (`parseIdempotencyKey`, shared by every route) already enforces the same 16 to 128 characters the database wants, before any route code runs, so a route-level check could never fire. Changing the status would change every route of the API; left as it is.
3. **The cancel routes answer with a small body, not the full object.** `POST /v1/payments/{id}/cancel` answers `{id, status: 'cancelled'}` and `POST /v1/mandates/{id}/cancel` answers `202 {id, result: 'cancel_requested'}`. Reason: `cancel_my_payment` and `request_mandate_cancellation` do not check the lender's switch, while the detail functions do (they answer P0002 when it is off). Reading the object back after the cancel would roll the cancellation back with a 404 exactly when a lender switches the feature off. The app fetches the object afterwards. The mandate cancel is `202` (a request, not a state change).
4. **`intent_not_cancellable` is mapped inside the route.** The hint is not in `RULE_HINTS` (`http/api-error.ts`, a shared file), so a 55000 with this hint would be `409 conflict`. The cancel handler turns it into `409 intent_not_cancellable`; see the shared-file request below. All other hints these functions raise are already registered.
5. **The failure log of an unopenable link carries one more field than "class and id".** It names the error class, the subject kind (`payment_intent` / `mandate`), the subject id and the vault's closed reason word (`cannot_open`, `unknown_key_version`, `link_invalid`, `config`), so an operator can tell a rotated key from tampering. No link, ciphertext or key material.
6. **The 503 message** is fixed text ("Hand-off links cannot be shown in this environment."), no data.
7. **`GET /v1/mandates` has no pagination.** The database function returns every mandate of the caller (a borrower has at most one live mandate per loan, and each needs a step-up code), newest first. No limit exists in SQL; none is added here.

## Not built, open gaps and weaknesses noticed

- **No list of a borrower's payments.** The spec's borrower table has only `GET /v1/payments/{id}`; the open payments of a loan appear in `payment-options.openPayments`, and the history is in the activity route (`servicing.my_loan_activity`, another stream).
- **`POST` of `charges` is accepted by the shape check** (the purpose exists in the database enum) and refused by the database with `409 purpose_not_supported`. `cooling_off_exit` is not in the database enum and is not accepted.
- **`GET .../link` writes** (the database counts every read). It is a GET with a side effect inside the request's transaction; the link routes are rate limited and never stored.
- **A lender-side change of the switch hides reads but not cancels** (deviation 3), and the database lets a borrower cancel a `created` payment of a lender whose payments switch is off. Not changed here; reported so the database owner can decide.
- **Idempotency keys of `request_payment` are scoped per lender in SQL, not per borrower.** Another borrower of the same lender who sends the same key gets `409 idempotency_conflict` (tested), never the first borrower's payment; but a key that is easy to guess (derived from a loan id) would let someone make another person's retry fail. Keys should be random (the app's job). Likewise `request_mandate` answers `409 idempotency_conflict` when a mandate id is already used by another borrower (the id is a uuid chosen by the app), which reveals that the uuid exists and nothing else.
- **A mock or sandbox configuration is refused fail-closed** where the session does not allow mock providers: both writes answer `409 collection_target_invalid` (tested), before the insert guard `mock_provider_blocked` could fire.
- **No real provider exists.** Everything runs on the labelled mocks; the tests prove the HTTP layer and the hand-off of ids, not any provider behaviour.
- **The borrower bank-account verification of Phase 07 does not exist** (see `mandates.md`): the route accepts the masked reference the borrower supplies, as the database does.
