# Phase 08a notes: stream API, lender payments, mandates, reconciliation and exceptions (HTTP)

Code: `services/api/src/modules/lender-payments/routes.ts` (the only module file), contracts in `packages/contracts/src/http/lender-payments.ts` (every export is prefixed `Lp`), tests in `services/api/test/integration/lender-payments.integration.test.ts` (71 tests, real database) and `services/api/test/lender-payments-csv.test.ts` (9 unit tests of the statement parser). Spec: `docs/specs/08-servicing-payments-mandates-collections.md` section 16. Database notes: `provider-events.md`, `mandates.md`, `reconciliation.md`, `accounts.md`.

## How the layer works

- **Every rule stays in SQL.** A write route validates the shape of the body (zod, strict objects), takes the caller from the token (the database resolves identity), passes ids and calls one SQL function. A read route selects named columns from the tables and views lenders may read; row level security decides which rows exist for the caller. Nothing here computes an amount, derives a stage, decides an eligibility or re-implements a closed list: the lists are checked by the database and the contract only mirrors them for clients (`LP_*` constants, with a drift test).
- **Auth.** Every route is `auth: 'staff'`: lender users and platform staff, always with the second factor (`runAsUser` answers `401 mfa_required` to an aal1 staff session on reads and writes alike; the SQL write functions check aal2 again).
- **Reads check the permission first.** `requireReader` answers `403 forbidden` when the caller holds none of the listed permissions for the lender asked for (or for any lender, when none is asked for), instead of a silent empty list. Row level security still filters what is returned. Detail routes answer `404 not_found` for a row the caller cannot see, whether it belongs to another lender or does not exist.
- **Writes take `lenderId` in the body.** The SQL function checks the permission of that lender; a lender the caller may not touch and a lender that does not exist both answer `403 forbidden` (tested). The exception routes take the exception id in the path and answer `404` when the caller cannot see it.
- **Idempotency.** Every POST requires `Idempotency-Key`; the framework stores and replays the answer (`idempotent-replayed: true`), the same key with a different body is `422 idempotency_key_reused`, and the key is scoped to the caller. None of the SQL functions behind these routes takes a key (they are naturally idempotent: `set` upserts, `acknowledge` repeats answer the same, bank credits with the same UTR and content count as duplicates).
- **Pagination.** Keyset cursors over `(timestamp, id)` newest first (`limit` 1 to 100, default 25, `nextCursor` or null). Debits page by `(scheduled_on, id)`, settlement items by `id`. A malformed cursor is `400 invalid_cursor`; a cursor cannot widen access (row level security applies to every page).
- **Responses.** Explicit field mapping, never a spread; the contract objects are `z.strictObject`, so a field that is not declared makes the response check fail (a 500, never a leak). Money is integer paise as a JSON number (checked parse of the database text); dates `YYYY-MM-DD`; timestamps ISO 8601 with offset. `cache-control: no-store` comes from the app.
- **What is never returned.** No borrower id or identity, no idempotency key, no settlement account reference or id, no payment configuration id, no secret reference, no endpoint token hash, no payload hash, no address hash, no signature, no fingerprint, no creditor reference, no hand-off link. Tested by planting canary values in those columns and scanning every response and the captured request log.

Bank-credit upload. The body is `{lenderId, accountId, rows}` or `{lenderId, accountId, csv}` (exactly one). `rows` is `[{valueDate, amountMinor (integer paise >= 1, JSON number), utr}]`, at most 2,000; the API turns the amount into the digit string the database function expects (a change of format, not a computation). `csv` is text with a header line and exactly the columns `valueDate,amountMinor,utr` in any order (a byte-order mark and CRLF are tolerated; quotes are not): any other column, a quoted field, a line with other than three fields, a blank line, a bad value, or more than 2,000 lines refuses the WHOLE upload with 422 (`unexpected_field` for a column, `row_invalid` for a line, `rows_invalid` for too many) and the message names a rule and a line number, never a value from the file. The database repeats the rules and adds its own (a value date in the future, a UTR that differs from one already recorded or repeats with different content: `row_invalid`, `utr_conflict`); in every refusal nothing is stored. The result is `{inserted, duplicates}`.

## Tests (what is proven, and how the guards were checked)

71 integration tests (real migrated database, real SQL functions, fake token verifier; run on a freshly migrated database) and 9 unit tests. Rows the system creates in production were inserted as the table owner with `session_replication_role = replica` (triggers and foreign keys off for that transaction; the file says so); exceptions through `payments.raise_exception` and a reconciliation run per lender through `payments.run_reconciliation`, both as the real system login, so those rows have the shape the database produces.

Covered: anonymous 401, missing second factor 401 on reads and writes, borrower 403, lender user without payment.read 403 on every read route, another lender 403 (named) or 404 (record) with no existence difference between "other lender" and "does not exist", isolation of every list, pagination without skips or repeats against the database's own order, cursor reuse by another lender, every write happy path and its permission, lender and second-factor refusals, idempotent replay (the function did not run twice), key reuse with another body, key reuse by another person, the closed reason lists (every listed code accepted, unlisted refused), the exception lifecycle with both owners, segregation of lender-owned and platform-owned work, the CSV and JSON upload refusals (nothing stored), the platform list, the derived stage of four payments, the real reconciliation report, a canary scan of every response of the file and of the captured request log.

Guards checked by removing them on purpose (each made at least one test fail; sources and database restored afterwards). ## Not built, deviations and open gaps

1. **Row cap is 2,000, not 5,000.** `payments.import_bank_credits` refuses more than 2,000 rows (22023 `bad_request`), so the JSON array and the CSV are capped at 2,000 here too (and 250,000 characters of CSV, 600 kB of body). Raising it needs a database change.
2. **Upload rate limit is 30 a minute per person** (reads 120, other writes 30). A tighter figure would make the integration tests, which upload from several logins, flaky.
3. **Activation switches are not consulted by these routes, because the SQL does not.** None of `set_payment_policy`, `set_mandate_policy`, `set_reconciliation_settings`, `import_bank_credits`, the exception functions or the lender read policies checks `servicing.lender_features`: the switches gate the borrower flows and the worker. So a lender whose `payments` or `mandates` switch is off still sees its history and keeps its settings (a test documents it). If the owner wants the lender portal hidden when a switch is off, that is a database change; `private.feature_enabled` is granted to the system role only, so the API could not do it either.
4. **Not built (not in the brief):** a list of the bank credits a lender uploaded, a list of the reconciliation matches of a run, the payment configuration routes (accounts module), webhook receipts beyond the summary (by design: platform staff only, and never the payload), `GET` of one run by id.
5. **The `accountId` of a bank-credit upload has to come from somewhere.** No route in this repository lists a lender's settlement accounts (ids, labels, masked references); `payments.my_settlement_account_registry_status()` and the RLS-protected `tenancy.lender_settlement_accounts` can provide it. The accounts builder should expose it; until then a client cannot discover the id.
6. **`set_mandate_policy` has a SQL default of 48 hours for the lead time; the API requires the value** (a deliberate choice for a regulated notice period, not a default hidden in TypeScript).
7. **Free-text notes are not screened for personal data by the database.** `resolve_exception` and `reopen_exception` check only the length (500) of `note`; evidence is label-only (enforced). A person can type a name into a note and it is returned to the lender users who read the exception. Recommended: a database guard like the one used for reminder wording (`private.reminder_text_ok`) or no free text.
8. **`import_bank_credits` does not check the status of the settlement account** (only that it belongs to the lender): credits can be recorded against a revoked or unverified account. Probably harmless (the stage `bank_confirmed` additionally needs the configured account), noted for the database owner.
9. **Body validation runs before authentication in the shared route framework** (`registerRoutes`): an anonymous caller who sends a malformed body gets a `422 validation_failed` that names the failing fields (never values) instead of a 401. Not specific to this module; the tests send a well-formed body when they test the 401.
10. **Detail routes cap their children:** a payment lists at most 200 provider payments and 200 adjustments; a mandate shows the newest 100 history rows, 60 debits and 60 notices (the complete debit list is `/v1/lender/mandate-debits?mandateId=`); an exception shows at most 500 history rows. Nothing is silently dropped below those figures.
11. **Reconciliation `report` and `counts` are mapped key by key from the run's jsonb.** A key the run function adds later is not returned until the contract adds it (no leak by construction); a missing key is `null`, never `0`.
12. **Platform operations staff** (`operations_agent`, `auditor`: payment.read is platform-grantable) read every lender's rows through the same policies; platform staff with `platform.payments.providers.manage` read every lender's exceptions, lender-owned ones included, but can only act on platform-owned ones. This is what the SQL says; it is listed here so the portals do not promise more.
13. **Shown to the lender on purpose, needed to reconcile with its own records:** the provider references (`providerPaymentRef`, `orderRef`, `providerMandateRef`, `providerDebitRef`, `providerEventId`), the settlement `batchRef` and `settlementRef` (UTR), the masked borrower account on a mandate (last digits only, as the borrower typed it) and the masked destination of a settlement batch. None is an account number.
14. **Compliance.** These routes are evidence plumbing, not compliance. Mapping to `docs/regulatory/controls-matrix.md` (PAY-xx rows for configuration, reconciliation and exceptions) is for the lead; nothing here claims a control is met.
