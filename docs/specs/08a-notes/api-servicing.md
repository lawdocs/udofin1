# Phase 08a notes: stream API, borrower servicing, documents, quotations, closure and reminders (HTTP)

Code: `services/api/src/modules/servicing/routes.ts` (`servicingRoutes({ documents? })`, the only module file), contracts in `packages/contracts/src/http/servicing.ts` (every export is prefixed `Svc` / `SVC_`), tests in `services/api/test/integration/servicing.integration.test.ts` (real database) and `services/api/test/servicing.test.ts` (route table and contract unit tests, no database). Spec: `docs/specs/08-servicing-payments-mandates-collections.md` sections 7, 10 to 12 and 16. Database notes: `servicing.md`, `servicing-documents.md`, `reminders.md` (this folder). The SQL functions called here are in migrations `20261018000911` (loans), `...912` (documents, requests, quotations, closure), `...914` (reminders) and `...917` (schedule, activity).

## How the layer works

- **Every rule stays in SQL.** A route validates the shape of the request (zod, `z.strictObject` for every body, query and params), takes the caller from the token (the database resolves who the borrower is), passes ids, calls one SQL function and maps the answer. Nothing here computes an amount, derives a stage or a status, decides an eligibility or re-renders a message. The only decisions in TypeScript are about transport: the checksum of a stored file against the recorded one, the cursor, and the choice of status code.
- **Auth.** Every route is `auth: 'borrower'`. A lender or platform user (second factor passed) gets `403 borrower_only`, a login without any access `403 no_active_access`, no token or a bad one `401 token_*`. No staff path into a borrower's loans exists here (lender-side reads are in `api-lender-servicing.md`).
- **Unknown, someone else's and "switched off" look alike where the SQL says so.** An unknown loan, another borrower's loan, document, request or reminder, and (for the loan, schedule and activity reads) a lender whose `servicing_sync` switch is off, all answer P0002, which the API maps to `404 not_found` with the same body. Where the SQL answers a different thing for a switched-off lender, the API passes it on unchanged: an empty list (`documents`, `document-requests`), `quote: null` (latest quotation) or `409 feature_disabled` (`statements_noc` off for the closure, the content of a document, a request and a cancellation). A malformed id is `422 validation_failed` before any database call.
- **Responses are mapped field by field** from the columns this module chooses to read (the table-returning functions are selected with an explicit column list; the two `jsonb` answers, the closure and the opened document, are parsed against a schema of their shape and copied name by name). The contract objects are strict and the framework checks every response against its declared schema, so an undeclared field is a 500, never a leak.
- **What is never returned.** No bank reference, payment mode, provider order or payment reference, settlement account, storage key, content hash of a report or receipt, lender user, borrower id, idempotency key, phone number or account number. The checksum of a document is returned only by the content route (the file the caller is receiving). Tested by planting canary values in those columns and scanning every response of the file, and the request log.
- **Money and time.** Money is integer paise as a JSON number (`Paise`, 0 to 1e14); the database returns `bigint` as text and a checked parse converts it (a value outside the range is a 500, never a wrong number). Dates are `YYYY-MM-DD`; timestamps are read with `to_jsonb(column) #>> '{}'`, so microseconds and the offset survive.
- **Withheld figures are null, never zero.** `GET /v1/loans` and `GET /v1/loans/{id}` return `figuresAvailable`, `reportedAsOf` and `stale`. When `figuresAvailable` is false (no report yet, the newest report carries a warning, or a conflict about the loan report is open) every figure is `null`, and the contract's `superRefine` rejects a response that says otherwise.
- **Idempotency.** Every POST requires `Idempotency-Key` (framework: letters, digits `. _ : -`, 16 to 128 characters; stored per caller and route; a replay answers `idempotent-replayed: true`; the same key with another request is `422 idempotency_key_reused`). The two request POSTs also pass the key to `servicing.request_document`. The database takes 8 to 100 characters, the API documents up to 128: a key longer than 100 is handed to the database as its SHA-256 (64 hex characters, always the same digest for the same key), so the documented range never answers 422 for its length alone.
- **Rate limits.** Writes 30 per minute per caller and route, reads 120, the document content route 60. The per-route limit is tested (429 `rate_limited`).
- **Documents are opened through the store.** `GET .../content` calls `servicing.open_loan_document` first (it authorises the caller and writes the access record), then reads the bytes from the private `DocumentStore`, recomputes the SHA-256 and compares it, and the size, with the recorded values. Any failure after the access record was written throws, which rolls the record back: a read that delivered nothing is not logged as a retrieval. Missing bytes answer `404 not_found` (like every other document route); altered bytes answer a generic `500` (logged without detail, never served). No store configured: `503 document_store_unavailable`. A document of another loan of the same borrower is `404` on this path (the access record is rolled back). The response is `cache-control: no-store`, a JSON body with `contentBase64` (like the Phase 07 document route); there is no permanent or public link.

## Routes

All routes: `auth: 'borrower'`. Common errors: `401 token_*`, `403 borrower_only` / `no_active_access`, `422 validation_failed` (shape of path, query or body), `429 rate_limited`; every POST also `400 idempotency_key_required` and `422 idempotency_key_reused`. Notes on the wire shapes:

- **Loan** (`SvcLoan`): loan facts (`loanStatus` as Udofin holds it, sanctioned and disbursed amounts), then what the lender reported with the lender's time (`reportedAsOf`) and when Udofin received it (`receivedAt`), `stale` and `staleThresholdMinutes`, `figuresAvailable`, and the figures. `stale` is pure staleness (the report is older than the lender's threshold, or none exists); combine with `loanStatus` in the app. The borrower is not told why figures are withheld.
- **Schedule** (`SvcSchedule`): the lender's installments exactly as reported (due date, principal, interest, fees, total); no status or allocation exists because Udofin allocates nothing.
- **Activity** (`SvcActivityPage`): lender receipts and reversals (`posted`, `reversed`, `recorded`), the borrower's payment attempts with the database's honest stage (`started`, `provider_received`, `lender_posted`, `needs_attention`, or `cancelled` / `failed` / `expired` when the provider never reported money) and provider-reported adjustments (`refund`, `chargeback`, `reversal`, `correction`). Newest first, keyset on `(sortAt, entryId)`. The cursor carries `sortAt` as the database printed it, microseconds included; the route asks for one row more than the page to know whether another page exists. `nextCursor` is null on the last page.
- **Documents** (`SvcLoanDocument`): metadata of lender-issued files only (`issuer` is always `lender`; Udofin generates none). `source: mock` is a labelled test document and exists only where mock providers are allowed. The list does not carry the checksum; the content route does.
- **Requests** (`SvcDocumentRequest`): `status` requested, fulfilled, declined (with the lender's own `lenderNote`), expired or cancelled; `dueBy` with its basis (`dueRuleKey`, `dueEvidenceStatus`, normally `unverified`: a platform default, not a regulatory deadline). The POST answer is the request as the borrower's own listing shows it.
- **Quotation** (`SvcQuote`): the lender's figures unchanged, `validUntil` as an instant (the app shows a date and time, not a countdown), `totalMismatch` when the parts do not add up (unknown is treated as a mismatch), `source`, and the letter's document id when the lender attached one. A foreclosure payment must equal `totalMinor` of an unexpired quotation; the payments stream checks this in the database.
- **Closure** (`SvcClosure`): prompt KEYS only (`closure.noc.*`, `closure.security_release.<type>.*`); statuses always come from the lender (`statusSource: 'lender'`), due dates carry their basis, and a key never claims a release unless the lender confirmed it. `closureRecordedAt` is when Udofin recorded the report, not the lender's closure date.
- **Reminders** (`SvcReminder`): the wording exactly as the database rebuilt it from the frozen template (shown only when it still matches the stored hash). Nothing is re-rendered, translated or shortened by the API.

## Tests

`services/api/test/integration/servicing.integration.test.ts` runs against a freshly migrated database through the real application (fake token verifier, the real `udofin_api` role, a local document store on a temporary folder). Five lenders and four borrowers are built: lender A has every switch on and approved due-date rules, B and E every switch on, C only `servicing_sync`, D none. Rows a lender person creates (documents, quotations, security-release confirmation, declines) go through the real SQL functions as a signed-in lender user at aal2. Rows the system creates in production (balance snapshots, schedules, lender receipts, payment attempts, provider payments, refunds, reminders and their delivery log) are inserted as the table owner with `session_replication_role = replica` (triggers and foreign keys off for that transaction only; check constraints and unique indexes still apply).

Covered: 401 on every route, 403 for a lender user and a login without access on every route, 422 for bad paths, queries and bodies (no submitted value echoed), the Idempotency-Key rules; loans (own only, newest first, stale, withheld figures null, a stranger's loan is the same 404 as an unknown one); schedule (newest version, empty cases); activity (all four entry kinds, no bank reference, payment mode or provider reference, paging without skips or repeats including entries inside one millisecond and at the same instant, microseconds kept in the cursor, the switch-off cases); documents (list, content with the right checksum and `no-store`, every retrieval recorded, refused for another borrower, a wrong loan path, an unknown document, a switched-off lender and altered or missing bytes, 503 without a store, mock documents only in mock mode); requests (creation, replay of the same key, a concurrent duplicate, reuse with different content, the full-length key, cancellation guards, period checks, the lender's answers); the quotation (figures unchanged, none, mock, a stranger, the mismatch flag); closure (none, pending, confirmed, delay reason, 404, 409); reminders (own only, newest first, every channel copy marked read, idempotent, 404 for others); live switch kills (each switch turned off while the app runs); the 429 limits; canary scans of every response and of the request log; the OpenAPI document; the closed vocabularies of the contract against the database.

The integration file has 61 tests and the unit file 22. The integration file removes every row it created in `afterAll` (scoped to its five lenders, triggers and foreign keys off for that one transaction): left behind, its approved due-date rules broke the documents file ("every seeded rule is a draft") and its payment adjustment broke the scheduled-jobs file ("the run never writes a money row"). It completes its own pending outbox events as well. The organisations, their onboarding gates and the people stay, as in the other files (the platform account listing needs a gate for every lender organisation).

The guard checks were made by removing each guard on purpose and watching a test fail (the list is below under "Guard checks").

## Not built, deviations, open gaps

1. **`GET` / `PUT /v1/me/reminder-preferences` (spec section 16) is NOT built, on purpose.** The language already lives on the borrower profile (`POST /v1/borrower/profile`), push on or off is the device's notification permission, and the database has no server-side opt-out (`reminders.md`: "per-borrower preferences or opt-out" are not built). A route that stored a preference nothing reads would be a placeholder that pretends to work. Needs an owner decision and a migration first.
2. **No SMS, no real push.** The reminder inbox is the in-app copy; the push adapter and any SMS provider are later streams (`reminders.md`).
3. **Deviation from the spec text: the document content is a JSON base64 body, not an "authenticated stream"** (spec section 16). It is the same shape as the Phase 07 document route and the lender content route, so one client path handles every document, and the checksum is verified before any byte leaves. The cost: a file at the 25 MB limit becomes about 33 MB of JSON. A streaming variant needs an owner decision on the client side (the mobile app and the portals read the JSON today).
4. **Production document store.** `DocumentStore` is injected; without one the content route answers 503. Production reads of lender-issued content stay blocked until a production store exists (`servicing-documents.md`, section 6). Nothing here claims otherwise.
5. **Due dates are platform defaults, not regulatory deadlines.** The three rules behind them are seeded as drafts and never approved by a seed (`servicing-documents.md`, section 1): the statement and NOC defaults are labelled `unverified`, the security-release rule `confirmed` only for the cases its note names. The API only passes the basis through (`dueRuleKey`, `dueEvidenceStatus`); the app wording must say "platform default" where the label is `unverified`. Nothing here claims a deadline is met or required.
6. **Activity is ordered by the time Udofin recorded each entry**, not by its value date (`received_at` of a lender receipt, `created_at` of a payment attempt, `occurred_at` of an adjustment). A backfilled old receipt therefore appears near the top with an old `occurredOn`; the app should show `occurredOn` as the date and use the order only as the order of arrival.
7. **The idempotency key is hashed only above 100 characters.** Shorter keys (16 to 100) reach the database unchanged and are stored in `servicing.document_requests.idempotency_key`. They are random client keys, not personal data, but an app that put a personal value in the key would store it; the mobile client uses random UUIDs.
8. **`GET .../foreclosure-quotes/latest` costs two function calls** (an ownership probe through `my_document_requests`, then the quotation) because `latest_valid_quote` deliberately answers an empty set to a stranger, and the contract here is 404 for a stranger. If the database later exposes a borrower-only variant that raises P0002, the probe can go.
9. **The read-only reminder list has no cursor** (the database caps it at 50 messages). The borrower cannot page back further.
10. **The OpenAPI document and `docs/api/servicing-payments.md` were not edited** (the lead regenerates them after merging). No migration was written and no shared file was edited.
