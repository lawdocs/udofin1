# Phase 08a notes: the payment-provider callback receiver (builder d)

`POST /v1/hooks/provider/:endpointToken`, the route that takes signed events from payment providers (payments, refunds, chargebacks, mandates, debits, settlements). It runs in the separate callback-receiver process (`workers/callbacks-main.ts`, the system login); the public API never registers it and it is not in `docs/api/openapi.json`. Nothing in this note claims regulatory compliance: it describes what the code does and what it does not.

Code: `services/api/src/workers/provider-callbacks.ts` (route, limits, verification wiring), `services/api/src/system/provider-hooks.ts` (the two system-role queries). Tests: `services/api/test/provider-callbacks.test.ts` (unit, an in-memory stand-in for the database) and `services/api/test/integration/provider-callbacks.integration.test.ts` (real migrated Postgres, the real callback app, real signed mock deliveries). Protocol: `provider-events.md` (this folder), spec section 9, migration `20261018000913`.

## What the receiver decides, and what it leaves to the database

The receiver decides only what the database cannot: the shape of the routing token, which signature scheme verifies a configuration, the signature and timestamp check over the exact bytes received, size and content-type limits, rate limits, and the keyed hash of the client address. It computes no amount, derives no status and applies no business rule. After verification it calls `payments.ingest_provider_delivery` exactly once; replay, merchant, correlation, amounts and the outbox job are all there. It never marks anything successful: the worker does, later, from the verified event (`payment.apply_event`).

## The route

| Step | What happens                                                                                                                                                                                                                                                                                  | Database function / table                                                                                          |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 1    | Per-token-hash rate limit (`onRequest`), per-address limit (`@fastify/rate-limit`), content type `application/json` only, body at most 256 KiB read as raw bytes. Refused here: 429, 415, 413. No database work.                                                                              | none                                                                                                               |
| 2    | Token shape check: 32 to 128 URL-safe characters. A bad shape spends the decoy verification work and answers the uniform 401. No database work, so no receipt.                                                                                                                                | none                                                                                                               |
| 3    | `lookupConfig(sha256(token))`: the ACTIVE configuration of that token hash; reads only `id`, `provider`, `provider_mode`, `webhook_secret_ref`.                                                                                                                                               | select on `payments.lender_payment_configs` (system role)                                                          |
| 4    | Pick the verifier: only the labelled mock scheme `mock-standard-webhooks-v1`, for provider `mock_payment_provider` in mode `mock`, in `local` and `test`. Anything else (sandbox, production mode, another provider, a mock configuration in staging or production) has no scheme.            | `resolveWebhookVerifier`; refusal is stored as `scheme_not_configured`                                             |
| 5    | Resolve the webhook secret by NAME (`webhook_secret_ref`) through `deps.secret`, verify signature (constant time), timestamp tolerance (300 s either way) and the body with the adapter's `WebhookVerifier`. No config, no scheme or no secret: the same work is spent on a random decoy key. | `WebhookVerifier.verify` (`packages/adapters/src/payments.ts`)                                                     |
| 6    | One call with the verifier's result, the payload hash, the scheme name, whether a signature was present, the timestamp skew, the body size and `ip_hmac` (HMAC-SHA-256 of the client address under `PROVIDER_HOOK_IP_HMAC_KEY`).                                                              | `payments.ingest_provider_delivery(token_hash, delivery)` (system role)                                            |
| 7    | Map the answer. Only a delivery THIS receiver verified can get anything but the uniform 401, whatever the database says.                                                                                                                                                                      | `payments.webhook_receipts`, `provider_events`, `ops.seen_webhooks`, `ops.outbox_events` (written by the function) |

Anything else under `/v1/hooks/provider/` (trailing slash, another method, an extra path segment, a token over 100 characters) answers one fixed 404 and is logged at warn level only.

### Authentication and permissions

There is no user. The caller is authenticated only by the signature over the body with the lender's own webhook secret, routed by the opaque token whose hash is stored on the configuration. The token is a routing aid, not a credential: knowing it without the secret gets the uniform 401. The database function is callable only by `service_role`.

### Answers (all `application/problem+json` except the 200; `cache-control: no-store`)

| Status   | `code`                    | When                                                                                                                                                                                                                                       |
| -------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 200      | (body `{"ok":true}`)      | Verified and stored (event, verified-and-ignored, or an acknowledged duplicate/replay).                                                                                                                                                    |
| 401      | `invalid_signature`       | Everything before authentication, identically: unknown, suspended or retired token, malformed token, missing header, bad or stale signature, unusable body, no scheme, no secret. Also a verified delivery the database rejected.          |
| 409      | `unmatched`               | Verified, but no intent or mandate of THIS lender, provider and configuration matches yet (the provider should retry; the delivery id was NOT consumed), or the named merchant is not the configured one (the configuration is suspended). |
| 422      | `invalid_event`           | Verified, but not business-valid (a money status without an amount, malformed field). The delivery id is not consumed.                                                                                                                     |
| 429      | `rate_limited`            | Per token hash (any token, valid or not): fixed text, `retry-after: 60`. The per-address limit answers 429 through the app's error handler.                                                                                                |
| 503      | `temporarily_unavailable` | The database could not be reached or failed: the provider should retry. The log carries a reason class and at most a five-character SQLSTATE.                                                                                              |
| 404      | `not_found`               | Anything under the prefix that is not the route.                                                                                                                                                                                           |
| 413, 415 | `bad_request`             | Body over 256 KiB, a content type other than `application/json`. Same answers as the lender receiver. Independent of the token.                                                                                                            |

### Log discipline

The route logs at warn level only (`logLevel: 'warn'` on the route and on the catch-all), because the automatic "incoming request" line carries the URL and therefore the token. A line carries the request id (added by the logger) and a reason class (`config_lookup_failed`, `ingest_failed`, `webhook_secret_not_configured`, `rejected_after_verification`, `scheme_not_configured`, `mock_blocked`, `verifier_failed`) and at most a five-character SQLSTATE. Never a body, header, token, token hash, signature, secret, address, order reference or error message.

### Address hash key

`PROVIDER_HOOK_IP_HMAC_KEY` (name resolved through `deps.secret`, in the entry point an environment variable). In `local` and `test` an absent key means a random key for this process only. In `staging` and `production` an absent key, or one shorter than 32 characters, is a startup error (the process does not start) that never contains the key.

## What changed in this stream

An earlier builder wrote the receiver and its unit tests. Review against the protocol found one defect and one small mismatch, both fixed:

1. **Token in the log for requests that missed the route.** A trailing slash, another method or an extra path segment under the prefix was handled by the framework's own not-found path, which writes the URL at info level (a real token in the log) and echoes it back in the response. A catch-all route under the prefix now answers one fixed 404, logged at warn level only. Unit test and integration test both fail without it.
2. The decoy verification now hashes the body too, as the real verifier does, so an unknown token and a bad signature cost the same.

Everything else was checked and found correct: uniform 401 and no enumeration, verification over the exact bytes, tolerance, body limit and content types, per-address and per-token limits, no sensitive log content, the keyed address hash and the startup refusal, and the route's absence from the public route table and OpenAPI document.

Lenders have an active two-person configuration, real intents (`payments.request_payment`, `record_order_created`) and a real mandate (`request_mandate`, `record_mandate_handoff`).

## Not built, deviations and open gaps

1. **No real provider scheme exists.** Only the labelled mock scheme. A real provider's configuration (sandbox or production mode, any other provider key) is answered with the uniform 401 and a `scheme_not_configured` receipt. Spec section 9 point 2 says `503 provider_scheme_not_configured` for that case; the receiver deliberately answers 401 (as `phase-08a-activation-gates.md` says: "answers every delivery with the uniform refusal"), because a distinct answer would tell a caller which tokens belong to real-provider configurations. The spec text and the activation-gates text disagree; the owner should pick one.
2. **Source-network check not built.** Spec point 2 allows a source-network check "where the provider documents it"; no provider documentation exists.
3. **Transport refusals are not uniform with the 401 and leave no receipt.** 413, 415 and 404 use the framework's error handler (`bad_request` / `not_found`), a different body from the 401. They are independent of the token, so they reveal nothing about tokens, but spec 9.1 wants "the same fixed response shape"; reading it as "same status family" they comply, reading it strictly they do not. They also write no receipt (no configuration is known at that point). A shape-invalid token (not 32 to 128 URL-safe characters) also reaches no database and leaves no receipt.
4. **Timing equivalence is structural, not measured.** An unknown token, an unusable configuration and a bad signature make the same calls (one lookup, equal verification work, one ingest). No timing measurement was made; do not read this as a proven constant-time property of the whole request.
5. **Rate limits.** In memory, per process (not shared between replicas). Not configurable from the environment: `callbacks-main.ts` passes no limits, so the defaults (300 per address, 120 per token hash, per minute) apply. A provider's settlement bursts from a few egress addresses could hit them. The per-token table is bounded (10,000 buckets); a flood of random tokens can evict a real token's counter and so reset it (the per-address limit still holds). Behind a load balancer the per-address limit is only meaningful if `TRUST_PROXY_HOPS` is right (the config already requires it to be set in staging and production).
6. **Receipt growth.** Every unknown-token, forged or stale delivery that passes the rate limits writes a receipt (the protocol wants this). `payments.webhook_receipts` is append-only and no retention or ageing job exists. Spec 9 point 4 also wants "a metric and alert beyond a threshold" for unverified deliveries: the receiver has no metrics or alerting yet.
7. **Secrets and the address key.** The entry point resolves secret names with `process.env[name]` only; no secrets-manager integration exists. `PROVIDER_HOOK_IP_HMAC_KEY` is not in `services/api/.env.example`. Rotating the key makes earlier and later address hashes incomparable; receipts carry no key version.
8. **Compressed bodies.** Nothing decompresses a request body; the signature is over the bytes as received. A provider that sends `Content-Encoding: gzip` would fail verification. Unverified assumption about providers.
9. **Not covered by tests.** Refund and chargeback deliveries over HTTP (they take the same order-reference branch in SQL, covered by pgTAP; the mock scenarios `refund` and `chargeback` exist), a matched debit event (needs a planned debit; only the unmatched debit is tested), settlement events, partial-amount and out-of-order scenarios over HTTP (the worker side is tested in `payments-worker.integration.test.ts`), a real listening socket, TLS, and a real reverse proxy. All requests use `fastify.inject`.
10. **The leak test builds its own Fastify.** `buildCallbackApp` creates its logger inside (off when `APP_ENV` is `test`) and takes no output stream, so the log capture uses a Fastify instance configured like it (same `loggerOptions`, same error handler, same rate-limit plugin) with the real route and the real database pool. The real process output of `callbacks-main.ts` is not captured by any test.
11. **Tokens longer than 100 characters** never reach the route (the router's parameter limit); they get the fixed 404. Real tokens are 43 characters, so no real token is affected.
12. **The receiver's database role.** The receiver uses the plain system login; it cannot move a mock-mode mandate. This is intended (only the worker applies events) and is how the tests run it: the mandate event is applied by a separate worker-style session, never by the receiver.
