# Phase 08a notes: stream API, lender reminders (HTTP)

Code: `services/api/src/modules/lender-reminders/routes.ts` (the only module file), contracts in `packages/contracts/src/http/lender-reminders.ts` (every export is prefixed `Lr` or `LR_`), tests in `services/api/test/integration/lender-reminders.integration.test.ts` (75 tests, real database) and `services/api/test/lender-reminders.test.ts` (12 unit tests of the declarations and contracts). Spec: `docs/specs/08-servicing-payments-mandates-collections.md` sections 11 and 16. Database notes: `reminders.md` (policy, wording, penal-charge text, two-person approval, window, caps, holds, suppress reasons, the missing-texts register).

## How the layer works

- **Every rule stays in SQL.** A write route validates the shape of the body (zod, strict objects), takes the caller from the token (the database resolves identity), passes ids and calls one SQL function. A read route selects named columns from the tables lenders may read; row level security decides which rows exist for the caller. Nothing here computes a charge, writes, suggests or translates a sentence, derives a stage, or decides who may send what. The closed lists (statuses, kinds, languages, channels, suppress reasons, hold reasons, delivery states, error classes, charge kinds) are checked by the database; the contract only mirrors them as `LR_*` constants and `z.enum`, and an integration test compares each with the check constraint it comes from, so a drift fails.
- **The lender's words and figures pass through unchanged.** Policy figures, wording, the penal-charge figure, the two attestations, the reason and the sentences in English and Hindi are handed to the SQL function as sent and returned as stored. The API adds no placeholder, no default, no sentence, no translation, no conversion and no suggestion. Where the contract bounds a field (array sizes, string lengths, a `HH:MM` shape) it only protects the shape of the request; the range rules (offsets, window, cap, charge limits, wording rules) are the database's, and its refusal is the answer. For that reason the attestations are typed as booleans, not as `true`, and an out-of-range figure is not blocked in TypeScript: the client sees the same `attestation_missing` / `charge_invalid` / `offsets_invalid` / `window_invalid` / `policy_invalid` code whatever it sent.
- **Auth.** Every route is `auth: 'staff'`: lender users and platform staff, always with the second factor (`runAsUser` answers `401 mfa_required` to an aal1 staff session on reads and writes alike; the SQL write functions check aal2 again, and a test calls them directly as aal1 to prove the database refuses on its own).
- **Reads check the permission first.** `requireReader` answers `403 forbidden` when the caller holds none of the listed permissions for the lender asked for (or for any lender, when none is asked for), instead of a silent empty list. Row level security still filters what is returned. The permissions mirror the row level security policies: the policy, wording and penal-text tables are readable with `loan.read`, `reminder.policy.manage` or `reminder.template.approve`; holds, reminders, deliveries and the summary with `loan.read`. Platform operations roles hold `loan.read` across lenders, so they read everything and write nothing (`reminder.*` are not platform-grantable).
- **Writes take `lenderId` in the body** (drafts). The SQL function checks the permission of that lender; a lender the caller may not touch answers `403 forbidden`. **Actions on an existing row take its id in the path** (approve, retire, release, place a hold on a loan) and answer `404 not_found` for an unknown id, another lender's id and an id the caller has no permission over: the SQL answers `P0002` for all three, so existence is not disclosed.
- **Idempotency.** Every POST requires `Idempotency-Key`; the framework stores and replays the answer (`idempotent-replayed: true`), the same key with a different body is `422 idempotency_key_reused`, and the key is scoped to the caller. None of the SQL functions takes a key. A replay does not run the function again (tested: one policy row, one hold row).
- **Pagination.** Keyset cursors over `(timestamp, id)` newest first (`drafted_at`, `placed_at`, `scheduled_for`), `limit` 1 to 100, default 25. A malformed cursor is `400 invalid_cursor`; a cursor cannot widen access (row level security applies to every page; tested by replaying lender A's cursor as lender B).
- **Responses.** Explicit field mapping, never a spread; the contract objects are `z.strictObject`, so a field that is not declared makes the response check fail (a 500, never a leak). Money is integer paise as a JSON number (checked parse of the database text); dates `YYYY-MM-DD`; times of day `HH:MM`; timestamps ISO 8601 with offset. `cache-control: no-store` comes from the app. Nothing in this module writes a log line.

## Routes

`SQL` is the function called or the table read (RLS = row level security of the table). Common errors on every route: `401 token_*`, `401 mfa_required`, `403 staff_only` (a borrower), `403 no_active_access`, `422 validation_failed` (shape), `429 rate_limited`. Writes also `400 idempotency_key_required`, `422 idempotency_key_reused`. Lists also `400 invalid_cursor`. Rate limits: 30 writes and 120 reads per minute per person and route.

### What the lists return

- **Policy.** Version, status, offsets in days (negative before the due date, 0 the due day, positive after), `overdueWeekly`, channels, window `HH:MM` IST, `maxPerDay`, who drafted, approved and retired it and when (user ids only, no names). The platform window, cap and quiet period are narrowed in the database and are not shown here.
- **Wording.** Kind, language, version, status and the body exactly as submitted (the approver must read it). Placeholders: `lender_name`, `due_date`, `amount`, `penal_text` (`LR_TEMPLATE_VARIABLES`); an overdue wording carries `{{penal_text}}`. The wording hash is not returned.
- **Penal-charge text.** Version, status, the lender's figure (`flatAmountMinor` in paise or `percentBps`, never both, never computed), `basis` (`overdue_amount`, the only value), the two attestations, the reason, `sentenceEn`, `sentenceHi` (or null) and the approval trail. The statement is the lender's own and is shown verbatim in an overdue reminder; it is not a regulatory quotation and nothing here says it complies with anything.
- **The "no approved text, no overdue reminders" flag.** The policy list and the penal-text list both carry `overdueReminders: {penalTextApproved, overdueRemindersWithheld}`, read from the lender's penal-charge text rows in the same transaction (`exists` / `not exists` of an approved row, row level security applies); no TypeScript rule applies it. While `penalTextApproved` is false the database suppresses every overdue reminder (`penal_text_missing`) and opens one exception for the lender. Pre-due and due-day reminders do not depend on it. An approved text that is later retired makes it false again (tested). The flag does not look at wording or policy: a lender can have an approved text and still send no overdue message for lack of an approved overdue wording (`template_missing`).
- **Holds.** Loan, reason, the lender's notes, who placed and released it and when, and `active` (computed by the database from `released_at`).
- **Reminders.** Loan account, installment, due date, offset, channel, kind, scheduled time, status, suppress reason, attempts, claimed time, the frozen references (`templateId`, `penalTextId`), language used and whether Hindi fell back to English, and `amountMinor`. **Decision (the brief asked for one):** the rendered wording is not stored anywhere (the borrower's app rebuilds it), so none is returned. The table does hold `variables` (due date, the amount the LENDER reported, and the lender's display name) and the lender can read them through row level security (`loan.read`); of these the route returns only the amount, because it is the lender's own reported figure and the one thing a lender asks ("what amount did the reminder say?"). The due date is its own column; the display name is the lender's own and is not returned; the borrower id, the content hash, the penal-sentence hash and the worker lease are never returned.
- **Summary.** Counts by status, suppress reason and channel for messages scheduled at or after `since` (the database default of 30 days when `since` is omitted; the answer echoes `since: null` then). Counts only.
- **Deliveries.** The append-only attempt log, oldest first (at most 100 rows): channel, state, source, provider reference, error class, time, and the two SHA-256 values (the wording that was sent, the penal sentence it carried) as delivery evidence, as the table comment and the spec describe. `accepted` means the channel took the message, not that it was delivered; `delivered` appears only from a delivery report; an `sms` attempt can only be `not_configured`.

## Tests (what is proven, and how the guards were checked)

75 integration tests (real migrated database, real SQL functions, fake token verifier; run on freshly migrated databases) and 12 unit tests. The reminders and their delivery attempts, which the reminder worker writes in production, are inserted as the table owner with `session_replication_role = replica` (triggers and foreign keys off for that transaction; the check constraints and unique indexes still apply); everything else goes through the routes. Cleanup in `afterAll` deletes every reminder, hold, policy, wording, penal-text and loan row of the file's two lenders (scoped by lender id).

Covered: anonymous 401, missing second factor 401 on every read and write, the database's own second-factor refusal called directly, borrower 403, a lender user with neither `loan.read` nor a reminder permission 403 on every read, another lender named explicitly 403 on every read in both directions, a platform operations user reading across lenders and writing nothing, a viewer reading everything and writing nothing; the full draft, approve, retire flows of all three artefacts with the previous version retired on approval; self-approval refused by the database (403 `self_approval`; the only way to get a login holding both permissions is to switch the segregation trigger off, which the test does on purpose and proves is otherwise refused); approve/retire by someone without the permission, by the drafter, by another lender and for an unknown id all 404; the refusals of the SQL for every offsets, channels, window, cap, wording (link, web address, e-mail, phone-like number, eight-digit run, PAN-shaped token, promotional words, unknown placeholder, markup, too short, stray brace), missing `{{penal_text}}`, charge-figure, attestation and note case mapped to 422 with the hint as the code, nothing stored and nothing of the refused text in the response; the Aadhaar-shaped number and credential-shaped phrase that only the table triggers catch (`unsafe_free_text`); idempotent replay (one row), key reuse with another body; the lender's words stored and returned byte for byte; wording never in the audit event; holds (place, planned messages suppressed with reason `hold` and sent ones untouched, duplicate refused, release, release again, place again, lender assertion, other lender, viewer, approver, platform user); pagination without gaps or repeats at several page sizes against the database's own order; every filter against the same filter in SQL; the summary against the table's own aggregate, with and without `since`; the attempt log in order; the closed lists against the database's check constraints; a canary scan of every response of the file and of the captured request log (a phone-like number, an account-like string, a link, the lender's display name, the reminders-table hashes, the borrower ids and every refused text planted or submitted, never returned or logged); the OpenAPI document and an undeclared method.

## Not built, deviations and open gaps

- **No feature switch is consulted.** None of the draft, approve, retire, hold, summary or read functions or policies looks at the lender's `reminders` switch (activation needs an approved policy and approved wording first, `private.feature_prerequisites_unmet`, so a lender must be able to prepare them while the switch is off). With the switch off the planner writes nothing, so the reminders list and the summary are simply empty. The brief's "a lender switch that is off hides the feature" therefore has no case here, and no test.
- **`lenderId` is required on the three artefact lists** (policy, wording, penal text) because the answer carries the per-lender overdue flag, and optional on holds and reminders (row level security scopes them). The spec's `GET/PUT /v1/lender/reminder-policy` is replaced, as the brief says, by versioned drafts (`POST`), approve and retire; there is no `PUT` and no "get one by id" route.
- **`template_invalid` cannot be produced through HTTP**: kind and language are enums in the contract, so an unknown value is a `422 validation_failed` before the database. The same holds for an unknown hold reason. The database still refuses both, by its own hint, if called directly.
- **Draft answers are stored in the idempotency record for 24 hours.** `ops.idempotency_keys.response_body` holds the replayable answer, and the table comment says it must never contain personal data. A draft answer contains the lender's own wording or penal-charge sentence; the database refuses links, e-mail addresses, long digit runs, PAN-shaped tokens and the identifier patterns of `onboarding.reject_unsafe_text`, but it is free text the lender typed. The owner may prefer draft routes that return only the id; the cost is one more read by the client.
- **The `lenderId` assertion on the hold route needs `loan.read`.** It is checked against `servicing.loan_accounts` through row level security; a caller with `reminder.policy.manage` but no `loan.read` who sends `lenderId` gets 404 (leave it out). The shipped `communications_admin` role holds both.
- **A lender with `reminder.policy.manage` but no `loan.read` cannot list holds or reminders** (the policy on those tables is `loan.read`); it can still draft, retire and place holds. The shipped roles hold both.
- **Drafting a wording or penal-charge sentence is the whole of the text work.** No preview of a rendered message, no placeholder suggestion, no translation, no "suggest a sentence" and no levy-notice route exists (the spec's levy notice for a penal charge actually levied is not built in the database either). The lender cannot read what a borrower saw: the rendered wording is not stored, only its hash in the delivery log.
- **Hindi wording is checked for shape by the database, not for meaning.** A person who reads Hindi must approve each lender's Hindi wording (item 4 of the missing-texts register in `reminders.md`). The API does nothing about it.
- **Nothing here is a statement of compliance.** The penal-charge sentence is the lender's, with the lender's own attestations; the 08:00 to 19:00 window is an interpretation (unverified against the primary text); the daily cap and quiet period are platform defaults with no source. The API shows none of these as a legal position. The missing-texts register in `reminders.md` stays open: the lender's penal-charge disclosure sentence and agreement clause, the recovery-conduct text, the cap and quiet period, Hindi review, and push content and consent wording. The controls-matrix row for the reminder workflow is the lead's to add or confirm.
- **Not in this stream**: the borrower's reminder inbox and preferences (`/v1/me/reminders` exists in the servicing module; `/v1/me/reminder-preferences` is not built), the planner and sender worker handlers, a real push provider and the lender-portal screens.
- **Test-only construct.** The self-approval test creates a login with both reminder permissions by inserting a role with triggers switched off in a disposable test database; production cannot hold that state (the segregation trigger refuses it, and the test proves the refusal).
