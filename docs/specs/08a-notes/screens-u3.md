# Phase 08a notes: lender portal screens for loans, imports, sync, conflicts, documents, quotations and closures (builder u3)

Code: `packages/portal-kit/src/servicing/**` (views, loaders, allow-listed operations, wording, formatting), the pages and server actions in `apps/lender-portal/app/loans/**` and `apps/lender-portal/app/imports/**`, tests in `packages/portal-kit/test/servicing-ops.test.ts` (118 tests, node environment), `packages/portal-kit/test/servicing.test.tsx` (106 tests, jsdom) and the shared fixtures `packages/portal-kit/test/servicing-fixtures.ts`. The API this calls is described in `api-lender-servicing.md`; the contracts are `packages/contracts/src/http/lender-servicing.ts` (every export prefixed `Ls`). Spec: `docs/specs/08-servicing-payments-mandates-collections.md` sections 6, 12, 16 and 17 (lender portal list). These screens are for lender staff only; nothing here is shown to a borrower.

## What the screens do and do not do

- **Show, never work out.** Every figure is the one the API returned, written as rupees with Indian digit grouping from integer paise (`formatRupees`), or "Not reported" when the API says null. Nothing is added, rounded, totalled, compared or inferred: a total that does not match its parts (`overdue_total_mismatch`, `totalMismatch`) is shown as the lender stated it, with a flag, and the sum of the parts appears nowhere (tested).
- **Whose figure and when.** Reported figures say "As reported by <lender> on <date, time IST>" (and when Udofin received them). A stale loan gets a plain banner; a loan with no report says so.
- **No server text on a screen.** Closed vocabularies and stable error codes go through wording tables (`wording.ts`). A value or code the table does not know is shown as a generic sentence, never as it came (tested with drifted values and a fake SQLSTATE). A failed load says "Could not load ..." and repeats nothing the API said. Lender-written free text that the API returns on purpose (a decline note, a delay reason, a resolution note) is shown as written, escaped by React.
- **Write forms follow the permission set.** The page-frame permissions come from `/v1/me`; the pages turn the memberships into one grant per lender (`servicingGrants`), and a form is drawn only for a lender in which the person holds the permission. Read-only roles see no write form, only the plain GET filters. This hides a form; the API and the database authorise every call again.
- **One allow-listed operation per form.** `SERVICING_OPERATIONS` is the only way a form can write. Each entry maps a named operation to exactly one API route, checks its fields again, and sends an `Idempotency-Key` (minted when the page renders, fresh per upload). An unknown operation, a key of the wrong shape, or the staging operation through the general entry point is refused without any call to the API.

## Import behaviour worth knowing

- The upload is a multipart form to a server action (limit 9 MB, already configured for the portal). The action reads the file as UTF-8 text (refused if it is not valid UTF-8), keeps the exact text (a byte-order mark is kept; the importer ignores it) and posts it as `content` with its `fileFormat`. The file name is never sent anywhere. The screen shows the caps: 5 MiB and 10,000 records, one kind of record per file.
- Staging shows a preview and applies nothing. Applying is a separate form with a review box that is never pre-ticked; discarding is a separate form that needs a reason. The wording says "Nothing is applied unless every row is valid." A file with any error cannot be applied; the page lists row number, kind of problem and column name, never a value, and offers "Upload a corrected file" (which links the earlier file as a resubmission).
- A file the importer refuses has no batch and no preview page (the API answers 200 with `refusedFile`); its problems are handed back to the upload form and shown at once.
- A commit that fails inside the database is an HTTP 200 with the batch marked failed. The action reports that as an error with plain words (not "recorded"), and the result page says nothing was applied. The SQLSTATE class is never shown.

## Not built, deviations and gaps (honest list)

- **Upload path.** The brief says the portal reads the file as text "in the browser form". The browser sends the file in a multipart form and the server action reads it as text. The effect is the same (the exact text is posted as `content`), it keeps the whole upload as one allow-listed operation, and it needs no client-side file code.
- **No list of refused files.** A file the importer refuses is audited by the API but no route lists those records, so "rejected-file records" appear only (a) immediately after the attempt, on the upload form, and (b) as discarded batches (`rejected`) in the files list. Someone who reloads the page cannot see the refusal again. Needs a read route if wanted.
- **No row values and no file preview of content.** By design the API returns row numbers, error classes and column names only. The preview shows counts, not the rows.
- **Counts are not totalled.** The preview table shows the API's counts per outcome; no grand total or percentage is drawn.
- **No evidence upload for a conflict.** `resolve` takes short text references (label and value). The form offers four fixed labels and three slots. There is no file evidence because the API takes none.
- **The ₹5,000-a-day delay exposure** that spec section 12.3 says is "noted in the lender portal for lateness" is NOT shown. It is a regulatory reference the notes do not mark as verified against the primary text, and CLAUDE.md rule 5 forbids stating it as fact. The closure page shows the platform default target labelled "not a regulatory deadline" and the lender's own delay reason only. Owner decision needed.
- **Pages are not unit tested.** The Next.js pages, the two server actions and the file route are thin (session, client, load, draw); their logic lives in portal-kit and is tested there. `apps/lender-portal` has no test runner and `tests/e2e` was not extended (its fake API would need the new routes), so there is no browser test of these pages.
- **Inline PDF header.** The file route sets `content-security-policy: sandbox; default-src 'none'` exactly as the Phase 07 document route does. Some browsers may refuse to render a PDF under a `sandbox` policy in their built-in viewer; I could not check that here. If it is a problem, switch both routes to `content-disposition: attachment`.
- **Colour.** No new colours were added; the pages use the existing portal classes. Meaning is always in words, not colour alone. A contrast check against the theme tokens was not run.
- **Navigation.** The sub-pages (requests, closures, conflicts, flags) are reached from the in-page navigation (`Servicing pages`), not the top navigation, because the page frame has one entry for `/loans` and one for `/imports`.
- **Hindi.** The lender portal is English only, as in earlier phases.
- **Stale preview batches.** There is no route to expire an old preview (API notes: not built), so old `previewed` files stay discardable.

## Evidence for the controls matrix (facts about behaviour, no compliance claim)

- Owner decision 10 (all-or-nothing import, row errors without values): the screens say that nothing is applied unless every row is valid, list problems by row number, kind and column only, and offer apply and discard as separate explicit steps. This shows the screen follows the API; it does not show a regulated obligation is met.
- Lender-issued documents: the portal never renders or issues a document; it registers and streams the lender's own PDF after the size and SHA-256 are checked against the recorded values.
- Foreclosure quotations: the five figures are sent as typed in whole paise and shown as quoted; a mismatch is flagged and never corrected.
- Security release: the closure page states that Udofin holds no collateral and never confirms a release; the confirm form appears only for a person holding `servicing.document.issue` in that lender.
