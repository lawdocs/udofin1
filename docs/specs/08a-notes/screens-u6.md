# Phase 08a notes: operations portal screens for payment providers, the account registry, feature switches and platform exceptions (builder u6)

Code: `packages/portal-kit/src/accounts/**` (client, loaders, allow-listed operations, wording, views), the pages and server actions in `apps/ops-portal/app/providers/**`, `apps/ops-portal/app/accounts/**`, `apps/ops-portal/app/features/**` and `apps/ops-portal/app/exceptions/**`, tests in `packages/portal-kit/test/accounts-ops.test.ts` (88 tests, node environment), `packages/portal-kit/test/accounts.test.tsx` (111 tests, jsdom) and the fixtures `packages/portal-kit/test/accounts-fixtures.ts`. The API these call is described in `api-lender-accounts.md` and `api-lender-payments.md` (exceptions); the contracts are `packages/contracts/src/http/lender-accounts.ts` and `lender-payments.ts`. Spec: `docs/specs/08-servicing-payments-mandates-collections.md` sections 5, 7.1, 16 and 17 (ops portal list). These screens are for Udofin platform staff only. Nothing here claims that anything is compliant, approved by a regulator or safe: an evidence label is shown as what a member of staff recorded.

## What the screens do and do not do

- **Show, never decide.** Every status, date and label is the one the API returned, in plain words from closed tables (`wording.ts`). Times are written in IST. A value or code the table does not know is shown as "has no wording for", never as it came. A failed load says "Could not load ..." and repeats nothing the API said (tested with a hostile code in every page).
- **Two-person steps are enforced by the database; the screens do not offer the second step to the first person.** The person who registered an account is not offered "verify"; the drafter or proposer of a rule is not offered "approve"; the proposer of a key version is not offered "approve"; the requester of a switch change is not offered "decide" (they are offered "cancel", the one thing only they may do). The words say why. This hides a form; the API and the database still refuse it (`self_approval`, `segregation_of_duties`).
- **Write forms follow the four platform permissions** (`platform.payments.providers.manage`, `platform.accounts.registry.manage`, `platform.accounts.registry.verify`, `platform.features.manage`), read from `/v1/me`. A role without the permission sees no write form, only plain GET filters.
- **One allow-listed operation per form.** `ACCOUNTS_OPERATIONS` is the only way a form can write. Each operation is declared for `['ops']` only (the lender portal cannot run it), maps to exactly one API route, checks its fields again and then checks the finished body against the same contract schema the API uses. An unknown operation, a prototype name, a bad request key, or the account registration through the general entry point is refused without any call to the API. A request key is minted when the page renders, so a double click or retry applies once.
- **A client of its own for `/v1/platform`.** The generic client of `@udofin/auth-client` cannot reach `/v1/platform` on purpose (its test says so), and I was told not to weaken it. `createPlatformClient` (`accounts/client.ts`) is a server-only client with its own allow-list of exactly the routes these screens call (reads and writes separately, tested path by path), the signed-in person's token, no retry (a retry would send an account number twice), no followed redirect, and failures reduced to a stable code. The only extra it keeps from a failure is the list of reason identifiers of a refused feature request (below), read from the problem `detail` and filtered to identifier shape. See "Shared file requests".

## The account number (CLAUDE.md rule 3)

There is exactly one place a full account number is typed: the "Register an account" form on `/accounts` (and the "Re-register under key version n" form on an entry, for a key rotation).

- **Typed once, in a password-type field** (`autocomplete="off"`, no spell check, `inputmode="numeric"`, no `value`). The IFSC is treated the same way. There is no second field to confirm against and no client component: the form is server-rendered, so there is no client state to keep.
- **Its own entry point.** The form names no operation and posts to `registerAccountAction`, which serves `account.register` and nothing else whatever the form says. The general entry point (`platformAction`) refuses `account.register` without calling the API. A test fails if the form is given an `op` field or the general entry point serves the registration.
- **One request.** The number is read from the form, placed in the request body of `POST /v1/platform/accounts` and nowhere else: not in a path, a query, a header, the request key, an outcome, a redirect address, an error, a cookie, a log line or a thrown error (a throw while sending is replaced by `network_error`). The outcome of a registration is the registry identifier only, not even the masked reference.
- **What the next page shows.** The server action redirects to `/accounts?registered=<registry id>` (or `/accounts?error=<code>`). The page reads that entry from the API and shows the masked reference the API returned (for example `XXXXXX1234`) and its status. It never shows more. The fields of the form after a redirect are empty (a fresh render).
- **Refusals** (`account_number_invalid`, `ifsc_invalid`, `owner_invalid`, `account_already_registered`, `key_management_unavailable`, ...) are fixed sentences. A server that writes the number back in its error text is ignored (tested: the problem `title` and `detail` carry the canary number and nothing reaches the outcome, the address or the page).
- **Tests of this.** `accounts-ops.test.ts`, "the account number: typed once, posted once, to one route": one request on the wire (through the real client with a stub transport), the number in its body exactly once, not in the URL or headers, not in the outcome, the redirect address, a refusal, a thrown error or a network failure. `accounts.test.tsx`, "Registering an account": the form has one password field with no value, no operation field, nothing preselected, no field holds a value in any of ten states (success, five refusals, a network failure, an unknown code, a failed load, an empty list), and the rendered HTML holds neither the canary number nor the canary IFSC nor any run of nine or more digits (UUIDs stripped first).
- **Run against the built portal** (not committed): a one-off script started the production build of the ops portal with fake sign-in and a fake API, signed in with the second factor, fetched `/accounts`, posted the registration form the way a browser without JavaScript does (the hidden fields include the server action id), and checked: a 303 to `/accounts?registered=<uuid>`; the page after it shows `XXXXXX3628` and not the number; the fake API saw exactly one `POST /v1/platform/accounts` whose body held the number once; no API request line or header, cookie or portal output held the number or the IFSC; a refusal whose problem text echoed the number redirected to `?error=account_number_invalid` and showed no number; the general action refused `account.register` and sent nothing; every page of this area answered 200; collections showed as not available with no form for it; a malformed lender id in the address never reached the API. 34 of 34 checks passed.
- **Limits, honestly.** JavaScript strings cannot be wiped, so what is guaranteed is that no log, serialiser, address or stored record of this code reaches the number. A browser may offer to remember a password-type field; the attributes ask it not to, and nothing here can force it. The number is in the multipart body of the server-action request between the browser and the portal (as any form field is) and in the JSON body to the API, both over TLS in a deployment; the transport is not changed here.

## Switches that can never be enabled

Collections and the default loss guarantee are drawn as "Not available in this release. This switch cannot be enabled." with the catalogue's own recorded reason, and **no control of any kind**: no form, no button, no field, in the catalogue view and in the per-lender view. Two independent guards hold this: the screen locks any feature whose catalogue row says `enableable: false`, and also any feature on its own list (`collections`, `dlg`) even if the catalogue were wrong. A third guard sits in the operation: `feature.request` with `direction=on` for either feature is refused before any call. The emergency switch-off can only switch off (its body has no way to say otherwise).

## Reasons a switch cannot be enabled

There is no read route that lists a lender's unmet prerequisites. The reasons are available only in the refusal of a request (`409 prerequisites_unmet`, `detail` "Reasons: a, b"), which the platform client reads as identifiers (filtered to identifier shape, at most ten) and the screen shows in plain words from a closed table of the reasons the database can give (`featureReasonWords`), with a mock or sandbox payment configuration described as "for testing only". A reason that is not in the table shows as "another reason that this screen has no wording for"; no identifier is printed. Before a request is made, the page cannot say what is missing (see gaps).

## Not built, deviations and gaps (honest list)

- **Shared file: the generic client cannot reach `/v1/platform`.** I did not edit `packages/auth-client`. `createPlatformClient` lives in portal-kit instead (see above). If the lead prefers one client, `packages/auth-client/src/api-client.ts` could gain a platform-staff allow-list (and its test); then `accounts/client.ts` can be deleted and the pages pass the generic client. The allow-list in `accounts/client.ts` is the list to copy.
- **The fingerprint key source is not wired in the running API** (`api-lender-accounts.md` section 0): `POST /v1/platform/accounts` answers 503 `key_management_unavailable` until the lead wires it, and in staging and production no key manager exists. The screen says so in plain words ("Registering an account is not available here yet: the key service is not set up. Nothing was stored.") and nothing was stored.
- **Reasons before a request.** See "Reasons a switch cannot be enabled": there is no read route for unmet prerequisites, so the reasons appear only after a refused request. A read route (`GET /v1/platform/lenders/:id/features/prerequisites`) would let the page show them first. I did not invent a client-side workaround.
- **The list of lenders comes from the onboarding list** (`GET /v1/onboarding/lenders`, needs `onboarding.read`). A person without it gets a text field for the lender's identifier instead of a named choice. Staff are not listed anywhere, so "Assign" offers the person's own identifier, which they may replace by a colleague's.
- **Rule lengths are shown from the API.** A rule's shortest and longest number of digits (the seed is 9 to 18) is shown exactly as the API returns it, next to the word "(unverified)" when its evidence label is unverified, with the source note beside it. The screens hard-code no regulatory figure, deadline or limit. The notes mark the seeded rule as an unverified assumption; whether to show it at all before a source is supplied is an **owner decision**. Approving an unverified rule is a recorded platform decision, not evidence: the page says so on the rule.
- **Platform view of payment configurations is not built.** `GET /v1/platform/payment-configs`, `.../retire` and `.../suspend` (the platform kill switch of a lender's configuration) have API routes but are not in this brief; no screen calls them.
- **Return-code classes cannot be retired.** The contract has no retire input, only "set" (replace); the screen offers only that.
- **Resolved exceptions are read through the shared route.** `GET /v1/platform/exceptions` leaves resolved ones out, so the "Resolved" view uses `GET /v1/lender/reconciliation/exceptions?owner=platform&status=resolved` (allowed to platform staff with `platform.payments.providers.manage`, per the API notes). A resolved exception that a lender owns is never listed there.
- **Free-text notes of an exception are shown as written.** The database screens exception notes only for length (API notes, item 7), so a note could hold personal text; the history page prints it labelled "Note written by staff", escaped by React. Owner decision: screen notes in the database, or remove free text.
- **Subject identifiers.** The subject of an exception is printed only when each key and value looks like an identifier; anything else is counted ("2 recorded values are not shown ...") and not printed.
- **Additions beyond the brief, thin and tested:** the exception history page, the "Resolved" view, the re-registration form for a key rotation (the API's `rekeysRegistryId`; without it a rotation cannot be completed over HTTP), and the filters on every list.
- **Evidence for a switch request is three label and reference pairs.** The label is a lower-case identifier the contract requires; the reference is short text. No file evidence (the API takes none).
- **No client-side validation of the digit-run rule in free text.** The API refuses reasons and notes that hold nine or more digits or a PAN-shaped token with a generic `validation_failed`; the forms warn in their hints and the screen says "Please check the values you entered".
- **Pages are not unit tested.** The Next.js pages and the two server actions are thin (session, client, load, draw); their logic lives in portal-kit and is tested there. `apps/ops-portal` has no test runner and `tests/e2e` was not extended (its fake API would need the new routes, and `playwright-core` is not installed in this worktree), so there is no committed browser test. The one-off script above is the substitute, and it is not part of CI.
- **Colour and contrast.** No new colours or classes were added; meaning is always in words. A contrast check against the theme tokens was not run.
- **Hindi.** The operations portal is English only, as in earlier phases.
- **Controls matrix.** `docs/regulatory/controls-matrix.md` was not edited (not my file). Rows for the registry, merchant verification, the evidence label of a rule or provider and the feature switches are for the lead; the screens present the facts above and claim nothing.
