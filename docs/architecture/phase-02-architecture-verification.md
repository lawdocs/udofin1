Sensitive data crossing boundaries: phone number (read at send time inside a transaction, never stored in Udofin tables; lender portal reveals it through an audited call); documents (bytes only after a database authorisation call; hash verified); step-up codes (HMAC-hashed). Business logic lives in Postgres functions plus `packages/domain`; clients hold none.

## 2. Modular monolith and domain boundaries

A modular monolith remains appropriate. Evidence: nine modules each consist of routes calling database functions; the only imports between module folders are three uses of the `columns` SQL helper from `onboarding/sql.js` (by `borrower`, `products` and `panel`), and there are no circular dependencies (search of `services/api/src/modules`); that helper belongs in a shared folder; shared behaviour sits in `http/`, `db/`, `auth/`, `idempotency/`. Provider logic is behind `packages/adapters` ports and `src/system`. There is no concrete scaling, isolation or security reason for another deployable. The two existing extra processes (worker, callback receiver) are justified by a security boundary (the public API never holds the system login).

Boundaries to document now: tenancy/identity, onboarding (gates, engagement, products), lending (routing, offers), documents, and the system-login rule. Can stay flexible: notifications (only SMS exists), reporting (only the lender panel feed exists), financial operations (read models only).

Weak spots (not defects): module routes also contain some SQL strings and shape mapping (for example `panel/routes.ts`); database functions are the real domain layer, so "module" boundaries are mostly route files plus naming. That is acceptable at this size but should be a written rule (A-01 in the audit).

## 3. Frontend, backend and data-access boundaries

- Clients call only `/v1/*` (an allow-list in `auth-client/src/api-client.ts`); no client has database or storage credentials. Mobile holds no privileged keys. The earlier allow-list defect (blocked borrower paths) was fixed in Phase 07 and is covered by tests.
- Decisions are server-side: eligibility, validity windows, approval, acceptance, step-up. Shared types come from `packages/contracts` (zod), which are runtime validators, not only types; the API also validates responses.
- Shortcut to note: forms in `portal-kit` are allow-listed "operations" that map form fields to API calls. They re-validate and the API validates again, so the shortcut is safe, but `portal-kit` is now security-relevant code.

## 5. Multi-tenancy and authorization (verified rule)

Actors: platform operator (Udofin staff with platform roles), lender organisation members, borrowers (cross-lender by design, seen only through per-lender consented sharing), providers (no identity in the system; they reach the API only through signed callbacks). Tenant identity is derived from authenticated identity plus database membership, never from a request field. Workers re-read the tenant from the claimed row; the system login can only `SET ROLE service_role`; deployment config refuses equal user and system URLs.

Rule to adopt as written policy (Decision D-Q1): _tenant ownership is a column on the row; membership is resolved only in the database; every request path runs as `authenticated` with claims; the system role is used only by code in `src/system` and `src/workers` and must take tenant ids from persisted rows, never from the message payload alone._ The current code follows this; it should be an ADR so it binds future work.

Gaps: access tokens outlive sign-out (F-01); `documents` is missing from the grant snapshot test (F-07); rate limiters are per process (F-05, F-06).

## 6. API, integration and background processing

- Contracts: `/v1` prefix, zod validated, RFC 9457 errors with stable codes, cursor pagination on lists, request ids validated, generated OpenAPI checked for staleness. No second API version exists, so compatibility policy is untested (ADR 0012 covers intent).
- Idempotency: 89 of 90 POSTs; fingerprint is a hash of the request; a replay returns the first response; concurrent duplicates block on the unique index.
- Outbox: event is written by `ops.enqueue_event` inside the business transaction (atomic); delivery is **at-least-once** with idempotent handlers; leases expire to a dead state; permanent versus retryable errors are distinguished. The design makes **no exactly-once claim**. Ordering is not guaranteed and handlers must not assume it. Operational recovery (replaying dead events, alerts) has no tooling or monitoring yet.
- Webhooks: Send-SMS hook uses a Standard Webhooks signature with a replay cache that is per process (F-06). The lender callback receiver verifies signatures before touching the database for mock lenders; the real signature scheme per lender is undefined (D-43) and `api`-kind lenders return 503.
- Finbyx and third-party LOS/LMS: `LenderConnector` port with a mock and a manual mode; no real connector. Recommended contract (to approve, no implementation): a lender-neutral envelope of `{message id, lender id, type, occurredAt, payload}` signed per lender, an idempotent inbound endpoint keyed by message id, and an outbound push with a status lookup for uncertain sends. This is already the shape of `lending.inbound_messages` and the connector port.
- Integration configuration is separate from proof of readiness: lender `connector` rows carry status, and activation gates (`onboarding.lender_gates`) require evidence; nothing is "activated" by configuration alone.

## 7. Financial and audit integrity

Money is integer paise end to end. Udofin holds no funds (ADR 0008), so most financial controls belong to lenders. Present: append-only snapshots, installments and provider events; intents immutable; only the system can finalise an intent; applications cannot become "disbursed" without evidence; offers are stored as supplied and never recalculated; the acceptance record is distinct from any signature or disbursement. Operational status versus confirmed event is kept distinct in the schema (lender-reported status is labelled as reported).

Current defect/risk: payment success guard (R-01). Future requirements, kept separate: reconciliation jobs, reversal/compensating entries for payments, a status history for `servicing.loan_accounts` (R-05), audit anchoring/export (ADR 0013), and a reconciliation report before any provider is enabled.

## 8. Deployment and operational readiness

Environments are described (dev/staging on Railway with synthetic data, production on AWS ap-south-1) but nothing is built: no IaC, no deploy pipeline, no monitoring, alerting, tracing, error reporting, backup/restore test, rollback runbook beyond text, or image/SAST/SBOM scanning. Migrations are forward-only SQL applied by the Supabase CLI in CI against a fresh database; applying them to a managed project with existing data has not been rehearsed. Local build and CI success do not demonstrate any of this. The prompt's assumption "Railway" matches ADR 0010 only for non-production; production on Railway would contradict the residency rule in ADR 0010 (all Railway regions are outside India).
