# Independent security review of the Phase 01 baseline (10 October 2026)

Two reviewers attacked or audited the baseline independently of its author, and a third reviewer
(database schema) did not complete. This note records what was found, what was fixed, and what is
still open. **It is not a penetration test and not a statement that the system is secure.**

## Method and limits

- **Live attack on the database.** A reviewer applied the migrations to a scratch PostgreSQL 16
  database and tried to break tenant isolation, privilege boundaries, append-only history, payment
  and offer rules, consent and audit integrity with SQL, reproducing each defect it reported.
- **Code and configuration review** of the API skeleton, portal proxies, container and CI.
- **Verification gap.** A third pass was meant to try to refute every finding independently. It did
  not run (the session's usage limit was reached), so findings were verified by the author instead:
  each fix below has a test, and the new database tests were confirmed to fail against the
  pre-fix schema.
- **Not covered:** the schema reviewer never ran (a foreign-key index check was done by hand, see
  item N); nothing was tested on Supabase's hosted platform, only on local PostgreSQL 16 (CI runs
  the same tests on Postgres 17); no network-level or mobile-binary testing; no fuzzing.

## Findings and disposition

## Things the reviewers confirmed held

Cross-lender reads and writes on every domain table (composite keys, forced RLS); privilege
escalation through tenancy tables (no grants, no write policies); `anon` access (none); direct
DDL in domain schemas (denied); column-level tampering with tenant and borrower keys;
payment-state jumps and replayed webhooks; expired or terminal offers; consent against a draft
notice.

## Still open (carried into the roadmap)

1. The API's database login and per-request role switching are not built (Phase 02); until they
   are, no end-user traffic reaches the database.
2. Rate limiting is in-memory per instance (Phase 03: shared store).
3. Lifecycle sync test reads only the migration that defines the lifecycle; a later migration that
   changes transitions would not be compared (to be generalised when transitions first change).
4. Supabase auth settings in `supabase/config.toml` are local-development values; production auth
   settings (password policy, session limits, MFA enforcement) are not yet version-controlled
   (Phase 02/03).
5. Findings above marked "confirm on the hosted project".
